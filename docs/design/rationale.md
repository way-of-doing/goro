## Predicates initial wishlist

The design of the predicate grammar and specification in Goro was kickstarted by collecting a set of wishes and related observations made when these wishes come in contact with practical reality. This section documents the most important of them.

**We must be able to write `genre == "pop"` because it is most natural and convenient.**
This means that
- comparisons must not be too strict by default (you didn't write Pop with a capital P, it's Motörhead not Motorhead, etc)
- but there must be a reasonable way to take full control of the comparison

**A single value and multiple values must be easily handled with the exact same syntax.**
Data like artist and genre (and technically, almost everything else too) can appear zero, one, or multiple times for the same file. This will vary from one file to another and may vary across time even for the same file. It means that the syntax that answers the question "is this tagged to be pop", must be meaningful and make sense in all of these scenarios. Most importantly, the implication is that any operation on a single value must be syntactically and semantically valid even if the single value is logically replaced with a collection.

**It is not acceptable to stop batch processing midway through because of an error.**
Goro must be able to handle per-file hiccups gracefully.

**Strongly typed expression language.**
In a very constrained setting, perhaps automatic type conversions can work. In real life, and especially if you start adding features such as even simple addition and string concatenation, type juggling becomes a minefield of footguns.

**Multivalues design invariant.**
A value in a predicate is either **absent** or a bag of one or more occurrences: an unordered collection in which the same datum may appear more than once and duplicates are significant. A "simple" value is a bag of cardinality one, and everything stated in the documentation about simple values holds unchanged for a bag of cardinality one. No construct in the language is able to distinguish the two, and any proposed addition that could is for that reason alone the wrong design.

Absence is the only value of cardinality zero. There is no empty bag distinct from absence, and there is no bag that holds an absence: absence is a property of a whole value while unusability is a property of a single occurrence, so an occurrence that is not there is simply not an occurrence. A resolution rule that would discard an occurrence lowers cardinality instead, and a value all of whose occurrences are discarded is absent.

This invariant was originally written with plain `null` standing in for both the empty bag and a bag holding one `null`, which made it self-contradictory in a way that mattered, because the invariant is the test a proposed addition is measured against. `COUNT()` read that stand-in as the empty bag and returned zero, while the operator rules read it as a bag holding one unusable thing and evaluated to false rather than vacuously true. Naming absence as the cardinality-zero case, and denying that it is a bag at all, is what makes both of those correct at once.

One consequence of identifying absence with the empty bag has to be stated rather than derived. Ordinary quantifier semantics would make `ALL()` match vacuously wherever a value is absent, so Goro intercepts absence before iteration begins instead, which makes universal quantification non-vacuous. See the question on that below.

The invariant applies to every type, boolean included. A boolean is absent or a bag of occurrences like any other value, each usable or unusable, even though the operators and the boolean literals always produce exactly one occurrence.

_Definiteness_ does not breach the invariant, although it is a statement about cardinality. It is a property of an expression, decided by the text of the predicate: a literal, the result of an operator, or an identifier such as `file::size` that every file has exactly one of, is guaranteed to have exactly one occurrence for every file. It is never a property of a value, so an identifier that resolves to one occurrence for a particular file is not definite, and nothing in the language can tell its value from the result of a definite expression. What the invariant forbids is a construct that behaves differently for a bag of one; what definiteness provides is a construct that is known, before any file is read, never to produce anything else.

## Predicates Q & A

This section is structured as questions-and-answers, where the questions have been carefully selected to reveal the reasoning behind design decisions.

Q: **Why does a failed type conversion result in an unusable value rather than an error or a default?**
A: There are basically three options: a) result in some special value that signifies the failure, b) result to some default (e.g. zero or empty string), and c) error out and do not continue. Erroring out is out of the question because it could cause an operation on countless files to be aborted midway because one of them is not correctly tagged. Defaulting to something "neutral" is the classic type conversion footgun that could lead countless evaluations to produce an unintended result. Therefore the decision was made to use a distinct state, in particular one that can never cause a file to be selected: an operator that meets it cannot answer, its own result is unusable rather than true or false, and only a predicate that evaluates to true selects a file. This avoids processing files on the strength of something unexpected that happened while evaluating the predicate, does not stop a lengthy job midway, and, because the occurrence is marked unusable rather than merely empty, still allows the situation to be surfaced to the user.

Q: **Why do comparisons error out on different types instead of converting implicitly?**
A: A combination of reasons: the more types there are, the more complicated the implicit conversion rules become; conversions from string can easily fail and this is surprising when it happens implicitly; and the types of sub-expressions are very easily determined so it's not too much work to have an explicit conversion where needed.

Q: **Why does e.g. `STRING(120s)` result in `"120"` and not something prettier like `"120s"`?**
A: STRING() is a type conversion function; formatting for presentation should not be its concern.

Q: **Why is the warning rule stated in terms of what a construct reads rather than what it returns?**
A: Because stating it the other way round required three exceptions, and each of them was load-bearing. The original rule was that anything producing a non-null result from a tainted input consumes the taint and warns, which made operators always consume because they always produce a boolean — and then `ISNULL()` and `FALLBACK()` had to be carved out by name as sanctioned suppressors, and `COUNT()` had to be argued into consuming despite doing nothing with the datum. Restating the rule as **consuming means asking a question of an occurrence's content** leaves nothing to carve out. The comparison, range and regex operators ask questions -- they are where data turns into a truth value -- so they warn. `NUMBER()` and `STRING()` map an unusable occurrence to an unusable occurrence and ask nothing of it, so they propagate in silence. `COUNT()` reads cardinality, which is knowable without looking inside any occurrence, so it is silent and reports a count of one for a single unusable occurrence, data that cannot be read still being data that is there. `FALLBACK()` substitutes for an occurrence instead of reading it. A state test reads state, not content. The logical operators combine truth values. When a rule's exceptions are the interesting cases, the rule is stated at the wrong level.

The rule was once worded as "producing a result derived from the content of the occurrence". That wording stopped fitting when an operator that meets an unusable occurrence began producing an unusable boolean rather than false: such a result derives nothing from the content, and read literally the wording would have made the operators silent and left nothing to warn at all. Asking a question is what the operators do whether or not the question can be answered, which is why it is the better statement.

An operator's result can only be unusable because the operator consumed an unusable occurrence, which has therefore been reported already, so consuming the result again reports nothing new. That is a consequence of deduplication rather than a rule of its own, and it is also why such a result needs no source: every source that could have made it unusable has been reported by the time it exists, so an implementation may give it all of them, any of them, or none, with no observable difference.

Q: **Why is the default quantifier for a state test existential, when the conservative reading is the safer guard?**
A: The decisive argument is which way a mistake fails. A conservative universally quantified default fails silently: `ALL(NUMBER(x)) IS USABLE AND NUMBER(x) > 5` rejects a file holding one good track number and one piece of junk, emits no warning at all because `IS USABLE` is silent and `AND` short-circuits, and so quietly skips a file it could have matched — which is precisely the outcome the unusable state exists to prevent. An existential default fails loudly: the guard admits the file, an operator meets the unusable occurrence, and a warning says so. For a tool whose worst failure mode is silently operating on the wrong set of files, the noisy wrong answer is the better default, and the conservative reading remains available as `ALL(x) IS USABLE` for anyone who wants it.

Q: **Why is universal quantification non-vacuous, when absence is the bag of cardinality zero?**
A: Because the vacuous reading is both surprising and useless here. Set semantics would make `ALL(genre) == "rock"` true for a file with no genre at all, there being no counterexample to find, so a predicate written to narrow a selection would instead widen it to every untagged file in the collection. Nobody writing that predicate means it. Rather than give the quantifier unusual semantics of its own, the rule is placed where it reads naturally: an absent operand makes a comparison, range or regex operator false before any iteration runs, which is the same rule that already makes `id3v2::track < 5` and `id3v2::track >= 5` both false for a file with no Id3v2 tag. Non-vacuity is then a consequence of how absence is handled rather than a special case in the quantifier, and the only operator exempt is the state test, whose job is to observe absence in the first place.

Q: **Why does an operator that meets unusable data produce an unusable boolean, rather than false?**
A: Because false is a claim, and the operator is in no position to make it. A comparison that could not read the data it needed has no answer, and the difference between "no" and "no answer" matters as soon as anything negates the result. With false standing in for both, `NOT year >= 2000` selected every file whose year could not be read, and rewriting `NOT x < 5` as `x >= 5` -- a transformation nobody registers as one -- changed which files a predicate selected. The promise made about unusable data, that it never causes a file to be selected, held only for predicates without `NOT`.

Carrying the missing answer as an unusable boolean keeps the promise everywhere. The logical operators then follow with no further choices to make: each gives true or false whenever its other operand settles the matter, and unusable otherwise, which are the rules of Kleene's three-valued logic, and the quantifiers are the same rules applied across a bag. A predicate is true only if it would be true whatever the unreadable data had turned out to hold, so no file is selected on the strength of data that could not be read.

The change costs less than it looks. A predicate without `NOT` selects exactly the same files as before, since nothing but negation can turn false into true. What differs there is that an unusable first operand no longer settles an `AND`, so its second operand is evaluated and may warn as well, and that the command can tell a predicate that could not be answered from one that was false. Nor does it add anything to the value model: booleans simply stop being the one type exempt from having unusable occurrences, an exemption that turned out to be the cause of the problem rather than a simplification. What is given up is that a literally repeated condition is no longer guaranteed to cover every file -- `x < 5 OR NOT x < 5` is unusable rather than true when `x` cannot be read. Nobody writes that, and the forms people do reason with, a comparison and its complement, were never guaranteed to cover every file, absent values and multivalues having always seen to that.

Q: **Why does an absent operand still make an operator false, rather than unusable?**
A: Because false and unusable say different things, and absence is the case false describes. False means the operator was evaluated and found nothing to satisfy it; unusable means it could not be evaluated. A file that records no year is evaluated against `year < 2000` perfectly well, and there is simply no year to find. False is also the answer an existential quantifier gives over nothing, so rule 1 agrees with ordinary semantics for every operator except a universally quantified one, where it is what keeps quantification non-vacuous.

Making absence unusable would be the SQL choice, and would bring SQL's familiar trouble with it at a scale this tool cannot afford, absence being everywhere in a music collection: `NOT genre == "metal"` would stop selecting the files that record no genre at all, which is rarely what anybody means by "not metal". It would also erase the distinction the value model is built on, that absence is ordinary and unusability is a defect worth a warning. What remains is that a comparison and its complement are not complementary for an absent value, both being false. A multivalue does the same thing from the other direction, both possibly being true, and the specification explains the two together, as a consequence of cardinality rather than of anything going wrong.

Q: **Why must the operands of the logical operators be definite?**
A: Because the alternative was to decide what `NOT x` means for a boolean that may be absent or may hold several occurrences, and every answer is a choice the person writing the predicate would not see being made. No construct produces such a boolean today, but a boolean identifier read from tags -- a compilation flag, say -- would be one, and the question is better settled before one exists than after.

Take such a flag holding both a true and a false occurrence, or none at all. "No occurrence is true" and "some occurrence is false" are both reasonable readings of `NOT compilation`, and they disagree on exactly those two files. General operator rule 1 cannot be extended to the logical operators to settle the matter, since it would make `compilation OR year < 2000` false for a file with no flag even when the year matched. The only workable rule would be an implicit comparison, reading `b` as `b == TRUE`, which is an implicit conversion of exactly the kind this language refuses elsewhere, and a construct defined by rewriting it into another.

Requiring the operands to be definite settles all of this without deciding any of it. Definiteness is known from the text, so the requirement is checked before any file is opened; the logical operators only ever see a single occurrence that is true, false or unusable; and a boolean that is not definite becomes one through a comparison that says which reading is meant, `compilation == TRUE` or `compilation == FALSE`, with every rule that already governs comparisons applying to it unchanged.

Q: **Why must `!=` be given a quantifier on an operand that is not definite?**
A: Because the default quantifier gives it a meaning almost nobody intends. `genre != "metal"` read existentially is true when some genre is not metal, which includes a file tagged both "metal" and "rock", while the person who wrote it nearly always meant "not metal". XPath's general comparisons have exactly these semantics, `$x != 'a'` being that language's best-known trap, and XPath 2.0 added a second family of comparisons to escape it. The mistake is also silent: the predicate selects a plausible set of files with a few wrong ones among them, on the kind of collection where nobody checks by hand.

Nor is there one right reading to substitute. `NOT genre == "metal"` and `ALL(genre) != "metal"` agree on every file that records a genre and part company on a file that records none, which the first selects and the second does not. Both are reasonable, so making either one the meaning of `genre != "metal"` would decide silently for the person who wrote it. An error puts both in front of them instead, at the one moment they are paying attention, and costs a few characters once.

Three other courses were considered. Keeping the existential reading and relying on the documentation leaves the trap where XPath left it, catching exactly the people who did not read that part. Giving `!=` a universal default of its own would make it the one operator whose operands do not default to the same quantifier as everywhere else, and would still choose between the two readings above on the writer's behalf. Removing `!=` altogether would force the negation to be spelled out, but would forbid it where nothing is ambiguous, as in `COUNT(genre) != 1`, and would greet the person typing it with a syntax error where a diagnostic could tell them what to write; the reasoning is the same that keeps `NULL` reserved.

The rule turns on definiteness rather than on a value holding several occurrences, for two reasons. An error has to be decided by the text, and how many occurrences a value holds is decided by the file. And the trap is not only about multivalues: `id3v1::genre` can never hold more than one occurrence, yet `NOT id3v1::genre == "blues"` and `ALL(id3v1::genre) != "blues"` still disagree about a file with no Id3v1 tag. A definite operand is the one case in which every reading agrees, which is why it alone is exempt. It is also why `file::path`, `file::name` and `file::size` are declared definite: on them the error would offer two fixes that mean the same thing, which is no help to anyone. Like the requirement on the logical operators, this one is about the text of a predicate and never about a value, so it tells apart nothing that the multivalues invariant requires to look alike.

`!=` is singled out because it is the only comparison whose test is itself a negation, and an existential over a negation is what reads wrong; `=~` and the state test avoid the question by having no negated form at all. Nothing about evaluation changes: a quantifier written on an operand of `!=` means what it means on any other operator, and `ANY(genre) != "metal"` evaluates exactly as `genre != "metal"` used to.

Q: **Why is the treatment of a file whose predicate could not be answered left to each command?**
A: Because the safe direction depends on what the command does. A command that changes files should not act on a file it could not decide about, while a command that exists to account for every file -- hashing a collection to find bit rot, say -- should not quietly leave one out. While booleans could not be unusable there was no choice to make, since a predicate that could not be answered had already become false by the time a command saw it; keeping the missing answer until it reaches the command is what lets each command choose. `goro list` does not list such a file, a condition that could not be answered not having been satisfied, which is also how it treats a file it could not read.

Q: **Why are booleans unordered, and why do `NUMBER()` and `STRING()` not accept them?**
A: An order on truth values would be a convention rather than a fact -- false below true is the usual one, and means nothing in a predicate about music -- and nobody filtering a collection needs one. Conversion to and from text and numbers is a different matter: it will be wanted once booleans come from tags, and is better decided then, together with what tag text a boolean identifier accepts, than invented now with nothing to test it against. Both restrictions can be lifted later without changing the meaning of any predicate that is valid today.

Q: **Why are warnings deduplicated per file and per source, rather than once per run or once per place in the predicate?**
A: Once per run would be nearly useless, since it would only tell you that something somewhere in a hundred thousand files is malformed, when the whole point of the warning is to let you go and fix the data. Once per occurrence would be noise: a predicate that mentions the same tag three times has one bad tag to report, not three. Deduplicating by the _source_ of the datum rather than by the place in the predicate that touched it is what makes the number of warnings track the number of things that are actually wrong. It does not match it exactly: a source is a sub-expression, so one identifier resolving to three unusable occurrences in one file reports once rather than three times. Reporting the identifier and the file is enough to send somebody to the data, which is what the warning is for.

The intended implementation is that every occurrence which can be unusable carries a source, and that a source is the sub-expression which produced it: a symbol together with the sources of its arguments, in order of appearance, compared recursively. Note that the sources of the arguments are those of the argument sub-expressions themselves and do not depend on which value happened to flow out of them at runtime, so a source is a static property of the predicate. Since a source is therefore precisely the shape of the predicate's own syntax tree with positions erased, the distinct sources can all be identified once when the predicate is read, by assigning each structurally distinct sub-expression a small integer; an unusable occurrence then carries that integer and the per-file deduplication set is a bitset indexed by it. Interning the sub-expressions bottom-up keeps the comparison cheap, because by the time a parent is considered each of its children has already been reduced to an integer.

Two consequences are worth keeping in mind. The set of warnings a predicate is capable of emitting is enumerable before any file is read, which is directly testable. And the modifiers `ALL()`, `ANY()` and `LITERALLY()` must be transparent when sources are assigned, since they do not produce values of their own: treating them as distinct symbols would report a single bad tag twice.

Note that a warning's identity and its presentation come from different places. The interned source decides whether a warning has already been emitted and is deliberately position-independent, which is why the modifiers are transparent in it. What the warning quotes comes instead from the syntax node the value was actually born at, together with the span of predicate text that node was parsed from. Keeping the two separate is what allows the message to reproduce what the user wrote while the deduplication still treats two differently-written but equivalent fragments as one thing. The distinction also explains why transparency needs no special handling at the top of a source: a modifier can never produce an unusable occurrence in the first place, so it is never the birth node of one.

Q: **Why does Goro define its own normalization, rather than adopting a standard or a library's?**
A: Because there is no standard to adopt, and no library that does the right thing for a music collection. Unicode's own attempt, UTR #30 "Character Foldings", was withdrawn in 2008 without being approved, and what survives of the idea, NFKC_Casefold, folds case and compatibility forms but removes no accents. The usual recipe -- decompose, then drop every combining mark -- is what this specification first said, and it fails exactly where a music collection reaches: it equates ガンダム with カンタム, strips Thai tone marks and Devanagari vowel signs, and without recomposition makes regular expressions unable to match Korean text at all. Unicode's `Diacritic` property is no better a guide, since it too includes the kana voicing marks, Thai tone marks and Devanagari vowel signs. ICU collation at accent-insensitive strength, which .NET exposes through `CompareInfo`, makes most of the same equations, produces sort keys rather than a string a regular expression can be matched against, and measured two to six times slower than the rules adopted.

The rules are instead assembled from practice that has held up. Accents are stripped only from particular scripts, as SQLite's full-text search does for Latin. The letters without a decomposition are folded by a table that matches PostgreSQL's `unaccent` almost entry for entry, including its choice to fold `ё` and not `й`. Compatibility forms are folded and default-ignorable characters removed, as NFKC_Casefold and Lucene's ICU folding filter both do. And kana voicing marks are kept, their folding by MySQL's general Unicode collation being a long-standing complaint from Japanese users. A set of smoke tests and a rough benchmark were run against the choice; on a corpus of tag-like strings the adopted rules were faster than the original recipe, mainly because ASCII strings, the large majority, need almost no work.

Q: **Why does literal mode still compose characters?**
A: Because a literal comparison is meant to compare what a tag says, and a precomposed `ö` and an `o` followed by a combining diaeresis say the same thing. Without it, `LITERALLY(artist) == "Motörhead"` would fail for a file whose tagger stored the decomposed form, with no visible difference anywhere to explain why. The cost measured a few tens of nanoseconds per string, and nothing for text made entirely of characters below U+0300, which is what most tags are.

Q: **Why are strings ordered by code point rather than by UTF-16 code unit?**
A: Because the two orders differ for characters outside the Basic Multilingual Plane, and code point order is the one that does not depend on an encoding: it is the order of Unicode itself, and of the bytes of UTF-8. The difference costs nothing measurable.

Q: **Why does the regex operator normalize its subject but leave the pattern alone, when every other operator normalizes every string it compares?**
A: Because a pattern is not a value being compared; it is a program, and normalizing it rewrites it. The documentation already refused to case-fold a pattern on exactly that ground, and the argument does not stop applying merely because the rewrite is Unicode decomposition rather than case-folding. Stripping combining marks from a pattern can alter its structure and not only its literals: `e\u0301?`, an optionally accented `e`, becomes a bare `e?`, which is a different proposition about a different number of characters.

What the change costs is a coincidence that used to work. Under the old rule a pattern written with a diacritic had the diacritic stripped out of it, so it matched the equally stripped subject by accident; now the pattern keeps its `ö` and the subject has none, so it matches nothing. The rule a reader has to remember is unchanged -- a pattern cannot express a condition on a diacritic -- but it now follows from something true about the subject rather than from the pattern having been quietly edited to suit, and `LITERALLY()` is there for anyone who means to match one.

A static diagnostic for the case was considered and rejected. Warning that a pattern contains a character normalization removes would be wrong often enough to be a nuisance: `mot[öo]` contains such a character and matches a normalized subject perfectly well, so telling the difference needs real analysis of the pattern rather than a scan for marks, and that is a great deal of machinery for a mistake the documented rule already explains.

Q: **Why is regular expression matching specified as non-backtracking, when that rejects lookaround and backreferences?**
A: Because the alternative is a matching timeout, and a timeout makes the result of a predicate depend on the machine the run executed on and on what else that machine was doing at the time. This documentation objects to that elsewhere in a much milder form -- it is part of why a duration is whole seconds -- and the objection is far stronger here, since a run's purpose is to decide which files to touch. A timeout does not merely slow such a run down; it silently changes the answer, and it does so on the large collections where a person is least able to check.

The non-backtracking engine removes the need for one outright. A match takes time linear in the length of the subject whatever the pattern, so there is no catastrophic backtracking to contain and nothing to abandon part way through.

The price is that four families of construct are unsupported: lookaround, backreferences, atomic groups, and conditionals or balancing groups. That is a real loss and it was weighed rather than waved away. Two things make it acceptable. The construct anyone misses first is negative lookahead, and it is most often reached for to say "does not begin with" -- which this language already says better as `NOT (artist =~ r"^The ")`, at the level of the predicate, where a reader can see the negation instead of having to decode it. And rejection needs no new machinery: a pattern using an unsupported construct is a static error, like any other invalid pattern.

Keeping a backtracking engine alongside, for the patterns that need those constructs, is the obvious way to have both. It was not taken because it would hand the nondeterminism back for exactly the patterns using them, while doubling the number of engines whose behaviour has to be described. It is recorded as a deferred question rather than closed off, since a concrete want might change the balance.

Q: **Why does a numeric literal not stand for a string?**
A: To keep the two directions alike. `year == "2000"` was always an error, and a language that rejected the quoted number while silently accepting the bare one would surprise in the direction that matters: every identifier in a raw namespace is string-typed, and an ordering comparison over decimal text, such as `id3v2::raw::TRCK > 9`, is almost never what anyone means.

Q: **Why is a number a `System.Decimal`?**
A: Because base ten makes the claims the specification makes elsewhere true rather than nearly true: `1.4kib` is exactly 1433.6 bytes, and a decimal fraction written in a predicate is the value it appears to be rather than the closest approximation a binary fraction can manage. The range is ample for any music collection -- the largest value the type holds is some hundreds of thousands of times greater than the total quantity of data in existence, counted in bytes -- and Goro performs no arithmetic on numbers beyond conversion and comparison, so there is nowhere for precision to drift to.

Q: **Why is there no `IS NOT`?**
A: Because it would express nothing new. The quantifiers are explicit, so every negated reading is already available by applying `NOT` to a state test: `NOT (ALL(x) IS USABLE)` says that not every occurrence is usable, and `NOT (ANY(x) IS USABLE)` that none is. An `IS NOT` would add a second spelling, and with it another instance of the `!=` versus `NOT ==` distinction, which on a multivalue makes `x IS NOT USABLE` and `NOT x IS USABLE` mean different things.

Q: **Why are durations whole seconds, when a file's actual playing time is not?**
A: Because the alternative is that `file::duration == 4m5s` silently matches nothing, which looks exactly like a collection that genuinely has no such file. Answering "you are not supposed to use equality on durations" would leave a loaded footgun in the language for the sake of precision nobody wants: nobody writes `4:40.123456`, and if sub-second literals existed the same person would meet the ordinary floating-point equality trap in a new place instead. Truncating makes the precision of a value equal to the precision the syntax can express, which is the property that makes `==` trustworthy. Truncation rather than rounding matches the way playing times are conventionally displayed. For the same reason a bare number standing for a duration must be a whole number: anything accepted as a number of seconds should be accepted with an `s` after it, and `1.5s` is not a literal.

Q: **Why does an interpreted identifier trim, and why is a field holding nothing but whitespace absent rather than an empty string?**
A: Because the engineer's answer and the user's answer differ here, and the user's should win.

The engineer's answer is that an empty string is a perfectly good string and throwing it away discards information. That is true, and it is the wrong instinct in this position. Somebody who writes `artist IS ABSENT` to find the files with no artist on them means the files with no artist on them. A file whose artist frame holds three spaces has no artist by any reading a person would recognise, and a rule that reported it as *present, holding the empty string* would make the obvious predicate miss the obvious file, for a reason nothing in the predicate text could reveal. That is the shape of a trap, and the same argument runs for trimming generally: the widespread convention of putting a space after a separator means a `TCON` frame reading `Rock; Metal` has to yield `Metal` and not `" Metal"`, or `genre == "metal"` fails on one of the most ordinary genre tags in existence.

No information is discarded, though, which is what makes the choice cheap. It is moved to where somebody who wants it will look. The interpreted namespaces make innocent assumptions for your convenience and the raw namespaces make none at all, so `id3v2::raw::TPE1` still shows the three spaces, and `LITERALLY(id3v2::raw::TPE1) =~ r"^\s+$"` still finds every file whose tags were written that way. Simple things stay simple and the complex thing remains possible, which is the whole of why the two kinds of namespace exist.

There is one asymmetry worth defending rather than smoothing over. A field holding nothing is absent for a string-typed identifier and an *unusable occurrence* for one of any other type. The dividing line is whether interpretation was involved. A string needs none, so nothing there means nothing was recorded. A number needed the text interpreted and the text failed to supply anything to interpret, which is a defect in the file rather than an absence of information, and a warning is the right response to a year frame that fails to say a year.

Q: **Why is an Id3v1 field that holds nothing but padding absent, when every Id3v1 tag has every field?**
A: Because in a fixed-layout format the presence of a field says nothing about whether anything was put into it. The four bytes of the Id3v1 year field exist in every Id3v1 tag ever written, so treating a blank one as recorded-but-unusable would warn about a substantial fraction of any real collection while telling its owner nothing they could act on.

Q: **Why is a year of `0000` unusable rather than zero?**
A: Because the Gregorian calendar has no year zero, and because the case is common rather than exotic: `0000` is what a great many taggers write into an Id3v1 year field they have nothing to put in. Resolving it to zero would make `id3v1::year == 0` true across a large part of a collection and `year BETWEEN 1900..2030` quietly false for the same files, with no warning and nothing at all to notice.

Q: **Why does the global namespace fall through on usability rather than presence, and discard the defects it routes around?**
A: All of the global namespace exists to serve one goal, which might be framed as "the obvious naive attempt should succeed". Somebody who wants the files by Metallica should be able to write `artist == "metallica"` and get them, without first having to learn which tag formats their collection uses, which of them this particular file carries, how each one spells things, or that on some tracks Metallica are not the only artists performing. The ranking, the fall-through and the short-circuiting are machinery in service of that one sentence working.

Usability rather than presence decides the fall-through because the whole point of consulting several formats is to come back with something usable; a preferred format holding junk should not stop the search. And the defects routed around are discarded silently because a facade that reported every one of them would warn constantly on precisely the collections it exists to make bearable. That is the price of the convenience, and it is why the format-specific namespaces are the supported way to be precise.

Q: **Why are Id3v1's raw genre and track typed as numbers, when every other raw identifier is a string?**
A: Because a raw identifier reports the datum as recorded, and what Id3v1 records for these two is a single numeric byte rather than text. The choice is arbitrary only in the sense that the format is, needs no further rule, and earns two things. A junk index can be named exactly, as in `id3v1::raw::genre BETWEEN 148..254`. And a predicate that asks this namespace for a genre *name*, `id3v1::raw::genre == "rock"`, is a type mismatch, rejected before a single file is opened instead of warning once per file across an entire collection.

Q: **Why is Id3v1 text that decoded wrongly still a usable occurrence?**
A: Because nothing can tell. Text written in a local codepage rather than ISO-8859-1 decodes without complaint and comes out wrong, and Goro has no way to know that it did; a state for it would never be assigned.

Q: **Why is the leading field of a clock-form duration unbounded, when the others are capped at 59?**
A: Because the capped version rejected the way people actually write a long playing time. `90:00` is what a player shows for a ninety-minute file and what anybody would type for one, and with every field bounded at 59 it was a syntax error while `90m` was fine -- an arbitrary difference between two spellings of the same duration, falling on the more natural of the two.

This is a case where the Pit of Success argument simply won, and it won cheaply, because there is nothing on the other side. An unbounded leading field introduces no ambiguity: the field count already distinguishes `#:##` from `#:##:##`, so nothing has to be guessed at, and a large value in the leading position is meaningful rather than suspicious. The only new obligation is to reject a value too large to represent, which any literal already carries.

The trailing fields stay bounded because there they are genuinely positional: `01:90` is not a longer duration than `01:59`, it is somebody having written the wrong thing.

Q: **Why must the period in a number literal be followed by a digit, so that `1.` is invalid?**
A: A trailing period was never intended to be meaningful in the first place, since it expresses nothing that `1` does not. It also causes trouble: allowing it would make `1..100` a pair of adjacent number literals rather than a range. Since a token is always taken as long as it can be, the lexer would swallow `1.` and be left with `.100`, and the range operator would never be seen at all.

Q: **Why may `ALL()`, `ANY()` and `LITERALLY()` only be applied to the operand of a comparison, when they would be harmless no-ops almost everywhere else?**
A: The initial intent was indeed to allow them anywhere and accept that `COUNT(ANY(artist))` means nothing in particular, on the grounds that a permissive rule is a shorter rule. Two things argued the other way.

The first is action at a distance. A modifier only takes effect when an operator consumes the value it was applied to, so the further a modifier can sit from that operator, the less the comparison says about how it will be performed. Today the distance is bounded by the predicate text, but a future in which a value can be given a name, or held between statements, would allow a value to be annotated arbitrarily far from every comparison that eventually reads the annotation. That is materially worse than the same problem for unusable occurrences, which also travel: an unusable occurrence announces itself with a warning when it is finally used, whereas a modifier silently changes the answer.

The second is that the two directions are not equally reversible. Restricting now and relaxing later is backward compatible, because predicates that were valid stay valid and a construct merely stops being an error -- a future function that wanted to read the comparison mode of its argument could simply document that it does. Being permissive now and restricting later breaks predicates people have already written. Since the expressiveness is recoverable and the compatibility is not, the restriction is the choice that keeps both options open.

The restriction also removes several questions that would otherwise have to be answered, and answered durably: what modification a function's result carries when its arguments were modified, whether that is the union over the arguments or comes from a designated one, and whether modifications attach to a whole multivalue or to its individual occurrences.

There was a fourth such question, and what became of it is worth recording, because it is the clearest evidence the restriction was the right call. The question was whether a null test should respect the quantifier applied to its argument, and it looked unanswerable: `NOT ISNULL(ALL(x))` reads like "none of them are null" while it would have meant "at least one is usable", a guard weakened by the very construct that makes it read stronger. The restriction is what stopped that from having to be decided, and the question then disappeared rather than being answered, because the guard became the `IS` operator instead of a function. An operator takes an operand, an operand carries a quantifier by the ordinary rule, and `ALL(x) IS USABLE` reads as exactly what it means. The expressiveness that the restriction withheld from functions arrived through the door it was always going to arrive through.

Note that the restriction is directional. A modifier may be applied to a function call, so `LITERALLY(FALLBACK(genre, "pop"))` is valid; only the reverse, a modifier inside a function's arguments, is forbidden. Modifiers go on the outside.

Q: **Why are the iteration loops over two multivalue operands nested by quantifier rather than in the order the operands were written?**
A: Nesting by written position is the more obvious rule and the more expressive one, since it can produce both the "for every ... there is some ..." and the "there is some ... for every ..." readings, where nesting by quantifier can only produce the first. It was rejected because of what it costs in exchange.

Nesting by position makes an operator's result depend on which side each operand was written on. The visible casualty is that `ALL(a) == b` and `b == ALL(a)` stop meaning the same thing, but the more dangerous one is that the identity `x < y` if and only if `y > x` stops holding: `a < ALL(b)` and `ALL(b) > a` would be different propositions. Flipping a comparison and swapping its operands is a rewrite people perform without registering it as a transformation at all, so that edge is one readers would walk into unaware, whereas moving an `ALL()` across an `==` at least looks like a change.

What nesting by quantifier gives up is the "there is some value of X that compares thus to every value of Y" reading, and for the operators where anyone would want it, it is available in a better form anyway. For equality it is degenerate: it can only be true when every value of the second operand is the same value. For the ordering operators it is really a statement about aggregates -- `a > ALL(b)` is "the largest value of `a` exceeds the largest value of `b`" -- which a `MAX()` or `MIN()` function would say far more legibly than a quantifier ever could, and which can be added later without changing the meaning of any predicate written in the meantime. The reverse is not true: adopting nesting by position and later wanting order-independence would change what already-written predicates mean.

There is also a plain simplicity argument. Nesting by quantifier supports the flat statement that the order of an operator's operands never affects its result, which is what a reader's intuition already assumes; nesting by position requires the reader to hold an extra rule and needs a warning attached to it. The reading that nesting by quantifier keeps is also the one with a name: `ALL(a) == b` is a containment test.

Q: **Why may no construct in the language be defined by rewriting it into other operators?**
A: Because an operator is a single quantifier scope, and splitting one into two logical operators creates a second scope, which changes the proposition. The rule has to be stated as a constraint on the language rather than fixed where it happened to bite, because what goes wrong is a habit rather than an instance: defining a compound operator by the equivalence a reader would use to explain it is the obvious thing to do, it is correct for simple values, and it is wrong for multivalued ones.

Both instances that existed were of that kind. `BETWEEN` was defined as "`min <= v` and `v <= max` are both true", which is exactly right as a description of testing one occurrence and exactly wrong as a rewriting: for a value with occurrences `0` and `20`, the operator is false while the rewriting is true, each of its comparisons finding a different occurrence to satisfy it. And a deferred note recorded that a set inclusion operator `x IN (a, b)` "can also be implemented as simple syntactic sugar around OR", which holds under the default existential quantifier -- an existential distributes over a disjunction -- and fails under `ALL()`, where the operator asks that every occurrence match one of the two candidates and the rewriting asks that every occurrence match `a`, or else that every occurrence match `b`.

Neither error was hard to make, and both were made by people who knew the quantifier rules, which is the argument for writing the constraint down rather than trusting care. It will be needed again by everything plausible that might be added: a set inclusion operator, `MAX()` and `MIN()`, and any arithmetic at all.

Q: **Why does iteration over a multivalue operand not short-circuit, when `AND` and `OR` do?**
A: Because short-circuiting there would make a run's warnings depend on the iteration order of a collection this specification declares to have no order, and warnings are observable.

The result is not at stake. A quantifier's answer does not depend on how many witnesses were examined, so stopping early and going on to the end give the same boolean. What differs is which occurrences were touched, and touching an unusable occurrence emits a warning. For a value holding one matching occurrence and one unusable one, an implementation that stopped at the first witness would warn or stay silent according to which occurrence it reached first -- and since a bag is unordered, that is a choice the specification has deliberately not made. Two implementations would differ, a release could differ from its predecessor, and `--strict-exit-code` would return `10` or `0` for the same file and the same predicate. That is nondeterminism in the one part of the design whose whole purpose is to be scripted against.

The alternative repair was to give bags an order -- the order the occurrences were read from the file -- and keep the short-circuit. It was rejected for two reasons. It would make a bag ordered in the single place the language claims it is not, purely to pin down a side effect, which is a poor trade for a property stated as prominently as unorderedness is. And it would not even work, since the order occurrences are read in is a property of the tag-reading library rather than of Goro, so the guarantee would rest on emergent behaviour of a dependency, exactly the kind of foundation the testing documentation exists to warn about.

Evaluating exhaustively costs nothing worth counting. The bags involved hold a handful of occurrences: a file with five artist tags is unusual and one with fifty does not exist. The saving a short-circuit could offer is a few comparisons per file, against which the price is a result that cannot be reproduced.

`AND` and `OR` keep their short-circuit, and are relied on for the guard idiom. The difference is not that one kind of short-circuiting is safe and the other is not, but that the operands of `AND` and `OR` are evaluated in an order the person writing the predicate chose and can see, whereas the occurrences inside a bag are in no order at all.

Q: **Why must the second argument of `FALLBACK()` be a literal?**
A: Because a literal default cannot be absent and cannot be unusable, and that is what makes the function total: whatever `FALLBACK()` is handed, its result is a usable value of the right type. A guard with no failure mode of its own is worth a good deal, and it is the whole reason the function is silent -- there is no question of whether the default was evaluated, or of what happens when the default is itself the thing that is broken.

Admitting an arbitrary expression would take that away and would reopen a question that has already been answered by removing something. `FALLBACK(vorbis::artist, id3v2::artist)` is what everybody would immediately write, and that is `COALESCE()`, which was dropped before first publication. The reason it was dropped is precisely the one that applies here: a construct selecting among several candidates has to say whether the candidates it did not use were evaluated, because that decides whether an unusable occurrence in an unused candidate warns, and no answer to that is both useful and consistent with the short-circuiting that `AND` and `OR` are relied on for. Letting the default be an expression would smuggle the same question back in through a function that exists to be simple.

The cost is real and worth naming. Cross-format preference is expressible only for the five identifiers the global namespace covers; for anything else -- an album artist, a composer, a disc number -- there is no way to say "prefer the APE item, else the Vorbis field". The global namespace is the answer for the common cases and the honest position is that the uncommon ones are not served. Relaxing the restriction later would break nothing that is valid today, which is the direction worth keeping open.

Q: **Why must the endpoints of a range be literals?**
A: Mostly so that `min > max` can be an error. A range whose endpoints are the wrong way round is a mistake rather than a query, it is worth catching, and catching it before any file is opened requires both endpoints to be known when the predicate is read. With arbitrary expressions the check would have to be dropped, losing a genuine diagnostic, or moved into evaluation, which would add a third per-file condition to a list this documentation has worked to keep at two -- a value that is absent, and an occurrence that cannot be interpreted.

Two further questions would arrive with it, neither hard but both unnecessary. An endpoint that resolved to several occurrences would need the range itself to carry a quantifier, which is a new mechanism for a construct that is otherwise two literals and a pair of dots. An endpoint that resolved to nothing would need a rule about whether the range is then absent or the operator simply false.

Unlike the restriction on `FALLBACK()`, this one costs almost nothing. A range between two values read from the same file is a query nobody has wanted, where cross-format preference is wanted constantly. That asymmetry is why the two restrictions read alike in the specification and are worth separating here.

Q: **Why is the pattern of `=~` part of the operator rather than an operand?**
A: Because nothing but a literal was ever worth allowing there, and once that is so, an operand is the wrong shape for it.

A pattern read from tag data could only be checked file by file, and making room for that cost more than the check itself: an invalid pattern became a third way for an occurrence to be unusable, the pattern operand became a warning source that was neither an identifier nor a conversion, and the evaluator would have had to build matchers per file, with the engine that is the more expensive one to build. Nothing worth keeping was found on the other side. The one plausible use, `title =~ artist`, is a substring test for which a regular expression is the wrong tool: an artist called "Therapy?" or "R.E.M." is a pattern that means something other than the name, and "Sunn O)))" is not a valid pattern at all. A literal, by contrast, is checked when the predicate is read, so a malformed pattern, or one using a construct the engine does not support, is an error reported before any file is opened.

A literal operand would still have been an operand, with everything an operand can carry. A quantifier on a pattern would have been valid and meant nothing, `LITERALLY` could have been written on either side of `=~` to the same effect, and every future way of writing a string expression -- a named constant, a concatenation -- would have reopened the question of what counts as a literal. As part of the operator, the way the range is part of `BETWEEN`, the pattern is a token the grammar names: `LITERALLY` has one place to go, the subject, and there is nothing to quantify.

Q: **Why must a pattern be written as a raw string?**
A: So that a backslash in a pattern has only one reader. In a quoted string every backslash meant for the pattern has to be doubled, so `"^\\d+ "` is how `r"^\d+ "` would be written, and some escapes are understood at both levels and quietly change hands between them: `"\x41"` gives the engine a literal `A`, while `r"\x41"` gives it the escape. A raw string hands the engine exactly what was written, and the question of which level an escape belongs to never arises.

It also lets the string grammar grow without patterns growing with it. `\b` is not a string escape, so a quoted `"\bfoo"` would be rejected, and that rejection would be all that caught somebody who meant a word boundary. Were quoted strings ever to adopt `\b` for backspace, as most languages have, the same text would become a valid pattern matching a backspace, with nothing to say so; interpolation would be worse still, braces being everyday regular expression syntax. A raw string has no escapes to add.

The price is one character per pattern, and a diagnostic for a quoted pattern can offer the raw one. Admitting quoted strings later would break nothing, should the string grammar ever settle in a way that makes it safe; the reverse would.

Q: **Why is the regex operator spelled `=~`, when `~=` would sit beside `==`, `!=`, `<=` and `>=`?**
A: Because `=~` is the spelling people already know, and `~=` is known mostly as something else.

`=~` has meant "matches this regular expression" since Perl, and Ruby, Bash, Elixir, Groovy, Neo4j's Cypher, Prometheus and MPD's filter syntax all spell it the same way, so anybody who has used a regex operator before is likely to type it unprompted. `~=` has no such history. Where it is known at all, in Lua, MATLAB and Smalltalk, it means "not equal", which is about as far from a match as an operator can get, and a reader from one of those languages would take `artist ~= r"metallica"` to mean roughly the opposite of what it does.

The family resemblance `~=` would have bought is thin. `<` and `>` already stand outside the family, as do `BETWEEN` and `IS`, and a pattern that is part of the operator rather than an operand makes this one a closer relative of `BETWEEN` than of `==` anyway. Neither borrowed spelling is lost on the reader who types it: `~=` is answered with both `=~` and `!=`, since either may have been meant, and `!~`, which most languages with `=~` pair with it, is answered with `NOT`.

Q: **Why does the language reserve words that name nothing it defines?**
A: So that a predicate written in a plausible but mistaken expectation can be told what to write instead. `NULL` is the clearest example: Goro has no null value, but `year == NULL` is what somebody coming from SQL will write to find the files with no year. Were `NULL` an ordinary name, the best the diagnostic could say is that no identifier of that name exists, which is true and no help; recognised as a reserved word, it can point at `year IS ABSENT`. The same reasoning applies to any word a reader is likely to reach for in the wrong place, and the cost is small: a reserved word cannot be used as a bare identifier in the global namespace, and qualifying it, as in `::null`, still reaches one if one is ever defined.

Q: **Why are names in open namespaces not checked against each tag format's own naming rules?**
A: Because it is a lot of work for very little. Each format restricts its field names in its own way -- Id3v2 frame identifiers are four letters or digits, Vorbis field names are a range of ASCII, APE keys have a length limit and a few reserved values -- and checking a name against those rules means the identifier documentation carrying all of them, and keeping them right. What it buys is handholding, and only some of it: even after all that trouble, the mainstream case, a plain misspelling such as `vorbis::artistt`, is a perfectly valid Vorbis field name and would still not be caught.

Q: **Why is a name an identifier cannot spell written as a quoted string, rather than with a syntax of its own?**
A: Because it was the option with the least hassle attached, and nothing forced a more elaborate one. A dedicated delimiter would have meant choosing characters, and the obvious candidates are the ones a future addition would want: braces are what a set literal would use, and square brackets are what indexing would use. Reusing the string syntax spends no characters at all, and it inherits escaping rather than requiring an escape mechanism to be invented alongside it.

It is worth noting why this was cheap, because it was not luck. The restrictions Goro places on itself are what made it possible: identifiers are resolved statically, a quoted part may only follow `::`, and the first part of an identifier is never quoted. Those three together mean a string at the start of an expression is unambiguously a value and a string after `::` is unambiguously a name, so no lookahead and no new token are needed.

A function taking the namespace and name as arguments was the alternative, and it generalizes better to names made of several parts, such as addressing one `TXXX` frame by its description. It was not chosen because that case does not exist yet. Further escape hatches can be opened whenever something concrete needs them, and designing one now for a requirement nobody has stated would mean the common case paying for the rare one indefinitely.

Q: **Why is a pathspec that cannot be resolved an error, when a glob matching nothing is not?**
A: A pathspec is written by hand, and a mistyped one is far more likely than a deliberate reference to something absent; finding out at the start costs nothing, while finding out halfway through a run over a large collection costs the run. A pattern matching nothing is an ordinary result rather than a mistake. Both follow the line drawn everywhere else: what can be known before the run starts is an error, and what can only be discovered during it is a warning.

Q: **Why are there two categories of warning?**
A: Because they tell a caller materially different things. Unusable data means the run answered every question it was asked and disregarded some data while doing so; a file that could not be read means it did not answer one of them, so its output is incomplete. They also differ in how welcome they are. Data warnings are the normal state of a large collection and somebody may reasonably decide to live with them, while an unreadable file is the condition Goro exists to find. Keeping them apart is what lets the noisy one be silenced without burying the quiet one, and lets a script branch on each.

Q: **Why does a run that emitted warnings still return an exit code of zero by default?**
A: Because for the collections Goro is built for, warning is the normal case rather than the exceptional one. The whole unusable-occurrence design exists on the premise that a library of a hundred thousand files contains malformed tags, so a run across one will frequently have something to report while producing entirely correct output. A shell treats every non-zero code as a failure, so returning non-zero whenever there was a remark to make would break every pipeline Goro was put into, near-permanently, for a condition that is expected. The convention is not unheard of -- Borg reports warnings as exit code 1 -- but its own issue tracker carries reports from users who could not tell whether a successful-looking run had worked, which is the failure mode in question.

The Pit of Success argument does cut the other way, since the person who most needs the signal is the one who never thought to ask for it. The costs are asymmetric, though: a strict default silently breaks working pipelines again and again, whereas a lenient default costs somebody who wanted strictness a single line of documentation. And warnings go to standard error either way, so nothing is hidden from a person watching the run; only the exit code stays quiet.

Q: **Why does suppressing a warning remove it from the exit code too, and why is there no record that anything was suppressed?**
A: Because the option means the condition is not a problem, and the alternative reading -- report it more quietly -- wants the opposite implementation. A run cannot both disregard a condition and report it. A `--no-warn=data` run that still returned `10` would be telling the caller about exactly the thing they asked not to be told about, and a "500 warnings suppressed" line at the end would be the same mistake moved to another channel. So a suppressed warning is not produced at all, and nothing anywhere lets a caller distinguish a condition that was suppressed from one that never occurred.

The gain is that the codes describing the query's outcome become reachable. Warning is the normal case on the collections Goro is built for, which is the premise the whole design rests on, and it has an awkward consequence for the exit code: since something wrong with the data read outranks what the query found, a run over a large library almost always returns a code from the `1`x group, and the `2`x codes are in practice unobservable. Suppressing a category that has been accepted is what makes them visible again, and it does so without the exit code needing a mechanism of its own.

A selector on the strict option was the alternative -- something like `--strict-exit-code=empty`, or a bitmask of conditions. It was rejected because `--no-warn` is justified without reference to exit codes at all: a library with five hundred imperfect tags emits five hundred stderr lines on every run, forever, for a condition its owner has decided to live with, and what that teaches people is to redirect standard error to nowhere, which then also discards the warnings about files that cannot be read. Fixing the noise is worth doing on its own, and once it is done the exit code problem dissolves by composition. A selector would have solved only the smaller half and left the noise in place.

What remains unreachable is the conjunction: no single exit code says "warned and also matched nothing". That is accepted rather than worked around. An exit code reports the most serious thing that happened, `grep` and `diff` set the precedent, and a caller who needs two facts can read one of them from the output, which for `goro list` is as cheap as testing whether anything was printed.

Q: **Why is "nothing matched" worth an exit code when warnings are not?**
A: Because it is unambiguous and it never fires spuriously. An empty result is a fact about the query rather than about the state of the collection, it is exactly the distinction that `grep` and `diff` spend an exit code on, and a script branching on it is doing something sensible rather than working around a quirk. Warnings, by contrast, say that some file somewhere holds data that could not be interpreted, which on a large collection is almost always true and therefore almost never actionable as a yes-or-no signal.
