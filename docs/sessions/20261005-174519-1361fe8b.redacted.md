## Claude

You've spotted a flaw in how I described B. Without recovery, semantic errors aren't reported after a syntax error at all.

**Under B, a run reports one of two things, never both:**
- If the predicate doesn't parse, there is no syntax tree, so the binder never runs. The run reports that one syntax error and stops.
- If it parses, the binder reports every independent semantic error it finds. For example, two misspelled identifiers and a `!=` with no quantifier come out as three errors in one run.

So a predicate with a syntax error and a misspelled identifier takes two runs to fix. Each run costs milliseconds and processes nothing, so that loop is cheap.

**Full parser recovery (C) is overkill here, for three reasons:**
- **It mostly pays off in editors.** Roslyn and TypeScript recover because they need a tree for every keystroke of a half-typed file. Goro has no editor, and its input is a single line.
- **An expression language has weak points to resume from.** There are no statement terminators, so the parser can only pick up again at `)`, `AND`, `OR` or the end of the text. The heuristics guess what the broken part meant, and wrong guesses produce confusing follow-on errors. That works against the goal that diagnostics be first-class.
- **The cost spreads.** Error nodes can appear anywhere in the tree, the binder has to cope with missing children, and the recovery heuristics need tests of their own. All of that buys reporting of several unrelated syntax errors in one line, which is rare in hand-written predicates.

**A middle option, B′, gets most of the benefit for almost nothing.** The parser already accepts a wider grammar in a few places so that it can produce good diagnostics:
- borrowed operators: `=`, `<>`, `&&`, `!`, `!~`, `~=`
- a quoted or modified pattern after `=~`
- a chained comparison
- `NULL`

In each of those cases the parser knows the shape of what was written; only the spelling or placement is wrong. It can record the error, build the node and carry on, without guessing and without needing a point to resume from. Unexpected tokens elsewhere still stop the parse.

Take `artist = "metallica" && year = 2000`:
- **B** reports the first `=` and stops.
- **B′** reports all three borrowed spellings, plus any semantic errors, in one run.

These are also the mistakes people make several times in one predicate, because they come from the habits of another language.

**The one subtlety in B′:** where the intent can't be known, the node must not pretend. `~=` could mean `=~` or `!=`, so it becomes an error node carrying the error type. The binder's suppression of follow-on errors then keeps it quiet. That suppression is already part of B, so B′ adds nothing to the binder. Its cost is limited to the parser and the syntax tree: the tree has to carry the recorded errors, and a few node kinds need an "error" flavour. That's why I need this settled before writing the shared types.

**My recommendation is B′.** It's the same design as B, with recovery limited to the cases where the parser already knows exactly what went wrong. Do you want B′ or plain B?

  ## Parser (Parser.cs)
  - **Structure:** recursive descent over the token array with one current token: `Or → And → Not → Comparison → Operand (modifier "(" operand ")" | Primary) → Primary`. Spans run from the first token to the last; NOT's span runs from the keyword to its operand.
  - **Stopping at the first error:** a private exception carries the Diagnostic up to `Parse`, which turns it into a failed StageResult. It is never seen outside the parser and keeps the descent free of error plumbing.
  - **Primary:**
    - The tokens it accepts are a literal (String, Number, ByteCount, Duration, TRUE, FALSE), NULL (which becomes NullSyntax), `(` expression `)`, `::` (a rooted identifier) and a Name.
    - A Name is an identifier, or a function call if `(` follows.
    - Once a name is qualified or rooted, a following `(` is `qualified-function-call`. Where the last part is bare, the error offers `name(...)` without the qualifier.
    - After `::`, a part may be a Name, any keyword (using its source text) or a string; a string part is IsQuoted with its decoded text.
    - `::"x"` is `quoted-first-part`, since the grammar's first part is `name`.
  - **Reserved words at primary position:**
    - A keyword followed by `::` (`and::x`, `true::x`) is `reserved-word-in-identifier` and offers `::and::x`.
    - Any other keyword (or ALL, ANY or LITERALLY without `(`) is `reserved-word` and offers `::and`. The message for a modifier mentions `ALL(...)`.
  - **Comparison tail, read at most once:**
    - **`==` etc.:** read an operand.
    - **BETWEEN:** literal `..` literal.
      - A `(` there is `range-endpoint-not-literal`. If it is `(literal)`, the error offers the literal without the parentheses, which covers `x BETWEEN (1)..2`.
      - An identifier or NULL is the same code with no suggestion.
    - **`=~`:** read an operand, then classify it after looking through parentheses and modifiers:
      - **`modified-pattern`:** offers `LITERALLY(subject) =~ r"..."` when every modifier is LITERALLY. A quoted inner string is turned into the raw form, and the subject is not wrapped again if it already has LITERALLY.
      - **`parenthesized-pattern`:** offers the bare raw string.
      - **`quoted-pattern`:** offers `r"..."` built from the decoded value, with quotes doubled.
      - **`pattern-not-raw-string`:** covers `title =~ artist` and number literals.
    - **IS:** USABLE, UNUSABLE or ABSENT. Two extras with suggestions: `IS NOT x` is `is-not` and offers `NOT (subject IS x)`; `IS NULL` is `is-null` and offers `ABSENT`.
    - **`~=` and `!~`:** handled in the tail, with the operand read so that a suggestion can be built from it. Both use the code `borrowed-operator`.
      - `~=` offers `!=` (replacing the token) and, when the operand is a bare string literal, `=~` with the raw form.
      - `!~` offers `NOT subject =~ r"..."` when the operand is a bare string literal.

  The binder makes one recursive pass over the syntax tree, bottom-up, in text order. Each node binds to an internal record:

## Claude

No real pitfalls today. There is one wording trap for the future, and one small effect worth keeping in mind.

**Why it's safe now.** In C++, `::std::vector` differs from `std::vector` only because lookup is relative: an unqualified name is searched for in enclosing scopes first, so something nearer can shadow the top-level one. Goro has no scopes. Every name is already absolute and resolves the same way wherever it appears in a predicate, so the leading `::` has nothing to choose between.

**The non-semantic effect.** A leading `::` still changes what parses, though not what is named. It is the one way a reserved word can be the first part of an identifier (`::and::x`), and the place a quoted first part is now allowed (`::"file"::size`). Either way the name means what it would mean without the `::`, so this is syntax only.

**The trap: saying "redundant".** Goro may one day give unqualified names a relative meaning, for example named values defined in a predicate, or a scoped block where `artist` means `id3v2::artist`. Then the C++ distinction comes back: a rooted name must stay fixed while an unrooted one may change. If the spec now says the leading `::` is redundant, that feature would have to retract it. If the spec says it starts the name at the global namespace, the feature only adds a meaning for unrooted names, and nothing written today changes. So I'd specify it as an absolute path, not as "redundant". A sentence under "Identifiers and namespaces" in `predicates.md`, after the paragraph on the global namespace:

> A leading `::` starts a name at the global namespace, where every namespace sits, so `::id3v2::TIT2` and `id3v2::TIT2` are the same identifier.

**Two things the implementation must get right,** both already planned:
- **One warning source.** `::file::size` and `file::size` must count as one source. The binder interns identifiers by `IdentifierName` equality, which treats the leading `::` as global, so the two are one source.
- **Quoting the user's spelling.** Warnings and suggestions quote the identifier as you wrote it, with or without the `::`, because they're built from spans of your text.
