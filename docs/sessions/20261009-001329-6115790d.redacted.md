## Can we map an MP3 exactly and list all its tags?

Mostly yes, and the gaps are small. Most of a byte-exact map already comes out of the reader:

- **Top-level regions:** every tag's exact extent: each Id3v2 tag (with its footer), APE (with header and footer), Id3v1 and Lyrics3v2. That includes tags that aren't the source, such as the second and third Id3v2 tags.
- **The audio's edges:** the first frame (`C`), the summary frame and what it records, the start of the audio (`D`), its end (`E`, from the hash walk), and where the trailing tags start (`F`).
- **Gaps:** junk before the audio, and junk after a trusted header, each with its region.
- **Every field:** its key, its kind, where its content is stored in the file, and its storage transformations. Its text, description and content can all be read.
- **Damage:** typed conditions, most with offsets: where a structure broke, which tag is unusable and why, and which quirks were applied.

So listing every Id3v2 frame and its values, in every tag the file holds, is already possible from the reader's output.

**What a byte-exact map still lacks:**

1. **Regions inside tags that are skipped, not recorded:** the Id3v2 header, the extended header, each frame's header, and the padding. Most can be derived, since a frame header sits just before its content, but nothing records the padding's start or the extended header.
2. **Frames in a v2.3 tag unsynchronised as a whole have no file offsets.** Their content lives in the undone copy in memory. Mapping it back would mean tracking where the inserted bytes were removed.
3. **The identifier as written on disk is lost.** Fields carry the name Goro reads them under, so `TT2` becomes `TIT2` and `TYER` becomes `TDRC`. A faithful dump wants both names. A stepped-over illegal frame survives only as a quirk with its offset, without its size.
4. **The audio's interior isn't enumerated.** The hash walk passes every frame header and knows where it stepped over damage, but records only `E`. Mapping individual frames, or the damaged stretches between them, means keeping what the walk sees, and reading the whole file.
5. **Opaque contents:** a tag whose size can't be trusted is known only by its header, and Lyrics3v2's fields and binary frames such as `APIC` aren't parsed internally.

Points 1 to 4 are small changes to types we already have: a few more regions and fields on the index, plus an option for the walk to record what it sees. They're also exactly what `goro audit` will need, so the audit line is the natural home for them. Point 5 is new parsing, worth it only if someone asks.

If useful, I can produce such a map now for one corpus file, for example `all-tags.mp3` or `dmg-id3v24-frame-overrun.mp3`, as a page with a diagram, from what the reader already gives. It would show where the gaps above fall.

At the level of "which region is this byte in", the reader covers almost everything. Three things are left, and only one of them is a real blind spot.

1. **Tags anywhere but the edges go unrecognised.** This is the real one. The analysis looks for tags from the start inwards and from the end inwards, and never in the middle. So:
   - **Two files joined:** the second file's Id3v2 tag sits in the middle. The walk steps over it as damage, so the map would show it as part of the audio, and the hash would include it.
   - **A trailing tag with nothing at its end to find it by:** a v2.3 tag appended after the audio (v2.3 has no footer), or an APE tag with only a header. These would show as junk after the audio rather than as a tag.

   The fix is cheap. When the walk has to step over bytes, it can check whether they start with `ID3`, `APETAGEX` or `TAG` and record a "tag in an unexpected place" condition. That's exactly a `goro audit` finding, and fits the note you asked for on walks.

2. **A tag whose size can't be trusted has no known end.** It's a size past the end of the file, one that isn't syncsafe, or a v2.5 header. The bytes from its header to the first audio frame are "this tag, or junk after it", and nothing in the file can tell which. That's inherent, and the honest map draws it as one region labelled that way.

3. **Where the audio ends costs a full read.** The analysis alone knows `E` only when a summary header is trusted up to its frame end. Otherwise it takes the hash walk, which reads the whole file. That's a matter of cost, and a diagnostic can afford it.

**On listing the tags and their values:** every Id3v2 tag found is fully listed, whether or not it's the source, with each frame's values, description and content. There are two small exceptions:
- **A stepped-over frame with an illegal identifier** is recorded only as a quirk at an offset, not as a frame with a size and content. Its bytes are inside the tag's region, so the map is fine; only the listing misses it.
- **Frames show the name Goro reads them under**, not the one on disk: `TT2` appears as `TIT2`, `TYER` as `TDRC`. Keeping the identifier as written is one more field on the frame record.

What lies beyond a broken structure, and anything in a tag that can't be read at all, can't be listed by any reader; the map shows those regions as damaged.

So the coarse map plus a full listing needs two small additions:
- spotting tags where the walk resynchronises;
- keeping the on-disk identifier, and listing stepped-over frames as frames.

Everything else is already in `FileLayout` and the range walk.
