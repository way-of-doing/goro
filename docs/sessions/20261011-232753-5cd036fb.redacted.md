If all audio data in flac is checksummed, what advantage can Goro offer here?

## Claude

Inside a single FLAC file, its own checksums catch corruption better than Goro's hash can, because they need no history. What Goro's hash adds is a reference kept outside the file. And Goro shouldn't treat the checksums as competition; it should use them.

**What FLAC's checksums can and can't tell you.** Each frame header has a CRC-8 and each frame a CRC-16. STREAMINFO holds an MD5 of the decoded audio. Together they tell you whether a file is consistent with itself. They can't tell you whether it's the same file it was last year:

- **A valid change passes every check.** A tool that rewrites or replaces the audio writes fresh, correct checksums. So does a re-encode, and a remastered copy dropped in over the old one. Only a hash stored somewhere else notices.
- **Cutting at a frame boundary passes every frame CRC.** Only the MD5 or the total sample count catches it.
- **The MD5 is often missing.** An encoder writing to a pipe leaves it zero; the corpus seed `flac-piped.flac` is one such file. Then only the per-frame CRCs remain.
- **Nothing protects STREAMINFO itself.** If its MD5 or total rots, the check fails with nothing to show which side is damaged.
- **Checking the MD5 needs a full decoder,** which Goro deliberately doesn't have.

**What Goro's hash adds:**

1. **A reference outside the file.** It notices any change to the encoded stream since the hash was recorded, whether the change is consistent or not. It also lets you compare a primary copy with a backup without decoding either.
2. **One mechanism for the whole collection.** MP3 has almost nothing comparable: the MPEG frame CRC is optional, rarely written, and covers only the header and side information. The LAME CRC covers only the Info frame. Ogg's page CRCs get recomputed by every tagger. A collection-wide check can't rest on FLAC's checksums alone.

The caveat is that FLAC's MD5, when present, is a better identity for "same recording" than Goro's hash. It survives a re-encode at another compression level, and Goro's hash deliberately doesn't.

**What this suggests for the line.** The hash walk already reads every byte of every frame and finds each frame's boundaries, so checking each frame's CRC-16 along the way costs almost nothing. That gives Goro something no stored hash can: evidence of rot the first time it sees a file, with no baseline. A frame failing its CRC-16 would become a finding:
- for `goro audit`, and possibly
- for `goro hash` as something like `incomplete`.

Checking the MD5 would stay out of scope unless Goro ever takes on a decoder; `flac -t` already does it.

That would be a fifth group of questions for the brief: whether FLAC's frame checksums are verified, and how a failure is reported. I haven't changed the brief or the doc for this. Shall I add it?

## 3. A wrong recorded length

This is about metadata blocks. Audio frames record no length at all, which is question 4's problem.

**Every block's end has two candidates:**
- **The recorded end:** where the length in the block's header puts it.
- **The contents' end:** where the block's own data says it ends. Only some block types can say this:
  - STREAMINFO is always 34 bytes.
  - A VORBIS_COMMENT gives a vendor length, a count, and a length for each comment.
  - A PICTURE gives a length for its media type, its description and its data.
  - PADDING, APPLICATION and SEEKTABLE carry nothing that says where they end.

**Choosing between them:** the right end is the one from which the rest of the chain checks out. Every later block must be well formed, and the last one must end exactly where an audio frame header starts, with a passing CRC-8 and number 0. That is very unlikely to pass by chance. In all seven files (corpus and real-world) where the two candidates differ, exactly one passes:

| File                                | Block          | Recorded end      | Contents' end     | Right one
|-------------------------------------|----------------|-------------------|-------------------|-----------
| `dmg-block-length-overrun.flac`     | VORBIS_COMMENT | 431, nothing valid | 231, chain checks out | contents
| `rw-comment-block-too-short.flac`   | VORBIS_COMMENT | 94, nothing valid | 193, first frame  | contents
| mutagen `52-too-short-block-size`   | VORBIS_COMMENT | 94, nothing valid | 221, first frame  | contents
| mutagen `106-short-picture-block-size` | PICTURE     | 90, nothing valid | 222, chain checks out | contents

## 5. Playing time, with context

**What we want.** `file::duration` is the length of the stream's timeline. Damage in the middle of the stream doesn't shorten it; truncation does.

**What a FLAC file tells us.** It states the length twice:
- **STREAMINFO** declares the total samples. That can be 0 ("unknown") or simply wrong.
- **Every frame header** carries its frame number and block size, so the last frame's header says exactly where the stream ends. In the corpus audio, the last frame is frame 35, with a final block of 2,170 samples after 35 blocks of 4,096: 35 × 4,096 + 2,170 = 145,530 samples, 3.300 s.

The analysis reads only the file's edges, so it finds the last frames by searching back from the end of the audio.

**The problem.** When the last frame found and STREAMINFO agree, that's the answer. When the frames end early, there are two possibilities that need different answers:
- **Truncation:** the file was cut, those samples are gone, and the timeline is shorter.
- **Damage at the very end:** the last frames are present but unreadable, so the search stops at an earlier frame. The timeline is still STREAMINFO's.

The survey's prototype tells them apart by size. If the bytes after the last intact frame could hold the missing samples, it calls the tail damaged; otherwise truncated. That threshold was tuned on two fixtures, and bytes per sample swing widely with the music: silence compresses to a few bytes a frame, noise to kilobytes.

**What the file's structure says instead.** Two signals settle most cases without measuring anything:
- **A frame cut off by the end of the file proves truncation.** Its header is intact, but its body, parsed as decided in 4, runs past the end. In `truncated.flac`, frame 19's header is intact and the file ends partway through its body, so the answer is the end of frame 18: 1.765 s.
- **A short final block proves the stream ended naturally.** In a stream of fixed block size, only the last block may be smaller than the rest (RFC 9639 §8.2). `streaminfo-total-doubled.flac` ends cleanly with its 2,170-sample block, so 3.300 s is right whatever STREAMINFO claims, and the same goes for a total of 0.

**What's left.** Bytes with no valid frame header after the last intact frame. In `last-frame-damaged.flac`, frame 34 ends and then 642 bytes run to the end of the audio. Two readings fit:
- a last frame whose header was damaged, so the timeline is still 3.300 s;
- junk appended to a file that had been cut exactly at a frame boundary, so the timeline is shorter (ffmpeg decodes 3.251 s).

Nothing in those bytes tells the two apart. The choice for that case:

1. **Keep the size rule just for it.** `last-frame-damaged.flac` gets 3.300 s.
2. **Make `file::duration` unusable and count the file as `incomplete`,** as for an MP3 whose summary header fails its checks. Goro then never guesses a playing time. It needs damage exactly at the end of the file, so it should be rare.

I'd go with 2: it is the rule MP3 already follows, and every other fixture gets a definite answer from the structure alone.

**Also still open:** whether a search is worth building for a block that doesn't say where it ends (PADDING, APPLICATION, SEEKTABLE). No file in the corpus or the real-world data needs it.
