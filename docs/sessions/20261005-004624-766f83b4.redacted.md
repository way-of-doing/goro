**The dependency check**
I couldn't find any audio encoders or sample files on this machine, so I wrote a throwaway probe that builds small FLAC, Ogg Vorbis and Ogg Opus files by hand, the same way `SyntheticMp3Builder` does for MP3.

- **Reading works for all four extensions.** TagLibSharp 2.3.0 picks the reader from the extension. For `.ogg` and `.opus` it then works out Vorbis or Opus from the file itself, so Opus in `.ogg` and Vorbis in `.opus` both read correctly. "Treat each file by its extension" needs no format sniffing of our own.
- **Hashing only works for MP3.** `TagLibAudioHasher` hashes the byte range TagLib reports as free of tags. I edited the tags and hashed again:
  - **MP3:** the hash stayed the same.
  - **FLAC:** the range starts at byte 0, so the tag blocks (comments, pictures) are hashed. Every tag edit changes the hash.
  - **Ogg (Vorbis and Opus):** the hash holds while the tag still fits in the space it already has. Once it doesn't, for example when cover art is added, TagLib renumbers every page after it, and those numbers are inside the hashed range. The hash changes.

  Both failures break the vision's promise that the hash changes if and only if the audio does. Widening discovery as the brief asks would make `goro hash` print wrong hashes for FLAC and Ogg.

**Decisions needed**
1. **Hashing FLAC and Ogg.** I recommend a separate line for per-format hashing, with this one waiting on it. Hashing FLAC correctly is small: skip past the tag blocks. Ogg means hashing the audio packets and leaving out the page headers. The harder part is deciding exactly what the hash covers, because some Opus header fields affect the decoded audio and so arguably belong in it. That needs its own spec. Doing it inside this line would turn a small line into a large one.
2. **A file named directly whose extension isn't one of the four,** e.g. `goro hash cover.jpg`. The brief only covers globs. Today the code skips it silently. I recommend keeping that and applying one rule to every kind of pathspec. Shell-expanded `goro hash *` is the deciding case: there, every file arrives as a direct name, so an error or warning per `cover.jpg` would be noise.
3. **Globs search subfolders in the code but not in the docs.** In the code, `*.mp3` matches at any depth, and a test pins that. `pathspecs.md` and the FAQ say a glob matches within one directory and that any directory it matches is walked.
