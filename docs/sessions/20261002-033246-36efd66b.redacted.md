## A. Two truth values make every failure `false`, and `NOT` flips it

**A1. The rationale's main promise doesn't survive `NOT`.** `rationale.md:39` says an unusable value was chosen because it "will almost certainly result in the evaluation of a predicate to false: this avoids processing files where something unexpected happened." But `NOT (x == 5)` with junk in `x` is true, so the file is selected *because* its data was junk. That only holds for predicates with no `NOT`.

**A2. The spec treats two different problems as one.** Lines 238, 275 and 338 call the `<`/`NOT >=` gap "the same underlying phenomenon" as `!=` vs `NOT ==` on multivalues. They are different:
- `!=` vs `NOT ==` on a multivalue where every occurrence is usable comes from how "some" and "all" interact. It would exist under any logic.
- `<` vs `NOT >=` on absent or unusable data comes from collapsing failure into `false`. It is a design choice and can be changed.

Merging them hides the fact that one of them is fixable.

**A3. Each kind of per-file failure behaves differently under `NOT`:**

| Per-file condition | `x == v` | `NOT (x == v)` | Warns |
|---|---|---|---|
| absent | false | **true** (listed) | no |
| unusable occurrence | false | **true** (listed) | yes |
| invalid regex from tag data | false | **true** (listed) | yes, but category and dedup undefined |
| tags or file unreadable | evaluation abandoned | **not listed** | yes (`file`) |

The invalid-regex row sits outside the value model:
- No source is defined for it, so dedup is undefined.
- `warnings.md` doesn't say which category it falls in.
- A predicate can't guard against it.

The unreadable row has its own problem: `artist == "x" OR file::size > 1mb` can't be satisfied by its second half, because the evaluation is abandoned.

**A4. Booleans are the one type with no dynamic state (line 90), and that exception causes all of this.** I suggest dropping the exception rather than adding a new concept:
- A comparison that consumes an unusable occurrence produces an *unusable boolean* (the warning is emitted at that point, as now).
- `NOT` passes it through, the way `NUMBER()` does.
- `AND`/`OR` follow standard three-valued logic: `false AND u = false`, `true OR u = true`, otherwise `u`.
- Quantifiers behave the same way: "any" over {true, u} is true; "any" over {false, u} is u.
- Only a definite `true` selects a file.
- Absence stays `false`. That is principled: `false` means "evaluated, no match", while unusable means "could not be evaluated".

What this gets:
- The A1 promise becomes true.
- An invalid tag pattern is just an unusable occurrence of the pattern operand, so it gets sources, dedup and a category for free.
- Unreadable tags could become unusable occurrences instead of abandoning the whole evaluation.
- The guard idiom keeps working unchanged.

It also prepares for the future. The first boolean taken from tag data (the `TCMP` compilation flag, podcast flags) will need absent and unusable states anyway, and the logical operators will then need exactly these rules.

A side observation: the `IS` guards never change the result of a predicate without `NOT`, except that `ALL` also drops mixed files. Outside `NOT` they only manage warnings. With A4 that becomes their whole job, which is a cleaner story.

## B. Normalization is defined by mechanism, not intent

All of these were checked against the .NET runtime.

**B1. The spec contradicts itself.** Line 178 says "all combining marks are discarded" and then "precisely the combining marks that decomposition exposes." After NFD you can't tell which marks were exposed by decomposition and which were already there. The Unicode categories (Mn? Mc? Me?) aren't stated either.

**B2. Korean regex matching never works.** NFD splits Hangul syllables into jamo, which are letters, not marks, so they aren't stripped. The subject `한국` becomes `1112 1161 11AB…`, while the pattern stays as precomposed `D55C AD6D`. `title ~= "한국"` returns **False**. Equality comparisons still work, because both sides get decomposed. The fix is to recompose to NFC after stripping marks.

**B3. Other scripts get false matches.** Some marks that NFD exposes or strips are not accents:
- Japanese: the voicing marks on kana are combining marks, so `Norm("ガンダム") == Norm("カンタム")` is **True**. A pattern containing `ガ` can never match.
- Hindi: `कुमार` becomes `कमर`.
- Thai: vowel and tone marks have the same problem.

For a music library, J-pop, K-pop and Bollywood are ordinary content. The deferred item at `deferred.md:50` already accepts that an explicit fold table is needed for ø and ß. The same table approach fixes both directions: fold a defined set of Latin, Greek and Cyrillic accents instead of every mark.

**B4. `LITERALLY` loses canonical equivalence.** An NFC `Motörhead` and an NFD `Motörhead` compare **unequal** under ordinal comparison. Tags written on macOS or by some taggers are NFD. NFC normalization loses nothing and should apply even in literal mode, to both `==` and the regex subject.

**B5. The two kinds of case-insensitivity are both unspecified.** `==` uses `ToLowerInvariant`, which is simple per-character lowercasing, not case folding: final `ς` ≠ `σ`, so `ΟΔΥΣΣΕΥΣ` ≠ `Οδυσσευς`. `~=` uses the regex engine's own case-equivalence tables. Pick one definition and state it.

**B6. "Ordinal Unicode comparison" (line 182) is ambiguous.** Comparing UTF-16 code units and comparing code points give different orders for characters outside the Basic Multilingual Plane versus U+E000–FFFF. This affects `<` and `BETWEEN`.

**B7. Normalization can throw.** `"\uD800".Normalize()` throws `ArgumentException`. A lone surrogate can come from a `\u` escape in a literal, which could be rejected when the predicate is read. It can also come from broken UTF-16 Id3v2 frames, where nothing in the spec handles it. As written, such a file aborts the whole run, breaking the core guarantee. The spec needs to say what happens: either replace the bad code unit with U+FFFD, or make the occurrence unusable.

## C. "Knowable before the run, so it's an error" is applied only partly

- **C1. A namespace that doesn't exist isn't in the error list.** `vorbs::artist` isn't covered. Lines 390–397 only cover undefined identifiers in a *closed* namespace.
- **C2. Open namespaces still have fixed name rules.**
  - Id3v2 frame IDs are `[A-Z0-9]{4}` (plus the listed v2.2 leftovers).
  - Vorbis field names are ASCII 0x20–0x7D without `=`.
  - APE keys are ASCII, 2–255 characters.

  So `id3v2::artistt`, `id3v2::raw::foo` and `vorbis::"künstler"` can never match anything and could be read-time errors. That closes most of the "misspelled open identifier" hole (`deferred.md:53`) for the most common format. Likewise, `id3v2::TYER` is guaranteed absent by the unified v2.4 view. A "did you mean `TDRC`?" error is exactly the diagnostic quality `architecture.md` asks for, yet `identifiers.md:249` makes it silently absent.
- **C3. Converting a constant should be checked up front.** `NUMBER("abc") > 5` currently produces one warning per file in the run. Literal regex patterns are already validated when the predicate is read; constant conversions should get the same treatment.
- **C4. Literals that can't be represented aren't covered.** Only durations have a "too large is rejected" rule (line 146). A number literal with more than 28–29 significant digits is silently rounded: `1.0000000000000000000000000000001` becomes 1. That contradicts line 118, which says a literal "is the value it appears to be." `NUMBER()` on long text from a tag is also unspecified: does it round, become unusable, or overflow?
- **C5. The "modifier that can't affect anything is an error" rule is applied unevenly.** Line 394 states the rule, but it's enforced only for `LITERALLY`.
  - `ALL(x) IS ABSENT` ("no quantifier affects it", line 248) is unspecified.
  - `ALL(ANY(x))` is explicitly allowed even though the inner modifier does nothing (line 464).
  - `ALL("lit")` is unspecified.

  Pick one principle and apply it to all of these.

## D. Claims the spec makes about itself that don't hold

- **D1. The state tests can be derived from each other.** Line 260 and `testing.md:182,210` say they can't. Each identity below holds for every row of the table:
  - `ALL(x) IS USABLE` ≡ `NOT x IS ABSENT AND NOT x IS UNUSABLE`
  - `ALL(x) IS UNUSABLE` ≡ `NOT x IS ABSENT AND NOT x IS USABLE`
  - `x IS ABSENT` ≡ `NOT x IS USABLE AND NOT x IS UNUSABLE`

  The two existential tests generate all the others. Keeping all five as shorthand is fine, but the claim, and the test justification built on it, should go. Line 262 ("explicit and dual") also contradicts line 260 ("breaks the duality").
- **D2. The grammar comments are wrong (line 597).** `comparison_expr = operand [comparison_tail]` has an optional tail, so a bare operand, and therefore a modifier, can appear anywhere an expression can. Two consequences:
  - `COUNT(ALL(genre))` parses as a modifier, not as a call to a function named `ALL`.
  - `(ALL(genre)) == "x"` **does** parse.

  The deferred entry at `deferred.md:12` rests on that false premise. No grammar change is needed: static analysis just has to see through a parenthesized operand with no tail. This is the cheapest fix in this review.
- **D3. The cost advice at line 281 is wrong for `file::duration`.** It says `file::` identifiers need only file metadata. Duration needs the audio stream parsed, and for a VBR MP3 without a header, a scan of the file. "Put the cheap condition first" can be backwards here. Also unspecified: what `file::duration` resolves to when the audio can't be parsed.
- **D4. Durations "never carry a sub-second component" (line 140)**, but rule 4 (line 175) lets `1.5` stand for a duration, and `FALLBACK(file::duration, 1.5)` produces one. - **D5. Not every field name can be written.** `identifiers.md:19` says every field name the formats allow can be reached. In interpreted `vorbis`, `year` reads `DATE` and `track` reads `TRACKNUMBER`, and quoting doesn't help (`vorbis::"year"` is the same identifier). - **D6. The spec and the rationale disagree about the "safe" guard.** The spec calls `ALL(...) IS USABLE AND …` "the safe way" (line 266). `rationale.md:51` describes that same form as the one that fails silently.

## E. Unit types and conversions

- **E1. `STRING()` output isn't pinned down.** Literal syntax accepts both `.5` and `0.5`, and an optional `+`. Name the canonical form: presumably `0.5`, no `+`, and `-0` becomes `0`. People will write `STRING(x) == "0.5"`.
- **E2. The examples teach a pattern that breaks on real data.** Lines 266 and 372 apply `NUMBER()` to `id3v2::raw::TRCK` and `vorbis::raw::tracknumber`. That fails on `3/12`, the most common track format, and on any surrounding whitespace. Use `id3v2::track`, or make `NUMBER()` trim.
- **E3. Data can't be converted into the unit types.** There is no way to turn text into a bytecount or a duration, and there is no arithmetic. So "`TLEN` (milliseconds) disagrees with `file::duration`" can't be written, though it's a natural integrity check for a bit-rot tool.
- **E4. The internal representation of bytecount and duration is unspecified.** That leaves "cannot be represented" (line 146) undefined.

## F. Defaults that read differently from what they mean

- **F1. `!=` uses "some".** `genre != "metal"` reads as "some genre isn't metal", which almost nobody means. XPath 1.0's general comparisons have exactly these semantics, `$x != 'a'` is that language's best-known trap, and XPath 2.0 added `ne` to escape it. Options:
  - Keep it and document it (status quo).
  - Remove `!=`. `NOT x == v` and `ALL(x) …` cover what people mean, differing only on absence.
  - Require an explicit `ALL` or `ANY` on any operand of `!=` that could hold several values.

  I'd lean towards removing it.
- **F2. `FALLBACK` treats absent and unusable the same, and stays silent for both.** The rationale calls defaulting to a neutral value "the classic footgun" (`rationale.md:39`), yet `FALLBACK(year, 0) < 2000` silently treats every junk year as 0. Suggested change: fill only absence, and let unusable occurrences pass through and warn when used. "The result is never absent" still holds.
- **F3. Binary data is classed as unusable (`identifiers.md:39`).** The spec defines "unusable" as a defect, but cover art is legitimate data, and `ape::"Cover Art (Front)" IS UNUSABLE` reads like "is the cover art broken?". The has-cover-art question can already be asked with `NOT … IS ABSENT`. At minimum, stop defining "unusable" as "defect".
- **F4. String ranges cut off at the upper bound.** `artist BETWEEN "a".."b"` excludes "Beatles", because "beatles" sorts after "b". The example at line 334 invites exactly that reading.

## G. Syntax

- **G1. `~=` is spelled backwards from the familiar convention.** bash, Perl and Ruby use `=~` for regex match, and Lua and MATLAB use `~=` to mean *not equal*. Predicates are typed into a shell, so bash's spelling is the closest precedent. At minimum, recognize `=~`, `=`, `<>`, `&&`, `||` and `!` so they get targeted diagnostics.
- **G2. Keywords can start an identifier, and that creates a real ambiguity.** Line 663 allows `and::x`, and whitespace between tokens doesn't matter. So `NOT::x == 1` could mean `NOT (::x == 1)` or an identifier in a namespace called "not". Today only the absence of such a namespace settles it. Rule: a reserved word never starts an identifier.
- **G3. "Whitespace" isn't defined.** Is it ASCII only? Does a non-breaking space pasted from a web page count? Do newlines?
- **G4. `\u` escapes.** Characters outside the BMP need surrogate pairs. Consider a `\u{…}` form, and reject lone surrogates (see B7).
- **G5. Apostrophes clash with the shell quoting advice.** The recommended single-quote wrapping breaks on names like *Guns N' Roses*. `\x27` works but nobody will find it. Add a docs tip, and consider `--filter=@file` later.

## Claude

## Where collapsing failure to `false` causes trouble today

**`NOT` is the only operator through which collapsing changes which files are selected.** If a predicate contains no `NOT`, evaluating it with an "undetermined" value gives the same selection as collapsing that value to `false`.

The reason is that `AND`, `OR`, `ANY` and `ALL` never turn a `false` into a `true`. Treating "undetermined" as `false` therefore can't make a predicate without `NOT` come out true where a three-valued evaluation wouldn't, and the reverse holds too. A short induction over `AND`, `OR` and the quantifiers proves it. It can also become a property test: generate predicates without `NOT` and check that both semantics select the same files.

So the decision is really about one question: **what should `NOT` do with a comparison that couldn't be evaluated?** The other costs of today's design mostly come back to that:

1. **The rationale's promise is false.** "Bad data makes the predicate false" holds only without `NOT`. `NOT year >= 2000` and `NOT (artist ~= sometag)` select files *because* their data is broken.
2. **Rewriting a comparison changes its meaning.** Turning `NOT x < 5` into `x >= 5` changes the result on junk data. Nobody thinks of that as a rewrite, which is why it's dangerous.
3. **The information is lost too early.** By the time the command sees the result, "false" and "couldn't tell" are already the same value. So the command can't choose what to do with an undetermined file. This matters more later than now:
   - A future tag-writing command with `--filter='NOT …'` would write to the files whose data it couldn't read. That's the wrong direction for a destructive command.
   - A `hash --filter` (H5) has the opposite need: an undetermined file is exactly what you *don't* want to drop.

   With only two values, neither command can make its own choice.
4. **Each failure gets its own handling.** Invalid tag regexes and unreadable files each need separate wording. To be fair, the invalid regex could be made an unusable occurrence of the pattern under today's two values as well. Only point 3 strictly needs a third value.

Point 3 is the strongest argument for a change; point 1 is the most visible.

## If booleans become like other types

### Comparisons with an absent operand

I'd keep them a **definite `false`**, as rule 1 does now:

- **It's principled.** `false` means "evaluated, and no occurrence matched", which is the standard answer for "some occurrence matches" over nothing. "Undetermined" means "a defect prevented evaluation". The spec already treats absence as ordinary and unusable data as a defect, and this makes the logic follow that line.
- **`ALL` stays non-vacuous with no extra rule,** because absence is still intercepted before iteration.
- **It keeps the trouble out of absence.** SQL's three-valued logic is painful mainly because its "unknown" comes from *absence*, which is everywhere. Here the third value would come only from defects, which are rarer and always warned about.

The cost: the `NOT` asymmetry remains for absent data. `year < 2000` and `NOT year >= 2000` still differ for a file with no year. The warning box about this shrinks but doesn't disappear.

Making absence undetermined too (full SQL) would remove the box entirely. But then `NOT genre == "metal"` would drop untagged files, and anyone who means "everything not metal" would have to add `OR genre IS ABSENT`. I think that trade is worse.

### Where the warning is emitted

Keep the warning **exactly where it is now**. Note that no function currently warns. `NUMBER()` and `STRING()` pass an unusable value through silently, and `COUNT`, `FALLBACK` and `IS` don't read content at all. Only the comparison, range and regex operators warn.

Under the change:
- **Comparison, range and regex operators** still warn when they meet an unusable occurrence. What changes is their result for that combination: undetermined instead of `false`.
- **`NOT`, `AND`, `OR` and the predicate's final result** pass an undetermined value on silently, the way `NUMBER()` does. A warning has already been emitted for it.

One honest catch is that the current definition, "consuming means producing a result derived from the content", stops working. A comparison that returns "undetermined" didn't derive anything from the content either, so by that wording it would be silent. The rule needs restating along these lines: *a comparison is where an occurrence's content is needed, and needing it without having it warns.* It's slightly less elegant.

The alternative is to warn only when an undetermined value reaches the final result. That would make warnings mean "this file's outcome was uncertain" instead of "this file has bad data", and it would drop most of the audit value warnings currently have. I wouldn't do that.

A useful invariant follows from keeping the warning at the comparison: **a file can only be excluded because of bad data if a warning was emitted for it** (unless warnings are suppressed). The exit code could later use this to tell "bad data that changed the answer" apart from "bad data that didn't matter", but nothing requires that.

## Effects on the language as specified today

**Grammar and static analysis: no change.** Types stay the same and booleans are still never absent. A state test should still reject a boolean operand, because allowing `(x == 5) IS UNUSABLE` would add a second guard style for no gain.

**Evaluation changes in four places:**

1. **Rule 2.** An unusable occurrence makes its combination undetermined instead of `false`.
2. **Quantifiers.**
   - "Some" (the default): `true` if any combination is `true`, else undetermined if any is undetermined, else `false`.
   - `ALL`: `false` if any combination is `false`, else undetermined if any is undetermined, else `true`.
3. **Logical operators** (u = undetermined):

   | `a` | `b` | `a AND b` | `a OR b` | `NOT a` |
   |---|---|---|---|---|
   | u | `true` | u | `true` | u |
   | u | `false` | `false` | u | |
   | u | u | u | u | |

   The final result selects a file only if it is `true`.
4. **Short-circuiting.** `AND` can only skip its right side when the left is `false`, and `OR` only when the left is `true`. An undetermined left side forces the right side to be evaluated.

**Rows that change:**

| Condition | `NOT (x == v)` now | Under the change |
|---|---|---|
| absent | selected | selected (unchanged) |
| unusable | selected, with a warning | not selected, with a warning |
| invalid regex from tag data | selected, with a warning | not selected, with a warning |
| unreadable file | not selected | not selected |

Three of the four rows now behave the same way. The remaining one is absence, which is ordinary data.

Leave unreadable files as they are. Turning them into unusable occurrences would invent a cardinality: `COUNT(artist)` would report 1 for a file whose tags were never read. At the final result, "abandoned" already means the same as "undetermined".

## Could a reasonable predicate change meaning?

- **Without `NOT`: which files are selected never changes.** Two side effects do change:
  - **More warnings.** In `NUMBER(x) > 5 AND NUMBER(y) > 5` with both junk, the right side now runs, so you get two warnings instead of one.
  - **More reading.** An undetermined left side no longer saves the cost of evaluating the right side.

  The guard idiom is unaffected, because `IS` is never undetermined. Short-circuiting on undetermined values could be kept for predicates without `NOT`, which would preserve today's behaviour exactly, but the rule then depends on how many `NOT`s enclose an expression. That's too subtle to specify.
- **With `NOT`: files with junk on the negated side drop out.** This is intended for "act on everything except X" with a risky command. It is the wrong direction for "hash or back up everything except X", where junk-tagged files would be skipped, with a warning. This is the real cost. It is also exactly why the decision belongs to the command, which only a third value makes possible.
- **"x or not x" is no longer always true.** `year < 2000 OR NOT year < 2000` is undetermined for a junk year. Nobody writes that deliberately, but someone rewriting a predicate might produce it. `NOT NOT a` still equals `a`, and De Morgan's laws still hold.

## Cognitive load

- **For users it's about neutral, perhaps lower.** Today, every `NOT` requires asking "could this data be junk?", and the spec needs three warning boxes to say so. After the change, the rule users need is one sentence: *a file is never selected because its data couldn't be read.* Predicates without `NOT` need no new knowledge at all. They coexist today, but only because of two special cases, and one of them rests on a third rule elsewhere. There's a way to get the same behaviour from the deduplication rule alone.

## How they coexist now

Take a hypothetical interpreted flag `compilation` whose tag holds `maybe`:

```
compilation == TRUE OR NOT compilation == FALSE
```

1. **Deduplication by source.** Both comparisons consume the same unusable occurrence. Its source is `compilation`, so it warns once.
2. **Operator results are exempt.** Each comparison produces an unusable result. `OR` and `NOT` combine those, and "consuming the unusable result of an operator never warns" keeps a later `==` from reporting the same bad tag again.
3. **"An identifier is never definite."** This is what stops `compilation` from reaching `AND`/`OR`/`NOT` directly. A boolean identifier always passes through a comparison first, and that comparison is where it warns.

So the requirement to warn about a bad flag is met by (1), and no double reporting is guaranteed by (2). The two never collide, because (3) ensures nothing read from data reaches a logical operator.

## Why that's fragile

- **(2) depends on where a value came from.** An implementation has to know whether an unusable occurrence was read from data or produced by an operator, which the value model doesn't otherwise record. The spec says it as a rule rather than deriving it.
- **The logical operators' blanket "never consumes, never warns" is only safe because of (3).** Suppose that rule is ever relaxed, say for a never-absent, single-valued flag in a closed namespace that someone wants to write bare. An unusable flag would then flow through `AND`/`OR`/`NOT` with no warning at all, and nothing in the warnings section would look wrong. It's the same kind of time bomb you've been removing, just one step further away.

## Getting both from one rule

Let an unusable occurrence carry a *set* of sources instead of exactly one:

- An occurrence read from data, or produced by a failed conversion, carries one source, as now.
- An operator's unusable result carries the sources of the unusable occurrences it met.
- **Consuming an unusable occurrence warns once per file for each source it carries that hasn't been reported yet.** That is just the deduplication rule, applied to sets.

Because iteration within an operator is exhaustive, an operator meets every unusable occurrence in its operands. It therefore reports every source its result will carry before handing that result on. Consuming the result later finds nothing new to report, so (2) follows from deduplication and no longer needs its own rule. The logical operators can be ordinary consumers too: today they would never find anything to report, and if (3) is ever relaxed, a bad flag reaching them would warn exactly as it should.

**What it costs:**
- "An unusable occurrence is born once and carries that source" becomes "carries one or more sources".
- The rationale's line that such a result "needs no source of its own" changes accordingly.
- Nothing about what a warning quotes changes. A source is always first reported where the data was consumed, so a warning still quotes the sub-expression that produced the bad data.
- In implementation terms it's a bitwise OR of the operands' source bitsets, which fits the bitset the rationale already sketches.

**What it buys:**
- No rule about where a value came from.
- No dependence on (3) for warnings to be correct.
- The warning behaviour of every construct, present or future, follows from "warn once per unreported source".

```markdown
**Consuming an unusable occurrence means asking a question of its content.** Only consuming emits a warning. The comparison, range and regex operators are the constructs that ask such questions -- they are where data is turned into a truth value -- and everything else follows from that one rule:

- The comparison, range and regex operators need the content of their operands in order to answer. **Reference** (what the spec says now):
```

```
    d = s.Normalize(NFD)                     // throws on a lone surrogate
    for rune r in d:
        if category(r) not in {Mn, Mc, Me}:  // "all combining marks are discarded"
```

**Proposed:**
```
normalize(s):
    if s is all ASCII: return ascii_lower(s)        // most tags; no allocation unless there's uppercase
    d = sanitize(s).Normalize(NFKD)                 // lone surrogates become U+FFFD; compatibility decomposition
    for rune r in d:
        if r in DIACRITIC_BLOCKS: continue          // a fixed set of mark blocks, not every Unicode mark
        if r is BMP:
            f = FOLD[r]                             // precomputed lower(upper(r)): simple case folding
            if f is LETTER_FOLD marker: append LETTER_FOLDS[r]   // ø→o, ß→ss, ...
            else: append f; simple &= f < U+0300
        else: append lower(upper(r)); simple = false
    return simple ? result : result.Normalize(NFC)  // recompose Hangul, kana, ...

literally(s):   if every char < U+0300: return s    // already in composed form
                else: return sanitize(s).Normalize(NFC)
compare(a, b):  code point order (UTF-16 comparison with a surrogate fix-up)
regex:          subject = normalize(subject), as for every operator; pattern untouched; IgnoreCase
```

## Decisions to review

1. **Which marks are stripped.** I suggest a fixed set of Unicode blocks instead of "all combining marks": Combining Diacritical Marks (U+0300–036F) and its Extended, Supplement, for Symbols and Half Marks blocks (U+1AB0–1AFF, U+1DC0–1DFF, U+20D0–20FF, U+FE20–FE2F). Latin, Greek and Cyrillic accents fold. Kana voicing, Indic vowel signs, Thai tone marks and Hebrew and Arabic points are kept. **A consequence to accept:** Cyrillic `й` folds to `и`, just as `ñ` folds to `n`.
2. **Letter folds** for letters with no decomposition: `ø→o`, `æ→ae`, `œ→oe`, `ß→ss`, `ł→l`, `đ→d`, `ð→d`, `þ→th`, `ħ→h`. Dotless `ı` already folds to `i` through case folding. Deliberately left out: `ŋ`, `ĸ`, `ƒ`, `ʒ`. The table is short and has to be owned, and this clears the open `deferred.md` entry about it.
3. **Compatibility folding** (NFKD rather than NFD). It folds fullwidth and halfwidth forms and ligatures, which helps Japanese collections. It also turns `²` into `2`, `½` into `1⁄2`, `™` into `TM` and `①` into `1`. I suggest adopting it.
4. **Case folding** uses lowercase-of-uppercase per character, which approximates Unicode's simple case folding. It fixes final sigma and folds `ſ→s`, `µ→μ` and the Kelvin sign to `k`. Full folding (`ß→ss`) is covered by the letter table instead.
5. **`LITERALLY` keeps canonical equivalence:** it applies NFC, the standard composed form, and nothing else. I suggest adopting this, at the cost shown above.
6. **Malformed text.** A lone surrogate in tag data is replaced with U+FFFD, so normalization can never abort a run. In a literal it should be an error reported when the predicate is read.
7. **Regex.** The subject is normalized exactly as for every other operator, including case and letter folds. The pattern is left alone and matching ignores case. That's one rule instead of today's special case. Consequences: the pattern `strasse` matches "Straße", and `\p{Lu}` never matches in normalized mode, because the subject has been lowercased. Under `LITERALLY` it works as before.
8. **Ordering** is by code point rather than UTF-16 unit, at negligible cost. Only `<`, `>` and `BETWEEN` notice the difference, and only with characters outside the BMP.
9. **Not in the proposal yet: default-ignorable characters** (soft hyphen, zero-width joiner, variation selectors). The reference strips variation selectors by accident, since they count as marks. The proposal keeps them, so `❤️` ≠ `❤`. I'd suggest also dropping variation selectors and soft hyphens. Say if you want that.

## What the libraries do

**1. The folk recipe is the current spec.** "Decompose, then drop the combining marks" is what most answers give. Go's `golang.org/x/text` version is `transform.Chain(norm.NFD, runes.Remove(runes.In(unicode.Mn)), norm.NFC)`. It recomposes at the end, which keeps Korean intact (our spec omits that step), but it still strips every nonspacing mark, so kana voicing and Thai and Indic marks go too.

**2. Unicode has no current standard for removing accents.**
- UTR #30, "Character Foldings", was withdrawn in 2008 without ever being approved.
- What remains standardized is NFKC_Casefold (`toNFKC_Casefold`): case folding, compatibility normalization, and removal of default-ignorable characters. It doesn't remove accents.
- Unicode does have a `Diacritic` property, but stripping by it fails the same way as stripping every mark. It includes the kana voicing marks (U+3099–309A), the Thai tone marks (U+0E47–0E4C), the Devanagari nukta and vowel signs, and the Hebrew points.

**3. Search engines.**
- **Lucene's `ICUFoldingFilter`** is based on the withdrawn UTR #30. It applies NFKC, case folding, accent removal and about two dozen more foldings (width, ligatures, superscripts and so on), and removes default ignorables. Kana folding isn't on its list.
- **Lucene's `ASCIIFoldingFilter`** maps Latin and symbol characters to ASCII "if one exists".

**4. Databases.**
- **SQLite FTS5**, the full-text search module (`unicode61` tokenizer, `remove_diacritics`), removes diacritics **from Latin-script characters only**. That's prior art for stripping by script.
- **PostgreSQL `unaccent`** uses a hand-curated rules file. Its entries for letters with no decomposition are `ß→ss`, `æ→ae`, `ø→o`, `đ→d`, `ð→d`, `þ→th`, `ł→l`, `ı→i` and `œ→oe`, essentially my table. For Cyrillic it folds **only `Ё→Е`; `й` isn't in the file.**

## Proposed hot loop

```
normalize(s):
    if s is all ASCII: return ascii_lower(s)
    d = sanitize(s).Normalize(NFKD)
    for rune r in d:
        flags = FLAGS[r]                                  // precomputed for the BMP
        if IGNORABLE in flags: continue                   // soft hyphen, zero-width joiner, variation selectors, ...
        if MARK in flags:
            if base_is_latin_or_greek: continue           // accents on Latin and Greek letters
            if r == U+0308 and last == 'е': continue      // ё → е; й, ї, ў are left alone
            append r; continue                            // every other mark is kept
        base_is_latin_or_greek = LATIN_GREEK in flags
        f = FOLD[r]                                       // lower(upper(r)), or the letter-fold marker
        append (f is marker ? LETTER_FOLDS[r] : f)
    return all_below_U+0300 ? result : result.Normalize(NFC)
```

## What I'd write for normative evaluation

**What it is.** The spec defines the syntax formally (the EBNF), but its semantics only in prose spread across about eight sections. I'd add an **EVALUATION** section, the counterpart of **GRAMMAR**. It would define the value of every construct in a few lines of pseudocode, with no examples and no explanations; those stay in the prose sections above it.

**Why it's worth having.**
- **It gives the tests one source of truth.** Several claims we've had to correct this session (that state tests can't be derived from each other, that `(ALL(genre))` doesn't parse, "the same phenomenon") survived because nothing short and formal existed to check them against.
- **Some properties become provable rather than asserted.** Two examples: a predicate without `NOT` selects the same files either way, and operand order never changes a result.
- **It's short.** I'd expect 60–80 lines, because most of the semantics is one generic operator rule.

**The shape it would take:**

```
Values
  value      = ABSENT | bag of one or more occurrences
  occurrence = usable(datum) | unusable(source)
  truth      = T | F | U          -- a definite boolean; U is an unusable one

eval(literal)      = bag{ usable(v) }
eval(identifier)   = as resolved by identifiers.md
eval(NUMBER(e))    = map over occurrences of eval(e); a failed conversion gives unusable(this call)
eval(COUNT(e))     = bag{ usable(cardinality of eval(e)) }
eval(FALLBACK(e,d))= ABSENT → bag{d}; otherwise map: unusable → d

eval(op(e1..en))                                    -- comparison, range, regex
  v = eval of each operand; if any is ABSENT: F
  order operands: ALL-quantified first, then the rest, ties by written position
  result = Q1 o1 ∈ v1 … Qn on ∈ vn : test(o1..on)
    test = U, reporting each unusable oj   if any oj is unusable
         = op's test on the data, prepared per normalization.md, otherwise
    ∃ over outcomes: T if any T, else U if any U, else F
    ∀ over outcomes: F if any F, else U if any U, else T
  every combination is evaluated

eval(e IS ABSENT)       = T if eval(e) is ABSENT, else F
eval(Q(e) IS USABLE)    = F if ABSENT; else Q over occurrences of (usable ? T : F)
eval(NOT a), eval(a AND b), eval(a OR b)    -- Kleene; b is evaluated unless a settles it

predicate result ∈ {T, F, U}; what U means is the command's decision
reports = the sources of every unusable occurrence reported while evaluating, once per file each
```

Next to it would go a compact table of the **static judgements**: each construct's type, and whether it's definite. That would replace the scattered "must be of type…" sentences with one place to look. Identifier resolution and string preparation stay in their own documents, which the section points to, as above.

**Decisions before I write it:**

1. **Where it goes.** I'd put it at the end of `predicates.md` as EVALUATION, next to GRAMMAR. The alternative is a separate `concepts/` document like `normalization.md`. Keeping it in `predicates.md` mirrors how syntax is specified, and readers already go there for the formal part.
2. **Notation.** I'd use plain pseudocode as sketched, in the same register as the EBNF. Mathematical notation would drift into the pedantic end of your style range, and structured prose wouldn't give enough over what we already have.
3. **Which text wins if they disagree.** I'd state that a disagreement between EVALUATION and the prose is a defect, and that until it's fixed, the tests follow EVALUATION. Making the prose explanatory-only would be a bigger statement than we need, and the prose currently does define things the pseudocode would only summarize, such as the guard idioms.
4. **Static judgements.** I'd include the table, so typing and definiteness live in one place. The "constraints not expressed by the grammar" list would stay, but only for the things the table can't express, such as range endpoints.

It doesn't need to wait for the `!=` discussion. Whatever is decided there changes one operator's test, not the machinery around it.
