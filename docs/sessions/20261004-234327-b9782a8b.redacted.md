## Claude

Short version: the two spellings are close, and I lean slightly toward `=~`. The one argument for `~=` that carries real risk can be fixed with a better diagnostic. The others are mostly about how it looks.

## Where things stand

The spec uses `~=`. `architecture.md:15` already lists `=~` as a spelling from another language that the parser should recognise and correct. No code or tests exist for the operator yet, so switching would only mean changing the docs.

## Prior art

**`=~` for regex is the common spelling:**
- **Languages:** Perl, where it started; Ruby, Bash `[[ ]]`, zsh, Elixir, Crystal, Groovy, Vim script and Nim.
- **Query languages:** Neo4j Cypher, the PromQL/LogQL/Alertmanager label matchers, Jayway JsonPath, and the Apache httpd and lighttpd config languages.
- **Music tools:** MPD's filter syntax, `(artist =~ 'regex')` with `!~` as its negation. MPD's users overlap Goro's audience.
- Almost all of these pair it with **`!~`**.

**A bare `~`:** awk (`~`, `!~`), PostgreSQL (`~`, `~*` for case-insensitive), nginx and Varnish.

**`~=` exists, but rarely as regex match:**
- **Lua, MATLAB/Octave and Smalltalk:** it means **not equal**.
- **Swift:** it's the pattern-match operator, with the pattern on the **left**.
- **CSS:** `[attr~=v]` matches a whole word in a space-separated list.
- **D:** it means append-assign.

I don't know of a mainstream language that spells regex match `~=`.

**Keyword spellings:** MySQL/SQLite `REGEXP`, Mp3tag's `MATCHES` (from memory, worth checking), XPath `matches()`. Java's and Kotlin's `matches` require the whole string to match.

**Other music tools:** beets uses `field::regex`. Quod Libet uses `/re/`, with flags for case and, I think, diacritics. Neither has an infix operator.

## Arguments for `~=`
- **It fits the family visually.** `==`, `!=`, `<=`, `>=` all have the form "modifier character, then `=`". `~=` reads as "loosely equals", which matches Goro's default semantics: case-folded, diacritic-folded, substring match.
- **It doesn't suggest a `!~`.** Goro deliberately has no negated form.
- **It's already written.**

## Arguments for `=~`
- **People already know it.** Anyone who has used a regex operator has probably used this one, including MPD users.
- **It's never been "not equal".** Nobody will read it as the opposite of what it does.
- **Perl's `=~` matches your new design closely.** In Perl, `=~` binds a string to `m/…/`, and the right-hand side is effectively part of the operator. That's now true of Goro's `=~ r"…"`, after the drop-dynamic-regex line made the pattern a raw string inside the operator.

## Unobvious points

1. **The Lua misreading combined with your current diagnostic gives a silent wrong answer.** Someone who knows Lua writes `artist ~= "Metallica"` meaning *not equal*. They get a static error that helpfully offers `r"Metallica"`. If they accept it, they get a substring match, which is roughly the opposite of what they meant, with no further warning. This is the only argument here about a wrong result. It goes away if you choose `=~`, or if the `~=` diagnostic also says "for not-equal, use `!=`". Lua is common in audio tools (Reaper, Renoise, mpv scripts), so this could actually happen to Goro users.
2. **Whichever you pick, you use up both spellings.** Having `=~` and `~=` mean different things would be cruel. So the choice also decides whether "approximately equal" stays free. Fuzzy artist matching for deduplication is plausible for a library manager, and `~=` is its natural spelling. Choosing `=~` keeps that option open; choosing `~=` closes it.
3. **Anchoring expectations come with the spelling.** PromQL and Cypher `=~`, Groovy `==~` and Java/Kotlin `matches` match the whole string. Perl, Ruby, Bash and MPD `=~` match anywhere. Goro matches anywhere, so `=~` follows the larger and older tradition. But a keyword like `MATCHES` would bring the Java whole-string expectation.
4. **`!~` needs a diagnostic either way.** It's the most likely thing a user types for "doesn't match", and `architecture.md`'s list doesn't include it yet. The answer should be `NOT (x =~ r"…")`. The lexer has to recognise `~=`, `=~` and `!~` as tokens even where they aren't operators, so it can report the right error.
5. **A keyword is now a real third option.** Since the pattern became part of the operator, `~=` works like `BETWEEN` (a keyword) more than like `==`. `artist MATCHES r"^the "` would fit and sidestep this whole question. The costs: one more reserved word, more typing, and the whole-string expectation from point 3. I wouldn't pick it, but the recent change is what makes it worth considering.
6. **Shell behaviour doesn't matter here, but I checked.** In zsh, an unquoted `=~` word fails with `zsh: ~ not found` because of `=command` expansion. Predicates always contain `"` and are passed single-quoted (`--filter='…'`), so this never happens in practice.

## Recommendation

`=~`, with:
- `~=` diagnosed as "did you mean `=~`? For not-equal, use `!=`";
- `!~` diagnosed as "use `NOT (… =~ …)`".

The fit-the-family argument for `~=` is weak, because `<`, `>`, `BETWEEN` and `IS` already break that pattern. Familiarity, plus no chance of being read as not-equal, matters more. It's close, though. If you prefer how `~=` looks, keeping it is fine, as long as you add the extra not-equal hint to its diagnostic.
