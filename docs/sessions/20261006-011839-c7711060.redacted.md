The core of the design holds up well, and I wouldn't change it: absence as the only cardinality-zero value, nesting by quantifier, exhaustive iteration inside an operator, and warning sources interned by structure. ## The three causes

1. **The three-valued change hasn't fully spread.** Booleans can now be unusable, but several premises written for two-valued booleans are still stated as if they were true. That makes some guarantees, a warning category and a test property quietly wrong.
2. **The static analysis knows too little.** Definiteness is a single yes/no flag, "literal" is used where "constant" is meant, and a static check can only end in an error. Several rules are therefore too strict in one place and silent in another.
3. **Some built-in facilities follow rules users can't access.** The global namespace and the open namespaces work in ways the language refuses to expose, or that clash with its own guarantees and its promise to stay backward compatible.

Two more clusters stand on their own: how coarse "unreadable" is, and the regex/normalization trade-offs. Smaller items come at the end.

## A. The three-valued change hasn't fully spread

**A1. The warning categories were defined before unanswered predicates existed.** `rationale.md:278` separates the categories like this: a data warning means "the run answered every question", while an unreadable file means "it did not answer one of them, so its output is incomplete". A predicate that evaluates to unusable is now a question left unanswered, and `goro list` drops that file. By the rationale's own definition, that belongs with `file`, not `data`.

The practical effect:
- `faq.md:127` calls `--no-warn=data` "ordinary housekeeping". It now also silently drops every file whose answer depended on junk data.
- `deferred.md:52` merges "I accept junk tags" with "I accept unanswered questions".
- `faq.md:173` ("a data warning means every file was answered") is stale.

Data warnings currently mean two things: "junk was seen" (noisy, harmless) and "junk changed the outcome for this file" (rare, consequential). The fix I'd look at is reporting the second on its own, low-volume channel, so that silencing the noise doesn't also silence the drop. That fits the rationale's own position that "the noisy wrong answer is the better default".

**A2. "Nothing but negation can turn false into true" is false** (`rationale.md:65`). Each of these predicates uses no `NOT`, yet it changed which files it selects when unusable stopped meaning false:
- `(year < 2000) == FALSE`
- `(year < 2000) != TRUE`
- `FALLBACK(year < 2000, TRUE)`
- `(year < 2000) IS UNUSABLE`

The first generated property in `testing.md:184-190` ("a predicate without `NOT` selects the same files…") will therefore fail once the generator produces boolean comparisons. The property that actually holds is monotonicity, which is the second one listed. Restate the first property, or limit it to monotone constructs.

**A3. The global namespace breaks the strong form of the "unusable never selects" guarantee.** Take an APE `year` holding junk and an Id3v2 `year` of 2005. The global `year` gives 2005, so `year > 2000` is true. Had the APE value been readable as 1995, it would have won the fall-through and the predicate would be false. So the result depends on what the unreadable data held, and nothing warns.

`rationale.md:63` states the guarantee two ways: "true only if it would be true whatever the unreadable data had turned out to hold", and "not selected on the strength of data that could not be read". The global namespace satisfies the second and breaks the first. The spec should choose one wording and say explicitly that the fall-through is an exception (see B).

## B. The global namespace is COALESCE, built in

COALESCE was dropped, and `FALLBACK()` limited to a literal default, because a construct choosing among candidates "has to say whether the candidates it did not use were evaluated" (`rationale.md:223`, `deferred.md:64`). The global namespace already answers that question: stop at the first usable candidate, don't consult the rest, and silently drop the defects it skipped over. The rationale defends that answer at `rationale.md:162`.

So the question that blocked the function has an accepted answer, and only built-in code gets to use it. Meanwhile the cost the rationale admits remains: no cross-format preference for album artist, track, disc or anything else outside the five global identifiers.

Proposal: one function, say `FIRST_USABLE(a, b, …)`, with exactly the facade's semantics, and global identifiers defined as calls to it (`artist` ≡ `FIRST_USABLE(vorbis::artist, ape::artist, id3v2::artist, id3v1::artist)`). The facade becomes explainable within the language, users can extend it, and A3 becomes a documented property of a single construct. The `FALLBACK` literal restriction can stay as it is.

## C. The static analysis knows too little

**C1. Definiteness merges two separate facts:** "never absent" and "never more than one occurrence". The `!=` trap has two halves, absence and multiplicity, but the rule can only see whether both are excluded. Consequences:
- `FALLBACK(file::extension, "") != "mp3"` is rejected, although it has exactly one occurrence for every file. FALLBACK removes absence, and the identifier can never hold two values.
- For `id3v1::genre != "blues"`, the diagnostic asks for `ALL` or `ANY`, which mean the same thing on a value that can hold at most one occurrence. The quantifier is really serving as a token for "absent counts as false".
- `file::duration` was left out of the definite list because nobody has said whether a readable file can lack a duration. That is a gap in the spec in its own right; see G.

Cardinality bounds would fix all three: {0..1, 1, 1..n, 0..n}. Definite becomes "exactly 1", FALLBACK raises the lower bound, the catalog declares bounds, and the `!=` diagnostic can name the reading that actually differs. A future boolean identifier read from a single Id3v2 frame would also benefit.

**C2. "Literal" is a syntactic stand-in for "constant".** Being a literal decides:
- the numeric-literal exception
- what `FALLBACK`'s default may be
- what range endpoints may be
- the static check in `NUMBER("x")`
- the special case for parenthesized literals

`rationale.md:239` already notes that named constants or concatenation would reopen the question. So would arithmetic, which the rationale lists as plausible. The sign is lexed as part of the number, so if `-` ever becomes an operator, `-5` stops being a literal and all of those rules shift.

A "constant" property in the static analysis, produced only by literals today, would change nothing now and would stop each of those future additions from being a breaking change.

**C3. A static check can only end in an error.** `warnings.md:20` says "there is no third category", so anything knowable before the run that isn't certainly wrong passes silently:
- `id3v2::TYER` is documented as always absent (`identifiers.md:253`). That is knowable before the run, so `rationale.md:269` says it should be an error. It is a second hole in the "every error before any file" promise, and unlike the open-namespace typo (`deferred.md:44`) it can be closed. The same goes for `TT2` and the other v2.2/v2.3 names that have a v2.4 counterpart.
- An accented regex pattern (F1) and a misspelled open-namespace name have the same shape.

Either make the cases that are known for certain into errors, or add a notice issued once before the run.

## D. Open namespaces mix two vocabularies

**D1. Adding names breaks compatibility.** In `vorbis`, Goro's chosen names, which are renamed and typed, live next to field names passed through as strings, and the chosen names win (`vorbis::track` reads `TRACKNUMBER`). Suppose a future release adds `vorbis::disc` meaning `DISCNUMBER`, typed as a number. Today `vorbis::disc == "1"` is valid and reads a field called `DISC`. After the change it is a type error, and the identifier reads a different field.

Interpreting an existing pass-through name, for example typing an APE key as a number, does the same thing. This conflicts with the reversibility argument the rationale relies on elsewhere (`rationale.md:185`). FLAC and Ogg will bring `vorbis` into real use, so decide this before then. Options include giving pass-through names a space of their own, or a rule that chosen names never rename a field.

**D2. The meaning of `::` inside an open namespace hasn't been settled.**
- In the interpreted namespace, `TXXX`, `COMM` and `WXXX` produce bags of unrelated values. MusicBrainz IDs, ReplayGain values and mood all end up in one bag, although `predicates.md:163` defines a multivalue as "the same kind of data recorded more than once".
- In the raw namespace, they produce `[MOOD] calm`, which isn't raw.
- The deferred two-part name would make `id3v2::TXXX` both an identifier and a namespace. `raw` is already a reserved sub-namespace name inside open namespaces.

Settle what a path part means in an open namespace before the tag-namespace line starts.

**D3. "Unusable" carries two meanings.** Cover art resolves to unusable, so `id3v2::APIC == "x"` warns on every file that has artwork. The open `non-text-tag-data` line covers this. Related: an undefined genre index is unusable in Id3v1 (`identifiers.md:201`) but "left as recorded", and usable, in Id3v2 (`identifiers.md:274`). That is the same defect with two different outcomes.

## E. "Unreadable" is too coarse

`warnings.md:47`: a file whose tags can't be parsed, "even if only one of them is damaged", is unreadable. Elsewhere the spec is precise down to the single occurrence, but here it switches to all-or-nothing for the whole file:
- A damaged APE tag blinds `id3v2::artist == "x"`.
- The `file` category, which the FAQ calls the bit-rot signal you should never suppress, also collects ordinary tag defects. Those are the noisy kind.
- Whether a file counts as "unreadable" depends on the order of the predicate's operands.

The value model already has the right shape for this. A tag format that fails to parse could produce unusable occurrences for that format's identifiers, which falls in the `data` category, and the global fall-through would route around it. `file` would then mean I/O and audio failures only.

Whether TagLibSharp can report failures per format needs checking. The tag namespaces aren't built yet, so now is the cheap time to decide.

## F. Regex and normalization: the fixes cost more than the problems

**F1. An accented pattern silently matches nothing.** `artist =~ r"^Motörhead$"` matches nothing at all, including "Motörhead" itself. That is exactly the failure `rationale.md:142` called decisive for durations ("silently matches nothing, which looks exactly like a collection that genuinely has no such file"), yet here it is accepted. It hits Nordic, Greek and Vietnamese collections hardest.

The stated objection to a diagnostic is that `mot[öo]` works. But the `ö` in that pattern can never match a normalized subject, so a diagnostic pointing it out would be accurate, not a nuisance. The cost of the alternative was weighed carefully; the cost of the current choice wasn't.

**F2. Normalization isn't stable in three ways:**
- It isn't idempotent (`implementation.md:34`). A normal form that doesn't map to itself usually means a step is in the wrong order. Here, case folding turns U+0345 into a letter after accent stripping has already run.
- Some of its data comes from the host machine's ICU (`implementation.md:43`). That is a milder version of the "result depends on the machine" problem used to reject regex timeouts (`rationale.md:124`).
- The rules are marked provisional, yet whether a predicate is valid depends on them: the `BETWEEN` min > max check on string endpoints. Changing the rules can turn a valid predicate into an invalid one.

**F3. String `BETWEEN` traps anyone filtering by prefix, and the spec's own examples fall into it.** Because the upper bound is inclusive, `artist BETWEEN "m".."n"` excludes Nirvana, `genre BETWEEN "a".."b"` excludes blues, and `"ma".."mi"` excludes Miles Davis (`predicates.md:222, 376, 558`).

## G. Smaller inconsistencies and gaps

- `implementation.md` says nothing in it changes behaviour, but it defines observable behaviour: following symbolic links during a directory walk (`:66`), the meaning of `file::size` for a link (`:52`), and damaged tags versus `file::duration` (`:58`). `identifiers.md` says none of this.

- `file::duration` has no stated rule for when it is absent or unusable.

# Rethinking open namespaces

I think every one of the current problems has the same cause. A namespace in Goro does three jobs at once:

1. **It chooses the source:** which tag format to read.
2. **It chooses the vocabulary:** Goro's own names (`track`), or the file's names (`TRCK`, `MOOD`, `Album Artist`).
3. **It chooses the interpretation:** trimmed and parsed, or raw.

Each problem is two of these jobs colliding:
- **Shadowing, and new names breaking old predicates** (1+2): `vorbis::year` hides a field called `YEAR`, and adding `vorbis::disc` later would change what an existing predicate reads.
- **The table of renamed raw counterparts** (2+3): `vorbis::track` versus `vorbis::raw::tracknumber`, while `vorbis::raw::track` reads a different field.
- **`::raw` as a nested path** (3 written as part of a name).
- **Quoted name parts, and case rules set by the language rather than the format** (the file's names forced into identifier syntax).
- **`TXXX`/`COMM` needing two-part names** (the file's names don't fit a single identifier).
- **Typos silently matching nothing** (an open vocabulary in identifier position).

So the redesign I'd propose gives each job its own construct and lets no construct do two.

## The core proposal: sources, concepts, fields

**Sources.** `file`, `id3v1`, `id3v2`, `ape` and `vorbis` (later `mp4`). A source is a flat, single-level qualifier. Nothing is nested.

**Concepts.** These are Goro's names: `artist`, `track`, `year`, `genre`, `comment` and so on. There is one closed table of them, each with a type and an interpretation. A concept is defined once, with one cell per source saying which field it reads and how:

```
concept  type    vorbis        ape      id3v2         id3v1
artist   string  ARTIST        Artist   TPE1          artist field
track    number  TRACKNUMBER   Track    TRCK          track byte (v1.1)
year     number  DATE          Year     TDRC          year field
genre    string  GENRE         Genre    TCON + rules  genre byte → name
```

- `id3v2::track` means the track concept, read from Id3v2 only.
- Plain `track` means the same concept across tag sources, best-ranked first. That's the global namespace, which now covers every concept for free (today there is no global `track`).
- An empty cell, such as `id3v1::albumartist`, is a static error.

The vocabulary is closed, so a misspelled concept is an error with a suggestion. Adding a concept later never takes over a field name a predicate was already reading.

**Fields.** `source::field("KEY", …)` reads the source's own data as text, exactly as recorded. It has these properties:
- It is always a string and never definite.
- Its arguments must be literals, as `FALLBACK`'s default, range endpoints and patterns already must be.
- The format owns how names are matched and how many arguments it takes:
  - `vorbis::field("MOOD")`
  - `ape::field("Album Artist")`
  - `id3v2::field("TXXX", "MOOD")`
  - later, for an MP4 freeform atom: `mp4::field("----", "com.apple.iTunes", "MOOD")`

**What disappears entirely:**
- open versus closed namespaces
- raw namespaces, and nested namespaces generally
- interpreted pass-through fields
- quoted identifier parts
- well-known names that shadow real fields
- the renamed-counterparts table
- the `[MOOD] calm` presentation

What a user has to learn is three sentences:
1. A concept name asks every format, best first.
2. Prefix a source to ask only that source.
3. `source::field(...)` reads anything that source holds, as recorded.

| Want | Today | Proposal |
|---|---|---|
| Track, any format | (no global `track`) | `track` |
| Id3v2 track | `id3v2::track` | `id3v2::track` |
| `TRCK` as recorded | `id3v2::raw::TRCK` | `id3v2::field("TRCK")` |
| Custom Vorbis field | `vorbis::mood` / `vorbis::raw::mood` | `vorbis::field("MOOD")` |
| APE key containing a space | `ape::"album artist"` | `ape::field("Album Artist")` |
| TXXX:MOOD | `id3v2::raw::TXXX =~ r"^\[MOOD\] "` | `id3v2::field("TXXX", "MOOD")` |
| A nonstandard Vorbis `TRACK` field | `vorbis::raw::track` (not the same as `vorbis::track`!) | `vorbis::field("TRACK")` |
| Year frame of a v2.3 tag | `id3v2::TYER`, which is silently absent | your call (see choice a below) |

## Your `id3v2::tag(...)` idea, examined

**Do functions in namespaces break anything?** Not in the grammar. An identifier and a call still differ only by a following `(`, so one token of lookahead is still enough.

Two rules do change:
- `predicates.md:569` says a qualified name is never a call. Names would instead resolve in their namespace whether or not a `(` follows.
- The rule that no function shares a name with a global identifier becomes a rule per namespace.

Warning sources still intern cleanly: the call's identity is the qualified symbol plus its literal arguments. One detail follows: two keys that the format treats as equal have to intern as one source, which is one more sign that the format should own name equality.

The real question is what kind of thing `field()` is. It doesn't transform values; it addresses data. The honest framing is **an identifier that takes a name**: it behaves like an identifier under every rule (type, cardinality, lazy loading, warning source) and just happens to use call syntax. Requiring literal arguments is what keeps it static.

**Format as an argument: `field(id3v2, "TXXX", "MOOD")`.** I think this is the weaker option, for three reasons:
- **A new kind of value.** `id3v2` has to become either a new kind of bare word or a magic string. Either way the format would then be written two ways: `id3v2::track` here, an argument there.
- **Arguments that depend on a value.** What the remaining arguments mean would depend on the value of the first one (TXXX takes a description, Vorbis takes only a key). That is overloading by value, where the namespace form gives each format its own signature in the place the format already lives.
- **The no-namespaces variant doesn't save it.** Taken to its end, `artist(id3v2)` and `size()`, there would be no `::` at all. It even yields a nice rank override, `artist(ape, id3v2)`. But `artist` and `artist(...)` would share a name, and some arguments would be addresses while every other argument in the language is a value. That kind of irregularity is what this redesign is trying to get rid of.

**Boilerplate.** `vorbis::field("MOOD")` costs eight characters more than `vorbis::mood`. That's fine, because anything frequent should become a concept, and growing the concept table is now safe.

**The name.** In ID3 terms the "tag" is the whole block, so `id3v2::tag("TPE1")` reads a little like "the Id3v2 tag". `field` is Vorbis's own term and works generically. Per-format words (`frame`, `item`) are more precise but give users more to learn.

## Choices inside the proposal, for you to make

**a. What "as recorded" means for Id3v2 frame names.**
- Either `field()` addresses frames by their v2.4 identifier, with obsolete names such as `TYER` and `TT2` becoming static errors that suggest the right one,
- or it reads the frame identifiers actually on disk, so the differences between versions show.

I lean towards the first. Unifying the names is about how a frame is addressed, not about its content. It is also partly forced: TagLibSharp converts some frames when it reads them, so "on disk" can't always be honoured.

**b. Where trimming goes.** Interpretation now lives only in concepts, so `vorbis::field("MOOD")` is untrimmed. The options:
1. Accept that.
2. Add a `TRIM()` function.
3. Move edge trimming into the normalized comparison mode.

I find the third attractive. Normalized mode already exists to ignore differences a person wouldn't count, and whitespace at the edges is one of them; `LITERALLY` would still see it. The cost is that it applies to every string comparison, including `file::path`. It also means `IS ABSENT` treats a field holding only spaces as present, which seems right for something billed as an escape hatch.

**c. Whether concepts can be defined in the language.** Two additions would be needed:
- the parse rules exposed as functions, for example a `YEAR()` for date-shaped text and a `TRACKNUMBER()` for track-shaped text
- the `FIRST_USABLE()` function from the earlier review

With those, every concept cell becomes a one-line definition, and the identifier reference turns into a table of definitions instead of prose:
```
id3v2::track = TRACKNUMBER(id3v2::field("TRCK"))
track        = FIRST_USABLE(vorbis::track, ape::track, id3v2::track, id3v1::track)
```
Users could then apply Goro's own interpretation to any field, for example `YEAR(vorbis::field("ORIGINALDATE"))`. The cost is more functions. A parse function named `YEAR()` would also collide with the concept `year` under the current naming rule; either drop that rule or choose other names.

**d. Data that isn't text.** If `field()` reads text only, cover art and other non-text data get concepts of their own and their own types, such as an `artwork` concept. That takes over most of the open `non-text-tag-data` line. For Id3v2, `field("APIC")` can even be a static error, because the frame ID is a literal. APE's binary flag is still known only at run time, so for APE one question remains: should a binary item be absent or unusable when read through `field()`?

**e. Checking field names.** The arguments are literals, so syntax checks per format become cheap. Two examples:
- an Id3v2 frame ID must be four uppercase letters or digits
- `TXXX` requires a description

The rationale rejected such checks when they applied to identifiers. As checks on a string they cost much less. Misspelled field names would still be silent, but only in the escape hatch, where the user has deliberately stepped outside Goro's vocabulary.

**f. A `field()` with no source.** Key spaces differ between formats, so `field("MOOD")` has no single meaning. I'd make it an error. Asking across formats is then either a concept, or `FIRST_USABLE(vorbis::field("MOOD"), id3v2::field("TXXX", "MOOD"))` written by the user.

## For contrast: patching in place

The alternative is to keep open namespaces and patch them:
- freeze the rule that well-known names never rename a field
- add `id3v2::TXXX::"MOOD"`
- reject the obsolete frame names
- give each format control over case matching

That meets your first two goals and fails the third. Every patch is one more paragraph of manual, and the three jobs stay tangled.

**1. Sources.** Close, with two corrections:
- **Not just a rename.** A source is flat (no `id3v1::raw`-style nesting), and it no longer has a vocabulary of its own: every source exposes names from the one concept table. So the open/closed distinction disappears because everything is closed, not because it was dropped.

The closer ancestor is today's global identifiers merged with each namespace's well-known identifiers into a single table:
- each concept is a row

## What it buys

**A clean line between conversions and functions.** If `AS` is defined as an operator that converts each occurrence separately and never changes how many there are, the boundary becomes simple:
- **`x AS T`** converts each occurrence to `T`. Absent stays absent. Unusable stays unusable and keeps its source. A conversion that fails gives an unusable occurrence whose source is the `AS` expression.
- **Functions** are everything else: `COUNT()`, `FALLBACK()`, `PREFERRED()` and `field()`. Each of them may change how many occurrences there are, or turn absent into present, and none of them converts.

`NUMBER()` and `STRING()` leave the function list. Anything odd about conversions then stays after the `AS`.

**It solves question 4 in the sources-and-fields brief.** That question was how to expose the parsing rules without a `YEAR()` function clashing with the concept `year`. After `AS`, the parsing rules are just more targets:
- `id3v2::year = id3v2::field("TDRC") AS YEAR`
- `id3v2::track = id3v2::field("TRCK") AS TRACK`

A target names an interpretation that has a result type. The plain type names are simply the interpretations that do nothing extra. The concept and the conversion share a name because they mean the same thing, and they sit in different syntactic positions, so they can't collide.

**It closes a gap from the review.** `AS DURATION` and `AS BYTECOUNT` give the missing conversions into those types, so a `LENGTH` tag can be compared with `file::duration`.

**It mirrors `IS`.** `IS` asks about state and takes a closed word on its right; `AS` changes type and takes a closed word on its right. Both are easy to teach together, and SQL users know `CAST(x AS T)`.

**Some things carry over unchanged.** Interning warning sources, definiteness ("when its operand is"), and the static errors (a boolean operand, `"x" AS NUMBER`, converting a value to its own type as a no-op) all work exactly as they do for `NUMBER()` and `STRING()` now.

## What it costs, or makes you decide

1. **A precedence level.** Function call syntax delimits itself; a postfix keyword operator doesn't. `x AS NUMBER > 5` has to mean `(x AS NUMBER) > 5`, so `AS` needs its own level, binding tighter than the comparisons, just above primary expressions. That's easy today. If arithmetic is ever added, though, readers would have to know whether `a + b AS STRING` converts `b` or the sum. Postgres's `::` cast is the familiar example of that trap. Parentheses fix it, but they'd be the spec's answer to a readability problem the function form never had.

2. **Modifiers sit in a tempting wrong place.** `ALL(x) AS NUMBER > 5` reads naturally, but it puts a modifier on an operand of `AS`, which is an error, exactly as `NUMBER(ALL(x))` is today. With the function form the misplacement is at least visible; with the postfix form it looks right.
   - My lean is to keep the rule and give a diagnostic offering `ALL(x AS NUMBER)`.
   - The alternative is letting quantifiers pass through `AS`. That's well defined, because `AS` keeps the number of occurrences, but it would reopen the questions the rationale settled by putting modifiers on the outside, and every future operator would ask for the same exception.

3. **The right-hand side must stay a closed, static vocabulary.** If parameterised targets ever arrive, say a date format, their parameters must be literals. Whatever follows `AS` must also have a known end, or the precedence level stops working. So the scope for unusual grammar is real, but it's bounded: a target word, plus literals at most.

4. **The cardinality rule stops some things being conversions.** It means:
   - genre resolution, which splits a frame into several values, can't be a conversion; it stays inside a concept;
   - neither can a trim that turns a blank field into absent.

   I'd keep the rule regardless, because without it `AS` stops being a simple idea.

5. **Keywords.** `AS` becomes reserved. The target names (`NUMBER`, `STRING`, `DURATION`, `BYTECOUNT`, `YEAR`, `TRACK` and so on) can be contextual, since the grammar only places them after `AS`. But the spec reserves the state names after `IS` so that misuse can be diagnosed, and consistency argues for treating these the same way.

6. **Chaining.** Should `x AS YEAR AS STRING` be allowed? It's composition and reads left to right, so allowing it is harmless. Making `AS` non-associative like `IS` is also harmless. This is a small call.

7. **New text to specify.** Text-to-duration and text-to-bytecount parsing need rules. The obvious answer is the literal syntax, as `AS NUMBER` already uses for numbers. The undecided part is whether bare `"90"` is accepted as ninety seconds.

## What the binder does today

`Analysis.cs` makes one recursive pass, and in every node method it does all of these at once:
- resolves names against the catalog;
- works out the type, including the rule that lets a bare number stand for a bytecount or duration;
- works out definiteness;
- tracks whether the expression is a literal;
- builds the structural form ("shape") that warning sources are interned by;
- folds modifiers into each operand's quantifier and each operator's comparison mode;
- checks every rule and reports its diagnostic;
- builds the typed evaluation tree.

`Bound` is essentially a bag of these computed properties (type, definite, literal, shape, node). `Comparison()` shows the problem well: the numeric-literal rule, the type check, the boolean-ordering check, the `!=` rule and node construction are interleaved in about 50 lines.

The four briefs we just wrote all add to this same method family:
- cardinality bounds replacing definiteness;
- constant values (`"x" AS NUMBER`, endpoint order);
- `AS` targets;
- `field()` argument checks for each source, concept cells, and `PREFERRED()`;
- possibly static notices such as `TYER`.

## How established compilers divide this

- **javac** names its phases plainly. `Attr` resolves names and types. `Flow` is a separate pass for facts such as definite assignment, which is close to definiteness. `Lower` desugars, then code is generated.
- **Roslyn** binds syntax into a bound tree carrying names, types and conversions. Separate walkers then run over that tree: flow analysis, and `NullableWalker`, a separate pass computing a small lattice of null states. `LocalRewriter` lowers it afterwards.
- **Rust** resolves names and lowers to HIR, type-checks that, then runs borrow checking as a dataflow analysis on MIR. Each analysis runs on the intermediate form that suits it.
- **SQL planners** (Calcite, for one) bind names and types, then compute "derived properties" on demand through pluggable metadata providers, including nullability and minimum/maximum row count. That last one is cardinality bounds under another name.
- **Attribute grammars** (JastAdd, Silver) state the principle directly. Each property is an attribute defined by its own equations, kept in its own module and woven into the node types.

The common shape:
1. Meaning is established once: names and types, producing a semantic tree.
2. Facts are computed by separate analyses over that tree, each owning one property and the rules about it.
3. The executable form comes last, by lowering.

## Why Goro ended up with everything in one place

Goro has the syntax tree (too raw: parentheses and modifiers are still nodes, and names are unresolved) and the evaluation tree (generic, shaped for evaluation). Decision D1 in `design/predicate-runtime.md` already named the cost: passes "other than evaluation" over the generic tree need a non-generic base or a generic visitor. With no tree in between, every analysis has to happen at the single moment of building, which means inside the binder.

## The shape I'd propose

| Stage | Job | Produces |
|---|---|---|
| Parser | as now | syntax tree |
| **Binder** | resolve names, assign types (including the bare-number rule, which only needs to know a literal is a number, a fact visible in the syntax), fold away parentheses and modifiers | semantic tree: one non-generic node family, with Goro types held as data |
| **Analyses** | each owns one property *and the rules that use it* | properties and diagnostics |
| **Lowering** | semantic tree to the typed evaluation tree; compile patterns, prepare ranges | `CompiledPredicate` |

The analyses, roughly:
- **Cardinality.** Bounds such as "at most one" or "exactly one", the lattice from the review. It owns three rules: the predicate must be a definite boolean, the operands of the logical operators must be definite, and `!=` needs a quantifier. These live with the property they're about, not in a general checker.
- **Constants and ranges.** Literal values, folding `"x" AS NUMBER`, and endpoint order checked in the comparison mode.
- **Sources.** The interned warning sources and the source table.
- **Patterns.** The regex validity checks.
- **Later:** `field()` arguments for each source, and static notices if they ever come.

Lowering then becomes the bridge `TypedNodes.cs` already half is. The D1 decision stays and even gets better, because the generic tree no longer has to support any pass but evaluation.

**Order follows dependencies.** Types need names. The analyses need types but not each other, so they can run in any order. Lowering needs everything and runs only on a predicate with no errors.

**Error reporting stays as complete as now.** The analyses must run on a tree that already contains errors, with error nodes silencing the checks that involve them, exactly as the error type does now. Otherwise a type error would hide a `!=` error until the next run, breaking decision D5 (report every independent error in one run).

## Cardinality inside the type, or beside it?

There's a real alternative to a separate pass: make cardinality part of the type, as XQuery does with `xs:string?`, `xs:string*` and `xs:string+`, or SQL with `NOT NULL`. XPath is already Goro's reference point for the `!=` trap.

I'd keep it beside the type:
- Goro's five user-facing types stay simple.
- The rule that operands must have the same type would otherwise have to ignore half of every type.
- Only three rules ever look at cardinality.
- XQuery's static typing, where occurrence counts carry the most weight, was an optional feature that few implementations supported, which is a hint.

## Costs

- A third family of node types (syntax, semantic, evaluation), for a language of about fifteen node kinds.
- A tree of a few dozen nodes walked several times, which costs nothing measurable.

In exchange:
- Each analysis can be tested on its own: assert an expression's bounds or its source table directly, instead of inferring them from which errors appear.
- Each upcoming line adds one analysis file instead of editing every node method.

**On the name.** "Annotator" isn't a standard term. I'd keep "binder" (Roslyn's sense: names and types), call each pass an analysis named after its property, and call the last step "lowering". Those terms are easy to look up for anyone who uses the code to learn from.

**On timing.** I'd make this its own line, landing before `as-operator` and `sources-and-fields`, so both land in the new structure instead of growing `Analysis.cs` and then being moved out of it. Short version: cardinality bounds pay for themselves soon, mostly once the concept table and `PREFERRED()` exist. Full constant folding doesn't pay yet. What does pay is the narrower step of treating "constant" as the property the literal-only rules check.

## Cardinality bounds

Each expression would carry a lower bound (0 or 1) and an upper bound (1 or many). "Definite" becomes simply "exactly one".

**Now:**
- **The obvious fix for the `!=` error is itself rejected.** `FALLBACK(file::extension, "") != "mp3"` is an error today, although it has exactly one occurrence for every file. `FALLBACK()` is the documented way to decide what absence means, so a user who tries it gets a second error. With bounds, `FALLBACK()` raises the lower bound to 1, the operand is exactly one, and the predicate is accepted.
- **Diagnostics stop asking for meaningless quantifiers.** For an operand that can hold at most one occurrence (`id3v1::*`, `file::extension`), the `!=` error currently asks for `ALL` or `ANY`, which mean the same thing there. With bounds it can say the actual problem, "this may be absent", and offer what decides it.
- **Definiteness stops being declared by hand.** Today three identifiers are marked definite by hand, and each function has its own "definite when its argument is" clause. With bounds, the catalog declares bounds and every function's rule is a small equation over them.

**Going forward:**
- **`PREFERRED()` gets the right answer.** The brief says the result is "definite when every argument is". Bounds say more: if any argument is never absent, the result is never absent. So `PREFERRED(id3v1::genre, "unknown")` is exactly one, while today's rule would reject it as an operand of `!=`.
- **Boolean data from tags becomes usable directly.** A compilation flag read from a single Id3v2 frame has at most one occurrence. With bounds, `FALLBACK(id3v2::compilation, FALSE)` is definite and can be used directly with `AND`, `OR` and `NOT`. Without bounds it always needs `== TRUE` first. This is the clearest future payoff.
- **The concept table needs it anyway.** Each concept cell has to state its cardinality somehow, and bounds are the natural form. It also helps users: the table would show at a glance that `id3v1::artist` can never hold several values.
- **Static notices, if they're ever added.** Expressions such as `x IS ABSENT` on something never absent, or `COUNT(id3v1::genre) > 1`, become provably always false. That's minor.

**What it costs users:** almost nothing visible. Bounds can live in `evaluation.md`'s static judgements, and the predicate documentation can keep saying "definite".

**My verdict:** worth doing, best together with `sources-and-fields`, where every concept cell gets bounds anyway. On its own today it buys one fixed rejection and better diagnostics.

## Constant folding

There are two different things under this name, and they deserve different verdicts.

**1. "Constant" as the property the rules check, instead of "literal".** Today several rules require a literal:
- the `FALLBACK()` default;
- range endpoints;
- the pattern of `=~`;
- `NUMBER()` rejecting a non-number string literal;
- the rule that lets a bare number stand for a bytecount or duration;
- and soon `field()` arguments.

Each rule uses syntax as a stand-in for "known when the predicate is read". The `as-operator` brief already needs the general version: `"x" AS NUMBER` must be a static error, which means converting a constant at bind time. So the constants analysis should compute values for literals, for conversions of constants, and for parenthesized constants, and the rules should check "constant". This is cheap, it's needed next, and it means any future way of writing a known value (a leading minus as an operator, named constants, concatenation) satisfies the rules automatically instead of reopening each one.

**2. Folding everything that can be folded.** That would mean computing `TRUE AND p`, `COUNT("x")` or `FALLBACK(5, 1)` at bind time. In today's language nobody writes these, folding them changes no answer and no warning, and the evaluation it saves is negligible next to reading a file. It starts to matter only with arithmetic (`file::duration > 5 * 60`) or user-defined constants, and even then only for the rules above.

**My verdict:** do the first, as part of `as-operator`, or of `semantic-analysis-passes` if you'd rather the "constants and ranges" analysis start with the right property. Skip the second until arithmetic or named constants are actually being designed.

5. **The cost of rework.** A worker's output is reviewed and integrated by the coordinator, on the expensive model. A cheap worker whose piece needs substantial rework costs more than it saved, and a bad wave costs a whole round.
6. **The fixed cost of starting cold.** Every worker reads `AGENTS.md`, the brief, the contract and the relevant docs before doing anything. ## Item 1: string ranges as prefix bounds

Yes. There's a clean way to say it, and good prior art. The rule:

> A string endpoint is compared with only as many characters of the value as it has.

Here "characters" means code points of the prepared strings, in the operator's mode. So `v BETWEEN a..b` holds when the first `len(a)` characters of `v` are not below `a`, and the first `len(b)` characters are not above `b`.

Consequences:
- **Lower bound:** unchanged in practice. Truncating gives the same answer as ordinary ordering.
- **Upper bound:** now includes every value that starts with it. `"ma".."mi"` includes Miles Davis, `"a".."b"` includes blues, and `"m".."n"` includes Nirvana.
- **Equal endpoints become a prefix test:** `"the".."the"` means "starts with the".
- **The reversed-range error needs restating:** a range is reversed when `a`, cut to `b`'s length, is above `b`. So `"mi".."m"` becomes valid: it's everything starting with "mi".

**Prior art:**
- **Phone books and encyclopedia spines:** "Ma–Mi" has always meant this.
- **Key-value stores** (LevelDB, RocksDB, Bigtable): a prefix scan's upper bound is the "successor" of the prefix, the smallest string above everything starting with it. That is the same rule, so the definition rests on established practice.

**Would it feel natural?** For music libraries, yes; it's how people read alphabetical ranges. The cost is that string `BETWEEN` no longer equals `min <= x AND x <= max`. That differs from SQL, where `BETWEEN 'a' AND 'b'` excludes "blues", but it differs in the direction people expect. `<` and `>` on strings stay ordinary dictionary order.

- the range operator section and the reversed-range rule in `predicates.md`;
- the range test in `evaluation.md`;
- a rationale entry and the `testing.md` rows;
- the string case of the range comparison, and the reversed-range check, in code.
