## Semantic gaps that will bite the implementer

4. **Normalizing the regex *pattern* is a real footgun (`:118`, `:263`).** Rule 4 normalizes both operands, and `:263` confirms the pattern is lowercased and diacritic-stripped. That silently rewrites regex syntax: `\W`→`\w`, `\D`→`\d`, `\S`→`\s`, `\B`→`\b`, `[A-Z]`→`[a-z]`, and `ö`→`o` inside a pattern the user wrote deliberately. This is the one place where the default "be forgiving" behaviour actively breaks correctness. I'd normalize *only the subject* and get case/diacritic insensitivity by compiling with `RegexOptions.IgnoreCase | CultureInvariant` over a diacritic-stripped subject — then document that the pattern is used verbatim. Also unspecified: which operand is the pattern (only implied), whether the left operand must be a string, and what happens on an invalid pattern (parse error? tainted null? — it can't always be caught statically if the pattern comes from a tag).

5. **Booleans have no type discipline.** Nothing says `AND`/`OR`/`NOT` require boolean operands, or what `NOT artist` / `artist AND year` do. Rule 1 ("any null input → operator evaluates to false") is stated for *any* operator, which nonsensically applies to `NOT`. Nothing says the top-level predicate must be boolean, nor that `a == b == c` is disallowed — yet `:140` ("the same operator in a chain is evaluated left to right") implies it's grammatical. Recommend: make comparison/`BETWEEN`/`~=` non-associative, state that boolean is only produced/consumed by logical operators, and state that a predicate must be a boolean expression.

6. **`ISNULL()` on a multivalue is undefined** — and this is the one function the doc designates as the sanctioned taint guard (`:196`, `:245`). Every other function spells out its multivalue behaviour; `ISNULL` doesn't. Is `ISNULL({null, "rock"})` true, false, or a boolean multivalue? If it's a multivalue, you've introduced boolean multivalues, which the quantifier machinery (defined only for *operands of operators*) doesn't cover, and `NOT ISNULL(...)` becomes undefined too. Needs an explicit rule.

7. **Nulls inside multivalues aren't specified against the quantifier rules.** `:148` says a multivalue may contain nulls, even all nulls. Combined with rule 1, `ALL(genre) == "rock"` is false if a single value is null — probably intended, but say so, since one malformed tag then poisons every universal quantifier. Also unspecified: whether nulls count toward `COUNT()`, whether a multivalue is a bag or a set (duplicates preserved? `COUNT` depends on it), and whether a one-element multivalue is distinguishable from a single value (`:229`'s "`COUNT(genre) > 1` is true iff `genre` is a multivalue" implies it collapses — worth stating outright in the Multivalues section).

8. **"the first time a tainted null value is used" (`:196`) — first time per what?** Per file, per run, per predicate, per sub-expression? On a 100K-file collection the difference is between one warning and 100K. This is the kind of thing `vision.md`'s scriptability goal makes load-bearing. Also unspecified: whether taint *propagates* (`STRING(NUMBER(x))`, `FALLBACK(x, 0) + …`), and whether the warning fires at the point of use or is aggregated at the end.

9. **Only `NUMBER()` can produce a tainted null — but identifiers can fail to interpret too.** `:52` says null represents "the absence of a value, **or the inability to interpret it in a reasonable manner**", and `identifiers.md` types `id3v1::year` as `number` even though the ID3v1 year field is four raw bytes that may be garbage. A garbage-but-present tag is exactly the case taint exists for, so it should produce a tainted null, not a plain one. Right now the spec leaves it as plain null and you get the silent-skip failure `:194` is trying to prevent.

10. **Durations are specified as integer-second literals but real audio durations are fractional.** `file::duration == 4m5s` will essentially never be true for an mp3, and rule 3 lets `1.5` become a 1.5-second duration that has no literal spelling. Specify the precision of `file::duration` and of duration arithmetic/comparison (and the same question for `NUMBER(duration)` round-tripping). Also: `:67` gives the *shape* `[#:]##:##` but never states that the groups are h:m:s — and it's inconsistent with form 1, where `90m` is presumably legal while `90:00` is not.

11. **Bytecount literals under-specified (`:62`).** The full suffix list isn't given (is bare `B` legal? `T`/`TiB`?), suffix case-sensitivity is never stated even though the spec writes `KB`/`KiB` and the example writes `1.4mb`, and fractional IEC values give non-integer byte counts (`1.4KiB` = 1433.6) with no rounding rule.

12. **Case-sensitivity of identifiers and namespaces is never stated.** Keywords and function names are explicitly case-insensitive; `id3v2::TIT2` suggests identifiers are case-sensitive; nothing says. Also: is the identifier character set ASCII letters or Unicode letters? And since function names aren't reserved (`:41`), the lexer needs `(`-lookahead to tell `all` the identifier from `ALL(` the call — worth a note, plus a rule forbidding a built-in identifier from colliding with a function name.

13. **When do errors surface?** `rationale.md` is emphatic that a run must never abort midway, and every type is in fact statically determinable (identifiers have declared types, functions have fixed result types) — so type errors, undefined identifiers, and `min > max` can all be reported *before the first file is touched*. One wrinkle: `min > max` for string ranges is *not* static, because whether `"M" > "m"` holds depends on whether `LITERALLY` is in play (`:76` vs `:98`) — worth resolving.

14. **Nothing says how a predicate reaches the CLI.** No command doc mentions predicates yet (`list.md` has no filter option), so `predicates.md` is currently orphaned. ## Design points worth revisiting

15. **Positional quantifier nesting makes `==` non-commutative (`:186`).** The spec is internally consistent, but `ALL(a) == b` being true while `b == ALL(a)` is false is a sharp edge, and it's at odds with `rationale.md`'s Pit-of-Success framing. The usual alternative — always order the quantifier prefix universal-outermost, rather than by textual position — makes `==` commutative again and keeps every example in the doc producing the same answer. The doc even has to spend a paragraph (`:190`) warning readers about the current rule, which is a hint. Worth a Q&A entry either way.

16. **No way to write a tautology.** No boolean literals, and `TRUE` is reserved-but-unusable (`:39`), so a script that always wants to pass a predicate argument can't write "match everything". Cheap to solve (allow `TRUE`/`FALSE` as literals, or document the omission).

17. **Function calls sit in the precedence table (`:131`) alongside `==`.** They're primary expressions, not infix operators; listing them there muddies an otherwise crisp table. Either add a "primary (literals, identifiers, parenthesised expressions, function calls)" row or drop them from the list.

18. **`ALL`/`ANY`/`LITERALLY` are annotations, not value transformations.** They're specified as functions returning values, but their effect is consumed by the *enclosing* operator. So `COUNT(ALL(genre))`, `FALLBACK(ALL(genre), "x")`, `NUMBER(LITERALLY(x))`, `ALL(LITERALLY(x)) == y`, `(ALL(genre)) == "rock"` and `ALL(ALL(x))` are all currently unanswerable. Simplest fix: state that these must appear directly as an operand of the operator they modify, and that nesting them inside other function calls is an error.

## 4. Regex normalization

Your solution is right, but it does **not** quite leave things closed. Three loose ends:

**(a) Rule 2 does not imply both operands are strings.** Rule 2 only requires the operands to have *the same* type. `file::size ~= 1kb` satisfies it (bytecount vs. bytecount), and rule 3 makes `year ~= 2000` satisfy it too (both become numbers). So `~=` needs an explicit "both operands must be strings", plus an explicit opt-out from rule 3 — otherwise `year ~= 2000` is legal and means something absurd.

**(b) An invalid runtime pattern returning false interacts badly with `NOT`.** `NOT (artist ~= sometag)` evaluates to *true* when `sometag` is a broken pattern, so the file gets processed on the strength of a failure. This is the same shape as the null asymmetry you already document prominently at `:120`, so I think the answer is just to call it out in the same way rather than change the behaviour — but it should be called out, because "false + warning" sounds safe and isn't under negation.

**(c) The warning needs a de-duplication scope**, same open question as the taint "first time" wording. Easiest is to define it once for taint and have this refer to it.

Also worth deciding while you're here: a **multivalue pattern operand** (each element validated independently, ordinary quantifier rules), and a **match timeout** — `.NET` regex with a user-supplied pattern over 100K files is one catastrophic-backtracking pattern away from a hang, and `vision.md` makes performance a stated goal.

### Proposed edits

**4.1 — replace general operator rule 4 (`:94`):**

> 4. When working with string values, all operators _normalize_ the values before checking for a match by default. Normalization entails a) **removal of all diacritics**: the value is decomposed into Unicode NFD form and all diacritic mark characters are discarded; and b) **case insensitivity**, which for all operators except `~=` is achieved by converting the value to lowercase using invariant culture rules. The regex matching operator `~=` is the exception to (b): case-folding a regular expression would silently rewrite it, so `~=` leaves the case of both operands alone and performs the match itself case-insensitively instead (see below). For example, `artist == "motorhead"` would match when the artist is recorded as "Motörhead", despite the difference in casing and diacritics. This normalization can be disabled on a per-case basis by using the `LITERALLY()` function (see below).

**4.2 — replace the body of "Regular expression match operator" (`:111`–`:115`):**

> String values can be tested to see if they match a regular expression with the regex matching operator `~=`. The left operand is the value being tested and the right operand is the regular expression. **Both operands must be of type string**, and it is an error if either is not; the polymorphic numeric literal rule (general operator rule 3) does not apply to this operator. Regular expressions are [.NET-flavored](https://learn.microsoft.com/en-us/dotnet/standard/base-types/regular-expressions).
>
> The regex matching operator will match if any substring of the tested value matches the regular expression, so if more exact matching is intended the anchors `^` and/or `$` have to be specified.
>
> Both operands are normalized by default, but this operator handles the case-insensitivity half of normalization differently from every other operator: rather than converting the operands to lowercase, which would silently rewrite the pattern (`\W` would become `\w`, `[A-Z]` would become `[a-z]`, and so on), only diacritic removal is applied to the operands and the match itself is performed case-insensitively using invariant culture rules. Two consequences follow: a pattern cannot express a case-sensitive condition, and a pattern cannot match a diacritic, unless `LITERALLY()` is used to suppress normalization.
>
> If the pattern operand is a string literal, it is validated when the predicate is read, and an invalid pattern is reported as an error before any file is processed. If the pattern operand is not a literal — for example, it comes from a tag — it cannot be validated in advance; if it turns out not to be a valid regular expression when it is evaluated, the operator evaluates to false and a warning is emitted, following the same policy as warnings for tainted null values. A match that exceeds the fixed matching timeout is treated the same way.
>
> If either operand is a multivalue, matching follows the ordinary quantifier and nested iteration rules described under [Multivalues](#multivalues); each individual pattern of a multivalue pattern operand is validated independently.
>
> There is no negated version of this operator; to determine if a value does not match a regular expression, apply `NOT` to the result of matching it.
>
> **IMPORTANT** Note that an invalid pattern making the operator evaluate to false has the same consequence under negation as a null operand does: `NOT (artist ~= sometag)` evaluates to _true_ when `sometag` is not a valid regular expression, so a file can be selected on the strength of a failed match. The warning is what surfaces this; see the discussion of `!=` versus `NOT ==` above for the same underlying phenomenon.
>
> Example: `artist ~= "s$"` matches any artist whose name ends in "s" or "S"

**4.3 — fix the now-inaccurate `LITERALLY` example at `:263`:**

> - `artist ~= "^met"` matches "Metallica" because diacritics are removed from both operands and the match is performed case-insensitively.

**4.4 — append to the `LITERALLY()` description:**

> When applied to either operand of `~=`, this function additionally makes the match case-sensitive, since for that operator case insensitivity is part of normalization rather than of the match itself.

## 6. `ISNULL()` on a multivalue

I don't think "obviously false" survives contact with the function's own stated purpose. Take the sanctioned guard from `:196` and give it multivalued data — `id3v2::raw::TXXX` with values `"12"` and `"oops"`:

```
NOT ISNULL(NUMBER(id3v2::raw::TXXX)) AND NUMBER(id3v2::raw::TXXX) > 5
```

`NUMBER()` maps element-wise, so the argument to `ISNULL()` is a multivalue of `12` and a tainted null. If `ISNULL(multivalue)` is false, then `NOT ISNULL(...)` is true, the guard passes, the right-hand operand is evaluated, the tainted null is used, **and the warning fires anyway**. The guard cannot suppress anything the moment the data is multivalued — and almost every tag identifier can be multivalued, so the sanctioned construct works only in the special case.

There's a second problem: it conflicts with your own item-7 invariant. Under "a simple value is a multivalue of cardinality 1", a multivalue whose single value is null *is* a simple null, so `ISNULL` of it must be true — but "a multivalue clearly does not evaluate to null" says false.

Two ways to close it:

- **(A) Element-wise, existential by default, like everything else.** `ISNULL(expr)` is true if `expr` is null or if any of its values is null. In the example above that gives true, the guard blocks, no warning. At cardinality 1 it degenerates exactly to the current wording, so the invariant holds. `NOT ISNULL(genre)` then reads "every genre value is usable", which is what a guard should mean. **I'd recommend this.**
- **(B) `ISNULL()` returns a boolean multivalue** and the enclosing operator's quantifier resolves it. Most uniform in principle, but it requires boolean multivalues, quantifiers over `NOT`/`AND`/`OR`, and a spelling for `ALL(ISNULL(x))`. Much bigger change for little practical gain.

Either way the function entry should say what it does with a multivalue explicitly, since every other function does.

## 7. Multivalues: bags, nulls, and cardinality 1

Your invariant is a good one and I'd write it into the spec as normative rather than leave it as a mental model — it's the thing that will keep future edits honest. Then it immediately pays for itself, because the current text violates it in one place.

**7.1 — add to the top of the Multivalues section:**

> **Design invariant.** Every value in a predicate is conceptually a _bag_: an unordered collection in which the same value may appear more than once and duplicates are significant. A "simple" value is a bag of cardinality one, and everything stated in this document about simple values holds unchanged for multivalues of cardinality one. No construct in the language is able to distinguish the two, and any proposed addition that could is for that reason alone the wrong design.

**7.2 — the definition at `:77` contradicts it** ("multivalues represent the simultaneous existence of **more than one** value"). Replace the opening clause with:

> multivalues represent the simultaneous existence of several values where a single value might otherwise be expected.

**7.3 — replace "unordered list" at `:148`:**

> an identifier logically corresponds to a _bag_ of values instead of a single one: an unordered collection whose values are not deduplicated, so the same value occurring twice in the underlying tags occurs twice in the multivalue.

**7.4 — nulls under quantifiers; append to the nested-iteration paragraph (`:152`):**

> A null among a multivalue's values participates in this iteration like any other value, with general operator rule 1 applying to it: every combination that includes it makes the operator false for that combination. Under the default existential quantifier a null value therefore simply fails to contribute a match, whereas under `ALL()` a single null value is enough to make the operator false overall. For example, if `genre` is a multivalue of `"rock"` and null, `genre == "rock"` is true while `ALL(genre) == "rock"` is false. Note also that universal quantification over a value that has no values at all is **false**, not vacuously true, so that rule 1 continues to hold.

That last sentence matters: in ordinary logic `ALL(x)` over an empty collection is vacuously true, which would contradict rule 1.

**7.5 — the one real violation: `COUNT()`.** Combining your three statements — nulls count as items for `COUNT()`, a simple value is a bag of one, and `COUNT(expr)` is `0` if `expr` is null — gives a contradiction at cardinality 1: a bag containing one null is `1` by the first rule and `0` by the third, and the invariant says they're the same thing. The root cause is that `null` is currently doing two different jobs: *"there is nothing here"* (an empty bag) and *"there is something here but it cannot be interpreted"* (an element of a bag). Those coincide only in the simple case, which is why the invariant flushes it out. Two ways out:

- **(A) `null` means absence, i.e. the empty bag, and a bag never contains null.** A failed conversion removes the value and records the taint, so `NUMBER({"12","oops"})` is a bag of one value (`12`) carrying a taint, and `NUMBER({"oops"})` is the empty bag, which *is* null. `COUNT()` becomes simply "the cardinality", the invariant holds exactly, and `ISNULL()` becomes "the bag is empty" — which also happens to give option 6(A) a cleaner footing. Cost: `:148`'s "it is even possible for _all_ values inside a multivalue to be null" goes away (that case is just null), and `COUNT()` can no longer tell you how many values were dropped, though the taint warning still surfaces that they were.
- **(B) Keep null as a value that can sit inside a bag, and make absence a distinct empty bag of cardinality 0.** `COUNT()` is the cardinality, `0` for absent and `1` for a bag holding one null. Cost: the spec now has two kinds of nothing to explain, and `COUNT(expr) == 0` no longer implies `ISNULL(expr)`.

**I'd recommend (A)** — it collapses the two nothings into one and is the only one of the two where the invariant needs no caveats.

**7.6 — under (A), replace the `COUNT()` entry:**

> **COUNT(expr)**
> : returns the number of values `expr` has, as a number. This is `0` if `expr` is null, `1` if `expr` is a single value, and otherwise the number of individual values in the multivalue. Values that occur more than once are counted once per occurrence. This is the only function whose result is not computed per value: it collapses a multivalue to a single number rather than returning a multivalue.
>

## 6 — proposed edits

**6.1 — replace the `ISNULL()` entry:**

> **ISNULL(expr)**
> : returns true if `expr` has no usable value, or false otherwise. Specifically, this function returns true if `expr` evaluates to null, and also if `expr` is a multivalue and any one of its values is null. It returns false only when `expr` is a single non-null value, or a multivalue none of whose values is null.
>
> Unlike most functions, `ISNULL()` does not apply to each value of a multivalue individually: it examines the multivalue as a whole and always returns a single boolean.
>
> Treating a multivalue with even one null value as null is deliberately conservative, and it is what allows the guard below to keep working on multivalued data: `NOT ISNULL(expr)` means "every value of `expr` is usable", which is exactly the precondition for going on to use `expr` without risking a warning.
>
> This function _does not trigger a taint warning even if its argument is a tainted null value_, or contains one. Therefore, it is the sanctioned way (through its negation, `NOT ISNULL()`) of checking the validity of a conversion with `NUMBER()` without potentially emitting a warning.
>
> Examples:
>
> - `ISNULL(genre)` is true when the file has no genre tag at all
> - `ISNULL(NUMBER(id3v2::raw::TXXX))` is true when the frame is absent, and also when the frame is present more than once and at least one of the occurrences does not hold a valid number
> - `NOT ISNULL(NUMBER(x)) AND NUMBER(x) > 5` is safe: because `AND` short-circuits, the right operand is only evaluated when every value of `x` converted successfully

**6.2 — add a Q&A entry to `rationale.md`,** since this is exactly the kind of non-obvious choice that section exists for:

> Q: **Why does `ISNULL()` return true for a multivalue that merely contains a null, rather than only for a plain null?**
> A: Because `ISNULL()`'s job is to be the safe guard in front of a value whose usability is not guaranteed, and almost every tag identifier can turn out to be multivalued. If a multivalue were never considered null, then `NOT ISNULL(NUMBER(x))` would pass for a multivalue holding one good value and one tainted null, the guarded expression would then use the tainted null, and the warning the guard was meant to avoid would fire anyway — the guard would only ever work on data that happened not to be multivalued. Reading `NOT ISNULL(expr)` as "every value of `expr` is usable" is the conservative choice, and conservative is the right default when the consequence of being wrong is silently skipping files.

## 4 — the timeout now returning a tainted null

Yes, this needs updates, and more of them than it looks. The change quietly promotes `~=` into the only operator that can produce something other than a boolean, and three things now contradict it:

1. **General operator rule 1 is now false.** Its last sentence reads "This rule does not concern the logical operators `AND`, `OR`, and `NOT`, whose operands are always boolean and therefore never null." With the new text, `NOT (artist ~= pat)` can have a null operand. Nothing says what `NOT null`, `null AND x`, or `x OR null` do.
2. **"Folded to boolean false" isn't written down anywhere.** You said it in your question, and it's the right rule, but the spec never states that a predicate evaluating to null puts the file out of scope.
3. **The same operator now has two different failure results.** Invalid pattern → false + warning; timeout → tainted null. Under negation they'd behave differently, and nothing explains why one is worse than the other.

There are also two consequences worth knowing about before you choose:

- **This particular tainted null cannot be guarded.** Booleans can't be function arguments (the rule you adopted as 5.1), so `ISNULL(x ~= pat)` and `FALLBACK(x ~= pat, ...)` are both errors. Every other tainted null has a suppression path; this one doesn't, so its warning always fires. Arguably correct — a timeout *should* always be loud — but it's a departure from the taint model rather than a use of it.
- **Under multivalues, a timeout produces a null *result* rather than a null *input*.** Rule 1 covers null inputs. Nothing says what a null result of one inner iteration contributes to existential or universal aggregation.

### Recommendation: collapse the two failure modes

Since the tainted null can't be inspected, guarded, or propagated anywhere useful, it buys nothing over plain false-plus-warning — and it costs you a three-valued logic you otherwise don't have. I'd make the timeout behave exactly like an invalid pattern:

> Regular expression matching is always subject to an implementation-defined timeout, applied to each individual match attempt. If no result is available within the allowed time limit, the operator evaluates to false and a warning is emitted, exactly as for an invalid pattern. Note that this makes the result of a predicate containing `~=` dependent on the machine it runs on and on system load; the warning is what surfaces that this has happened.

That requires **no changes anywhere else** — rule 1 stays true, no folding rule is needed, and the `IMPORTANT` paragraph about negation already covers the resulting footgun (extend its first clause to "an invalid pattern or a timed-out match making the operator evaluate to false…").

### If you'd rather keep the tainted null

Then four edits become necessary:

- **B1**, rule 1's last sentence: "This rule does not concern the logical operators `AND`, `OR`, and `NOT`. Their operands are boolean, with one exception: a regex match that times out yields a null result, and such a null is folded to false before the logical operator sees it. This folding counts as a use of the value for the purpose of tainted null warnings."
- **B2**, in the Overview after the boolean-predicate sentence: "If the predicate as a whole evaluates to null rather than to a boolean, the file is out of scope, exactly as if the predicate had evaluated to false."
- **B3**, in the Multivalues nested-iteration rules: a sentence on what a null *result* of an inner evaluation contributes to existential and universal aggregation.
- **B4**, in the `~=` section: a note that this tainted null cannot be guarded with `ISNULL()` or `FALLBACK()`, because a boolean-position value cannot be a function argument, so the warning is unavoidable by design.

And you'd still want to decide whether the invalid-pattern case should become a tainted null too, for consistency within the one operator.

Either way, worth pinning down whether the timeout is **per match attempt** (my wording above) or per predicate evaluation per file — with nested iteration over two multivalues, one `~=` can mean dozens of match attempts.

**8.1 — replace the warning sentence in "Value conversions and warnings" with a subsection:**

## 12b — the lookahead question

**Short answer: you don't need the lookahead hack, and you don't need the shadowing rule for parsing. But keep the shadowing rule anyway, for reasons that have nothing to do with parsing.**

### Why the lookahead isn't a real problem

The trap is thinking the *lexer* has to decide whether `all` is a function name. If it does, it has to peek past the token — and because whitespace is insignificant in your grammar it has to skip whitespace while peeking, so it isn't one character of lookahead, it's unbounded. That's the version that feels dirty, and it is.

Don't do that. Have the lexer emit a single `IDENT` token for every identifier-shaped thing and stay completely ignorant of what names mean. Then the *parser*, when it parses a primary expression, does:

```
parsePrimary():
    if current is IDENT:
        name = consume()
        if current is LPAREN:        // one token of lookahead
            return parseCall(name)
        return parseIdentifierRef(name)
```

That's ordinary LL(1) — one token of lookahead, which every recursive-descent parser already has sitting in a field because it needs it everywhere else anyway. Whitespace is a non-issue because the lexer discarded it before producing the `LPAREN`. There is no ambiguity in the grammar and no cost at runtime. This is the boring, standard shape and it's what I'd write.

Concretely I'd suggest: a hand-written lexer, and a **precedence-climbing (Pratt) parser** for expressions. With five levels, a prefix `NOT`, and non-associative comparisons, that's on the order of 150 lines, and non-associativity comes almost free — at the comparison level you parse one operand, parse the operator, parse the other operand, and then simply *don't loop*; if another comparison operator is sitting there you raise "comparison operators cannot be chained; combine them with AND" instead of a generic parse error. That specific error message is worth more to a user than the entire precedence table.

One more structural suggestion: resolve identifiers against the built-in table in a **separate pass after parsing**, not in the lexer or parser. Then "unknown identifier `artsit`" is a semantic error that can carry a did-you-mean suggestion, rather than a parse failure pointing at a column number.

### So do you need the no-shadowing rule?

Not for the grammar. Keep it anyway, for three reasons:

1. **It protects against a silent wrong answer, not a parse failure.** Today `count` isn't a defined identifier, so `count > 1` is a clean "unknown identifier" error. If a built-in identifier named `count` were ever added, that same expression would silently compare a tag value where the author meant `COUNT(...)`. Parse ambiguity was never the risk; quiet misinterpretation is.
2. **It's insurance against grammar evolution.** The one-token property holds only while nothing else can follow an identifier and change its meaning. Add indexing (`artist[0]`), a postfix operator, or parenthesis-free zero-argument calls later and the clean split erodes. The rule costs nothing now.
3. **Readability.** `ALL` as a bare identifier sitting next to `ALL(...)` as a quantifier in the same expression is confusing to a human even when the parser is content.

And note you already have the escape hatch you'd need if you ever wanted to break the rule: a *qualified* name can never be a call, so `::count` is unambiguous no matter what functions exist — the same trick the reserved words already use.

**12b.1 — add to the Functions section:**

> A function call is an **unqualified** name followed by an opening parenthesis. A namespaced name is never a function call, since functions do not live in namespaces: `foo::count(x)` is a syntax error. This is what lets a name be usable both as a function name and, in principle, as an identifier — `count` alone is an identifier reference, while `count(...)` is a call — and it means the qualified form `::count` always and unambiguously refers to the identifier.

**12b.2 — add alongside the reserved words section:**

> Although the grammar does not require it, no built-in identifier in the global namespace has the same name as a function, and no function is given the name of a built-in global identifier. This is a constraint on what Goro defines rather than on what a predicate may write.

### The lexing trap you haven't hit yet

While we're here: **`1..100` is lexically ambiguous under the current number grammar.** A number literal may have an optional integer part and an optional fractional part separated by a period (`-.55` is given as valid), so a naive maximal-munch lexer reading `1..100` consumes `1.` as a number, then `.100` as another number, and the range operator never appears. Worse, it's the kind of bug that produces a baffling error message rather than an obvious one.

The fix is a one-line lexer rule, and it should be in the spec because it's invisible to the author and load-bearing for the implementer:

> A period is part of a number literal only when it is immediately followed by a digit. This is what allows the range operator to be recognized in literals such as `1..100`, which is a range from `1` to `100` and not two numbers written next to each other.

With that rule: `1..100` → `1` `..` `100`; `1.5..2` → `1.5` `..` `2`; `-.55` → `-` `.55`. All three lex correctly, and `1.` alone becomes invalid, which it should be anyway.

## The simplification: this is structural equality on the AST, so compute it at parse time

A source tree as you've defined it — symbol id plus argument sources, recursively — **is the abstract syntax tree of the sub-expression that produced the value**, with positions erased. Your set-equality rule is structural equality on that tree. Which means the set of distinct sources a predicate can ever produce is fully determined by the predicate's own AST, and you already have that before you touch a single file.

So instead of building and comparing graphs at runtime:

- At parse time, walk the AST and hash-cons it: assign each distinct-modulo-position sub-expression a small integer *source id*. Structurally identical subtrees get the same id by construction.
- A taint then carries one `int`.
- The already-warned set becomes a `bool[]` or bitset sized to the number of source ids, reset per file. The dedup check is a bit test.

The recursive comparison you were worried about happens once, at parse time, over an AST with a handful of nodes.

I want to be straight about the cost argument though: your instinct that you'd have to try hard to make the runtime version hurt is correct. Sources are only allocated for values that are actually tainted, so on a clean collection the graph version costs nothing, and on a collection with 500 bad files it costs 500 small allocations. Performance is not the reason to prefer static ids. The reasons are:

1. **The spec becomes one sentence** instead of a description of a self-referential data structure. That matters for a document meant to be read by users.
2. **No recursive equality or hashing to get right**, no questions about source-graph lifetime or sharing, and a dedup key you can print in a debugger.
3. **You can enumerate every warning a predicate is capable of emitting, before running it.** That's directly testable — a unit test asserts "this predicate has exactly 3 warning sources" — and it opens the door to explaining a predicate without executing it.

## Two things to pin down

> A function that returns null when given a tainted null is **propagating** it, and propagation never emits a warning. ## Transparency and faithful rendering

These don't actually conflict, because they're answers to two different questions, and the spec already separates them without quite saying so:

- **The source answers "have I warned about this already?"** It's an identity, position-independent, and annotations must be transparent in it.
- **The node that produced the value answers "what do I print?"** It's a provenance, tied to one specific place in the predicate text.

Conflating the two is what makes it look like a dilemma. Keep them as separate fields on the taint and the tension disappears: a taint carries a reference to the AST node it was born at, and each node carries (a) its interned source id and (b) the character span of the text it was parsed from. The dedup check reads `bitset[node.SourceId]`; the message quotes `predicateText[node.Span]`. Both are precomputed at parse time, and the span is only ever dereferenced when a warning actually fires, so it costs nothing in the common case.

Quoting the original span rather than pretty-printing a reconstructed AST is also what makes the rendering genuinely faithful — the user gets their own text back, whitespace and casing intact.

### Why this is simpler than it looks: the top-level case needs no rule at all

`ALL()`, `ANY()` and `LITERALLY()` can never *birth* a taint. They don't convert anything; they return their argument, or null for null. So an annotation node is never the source of a taint.

That means in `ALL(m) == "a"`, the taint is born at `m`, `ALL()` propagates it without changing its source — which is already required by the "born once, propagation doesn't re-taint" rule in the spec — and the warning quotes `m`. The other branch's `m == "b"` produces a taint with the identical source and quotes `m` too. Same identity, same text, one warning, nothing ambiguous. **Transparency at the top of a source is automatic; it's just propagation.**

The transparency rule only earns its keep in the other position: an annotation sitting *inside* the arguments of a function that does birth taints.

```
NUMBER(LITERALLY(s)) > 1 OR NUMBER(s) > 2
```

Here the taints are born at the two `NUMBER` nodes. Their source keys are `(NUMBER, id(LITERALLY(s)))` and `(NUMBER, id(s))`, so transparency is what makes those equal — and it's one line during interning: an annotation node forwards its child's id as its own instead of allocating a new one. `id(LITERALLY(s)) == id(s)`, so the two keys coincide and only one warning fires. That single line also delivers the top-level case for free.

The rendering then differs between the two branches, and it should: the warning quotes whichever fragment actually produced the bad value on this file. That's honest rather than awkward — it names the machinery that failed, at the place it failed.

### One consequence for the spec text

The sentence I wrote, "a warning does not name a position within the predicate", was justified by the assumption that identity was all you had. With node-level provenance you *could* print an offset — but you shouldn't, and for a better reason: in `x > x` both occurrences are equally responsible, dedup reports one, and naming column 1 while column 5 is just as guilty is worse than naming neither. Same conclusion, different and stronger reasoning. I'd tighten it to:

> Each warning names the file being processed and quotes the sub-expression responsible, exactly as it was written in the predicate. Where the same source occurs in more than one place, the quoted text is that of the occurrence which actually produced the value. Because deduplication means only one of several equally responsible occurrences is reported, a warning deliberately does not name a position within the predicate.

## The invariant that makes "allow them anywhere" safe

Your FOMO has a precise answer, and it hinges on one property the spec already has: **normalization is applied at comparison time, not when a value is produced.** Rule 4 says operators normalize "before checking for a match".

As long as that holds, any function that merely *inspects* a value always sees the raw string, so the normalization bit cannot change what it computes. `LEN(LITERALLY(x))` and `LEN(x)` must agree, because both see the raw string and the bit only matters later. The same for `SUBSTR`, `INDEXOF`-as-position, anything structural.

Which means: **`FUNC(LITERALLY(arg))` can differ from `FUNC(arg)` only when `FUNC` itself does string matching internally.** And in exactly those cases you *want* the difference:

- `REPLACE(x, "ö", "o")` — replace case- and diacritic-insensitively, or exactly? That's a real question, and `LITERALLY()` is the natural answer to it.
- a future function-form matcher, or `INDEXOF(x, sub)` — same.

So the restriction doesn't protect you from a hazard; it forecloses the one part of the design space where the bit would genuinely be useful inside a function. If you later wanted `REPLACE` to be able to match exactly, under the restriction you'd have to invent a second mechanism — a flag argument, or a `REPLACELITERAL` — to say what `LITERALLY()` already says.

## Two things the flags model gets for free

**`ISNULL(ALL(x))` becomes meaningful.** We defined `ISNULL()` as true when *any* value is null. Under the flags model that isn't a special rule at all — it's the default existential quantifier doing its job, and `ISNULL(ALL(x))` naturally reads "every value is unusable", which is a genuinely different and useful question. The restriction makes it an error with no way to express it, and leaves `ISNULL`'s existential behaviour looking like an arbitrary carve-out rather than an instance of the general rule.

**Warning-source transparency stops being an exception.** We decided annotations must not contribute to source identity. ## On the parser question

Static, entirely — and under the restrictive rule it gets easier than it would have been.

Because `operand` is a grammar production, the parser sees a modifier chain structurally; it never has to guess. When it reduces an `operand`, it collapses the chain into two attributes and attaches them to the operand slot of the comparison node: a quantifier (existential or universal) and a normalization flag. Stacking resolves here too — `ALL(ANY(genre))` becomes one quantifier value, not a nested structure — so the tree holds no modifier nodes at all. That's also why modifiers are automatically transparent for warning sources: there's nothing left in the tree to intern.

The comparison node therefore carries the two flags per operand, and the "one `LITERALLY` suffices for the whole comparison" rule collapses at analysis time into a single boolean on the node rather than something checked per evaluation.

Two things that buys at runtime, both of which matter at 100K files:

- **Values carry nothing.** No flag bits on values, no plumbing through function results, no allocation. The evaluator reads fields on the node it's already executing.
- **Normalization of the constant side happens once.** `artist == "metallica"` can have the literal normalized when the predicate is read, not a hundred thousand times. Same for `~=`: the regex can be compiled once with the right options — `IgnoreCase | CultureInvariant` or not — decided from the flag at analysis time.

A dynamic approach would mean every value carrying flags that are read at every comparison, which costs allocation and indirection to express something that cannot vary between files. The flags-on-values idea is the right way to *specify* the semantics and the wrong way to implement them.

## The asymmetry is worse than `==` — it breaks mirror equivalence

Commutativity of `==` is the visible casualty, but lexical order also breaks the identity `x < y ⟺ y > x`, for every ordering operator:

- `a < ALL(b)` → ∃x∈a ∀y∈b : x<y
- `ALL(b) > a` → ∀y∈b ∃x∈a : y>x

Those are different propositions. And flipping `<` to `>` while swapping operands is a rewrite people perform unconsciously, without even registering it as a transformation — unlike moving an `ALL()` from one side of `==` to the other, which at least looks like you changed something. So lexical order's sharpest edge isn't the one that's been discussed; it's the one that hides in a rewrite nobody thinks twice about.

Universal-first preserves it: both forms become ∀y∈b ∃x∈a : x<y. In fact it gives you a much stronger and simpler headline than "equality stays symmetric" — **operand order never affects the result of any operator.** With both operands universal it's ∀∀, with neither it's ∃∃, with exactly one the universal is outermost; order is irrelevant in all three cases. That one sentence replaces the current subsection plus its "take particular care" paragraph, and the fact that the present rule needs such a paragraph is itself a signal.

## The expressiveness you lose is worthless for `==` and misshapen for `<`

The ∃∀ prefix that only lexical order can express is "some item of X relates to all items of Y". Look at what that means per operator:

- For `==`: ∃x∈a ∀y∈b : x==y is true only if every value of `b` is the *same* value and that value appears in `a`. That's the degenerate case the spec already dismisses in the `ALL(a) == ALL(b)` note. Nobody wants it.
- For `<` and `>`: it's genuinely meaningful — `a > ALL(b)` is "max(a) > max(b)". But that's a comparison of *aggregates*, and a future `MAX()`/`MIN()` would express it far more legibly as `MAX(a) > MAX(b)`. Reading `a > ALL(b)` as a statement about maxima requires a chain of inference; the aggregate form states it.

Meanwhile the ∀∃ reading that universal-first keeps has a clean name: `ALL(a) == b` is **subset containment** — every value of `a` appears among the values of `b`. That's a nameable, useful operation, and under universal-first you cannot accidentally invert it by writing the operands the other way round.

So the exchange isn't "expressiveness for symmetry". It's a degenerate reading plus an awkward spelling of `MAX`, traded for order-independence across the whole operator set.

## It's the reversible direction, again

Same asymmetry that settled the modifier question. Adopt universal-first now and later decide you want ∃∀: you add something — aggregate functions, or an explicit quantifier-prefix form — and no existing predicate changes meaning. Adopt lexical order now and later want order-independence: you change what already-written predicates mean.

Given that the ∃∀ cases have a better future spelling anyway, universal-first costs you nothing you can't get back, and lexical order costs you something you can't.

## How ID3v2 handles genre

The representation changed twice, and all three forms are still in circulation.

**ID3v1** stored genre as a single byte indexing a table — 80 entries in the original spec, extended by Winamp to 147. So the genre was always a number, never text.

**ID3v2.2 (`TCO`) and v2.3 (`TCON`)** made it a string, but kept backward compatibility by letting you *reference* the ID3v1 table in parentheses:

- `(17)` — reference alone
- `(17)Rock` — reference plus a free-text "refinement"
- `(51)(39)` — several references concatenated
- `(RX)` and `(CR)` — reserved for Remix and Cover
- `((I made this up)` — a literal leading parenthesis is escaped by doubling

**ID3v2.4** dropped the parenthesised syntax entirely. You write the number as a plain string (`17`), or free text (`Rock`), and multiple genres use the null separator that v2.4 gives every text frame. `RX` and `CR` survive without parentheses.

## What TagLibSharp does with it

Its genre table has **148 entries** — the 80 official plus Winamp's extension, ending Anime/Jpop/Synthpop. Out-of-range indices expand to an empty string.

`Tag.Genres` already does the expansion, and does it better than I assumed when I filed that deferred item:

| On disk | `Genres` yields |
|---|---|
| `Rock` | Rock |
| `17` | Rock |
| `(17)` | Rock |
| `(17)Rock` | Rock |
| `(51)(39)` | Techno-Industrial, Noise |
| `(130)` | Terror |
| `Not A Genre` | Not A Genre |

Two gaps: `(RX)` is **not** expanded to "Remix" and comes back inconsistently (`RX` on v2.3, `(RX)` on v2.4); and `(17)Progressive Rock` discards the refinement, keeping only "Rock" — which throws away the more specific information.

## What you see in the wild

Roughly in descending order of frequency: free text (`Rock`, `Progressive Metal`) dominates modern files; several genres crammed into one delimited string (`Rock; Metal`, `Rock/Metal`, `Rock, Metal`) is common and spec-sanctioned nowhere; bare numeric strings in v2.3 tags, which is really the v2.4 form written into the wrong revision; `(17)` and `(17)Refinement` from Winamp-era taggers; Winamp-extension indices in the 80–147 range; properly null-separated v2.4 multi-values, which are correct but rarer than the delimited-string hack; and occasional `(RX)`/`(CR)`.

## The argument for going direct

If the destination is owning the parse, the intermediate version is throwaway work. A parser written against TagLib's output has to handle v2.3 input that is *already* tokenised and paren-stripped (`17`, `Post-Rock`) and v2.4 input that is verbatim (`(17)Post-Rock`). Once we read bytes ourselves, both become verbatim and that asymmetry — the entire reason the parser was complicated — disappears. So writing it twice buys nothing.

**And there's an immediate win that costs nothing: it simplifies the spec we're writing right now.** If we own the parse, `identifiers.md` can state version-independent semantics today, and those statements stay true when the parser lands. If we specify TagLib's current behaviour, we document per-version quirks now and rewrite them later. So the genre question can be closed on paper immediately, with the implementation following whenever.

## Where the cost actually is

Not the genre grammar — that's a day. It's byte-level frame extraction, and it's the part where TagLibSharp is carrying a decade of real-world hardening:

- **Unsynchronisation**: tag-level in v2.2/v2.3, per-frame in v2.4. Must be undone before any frame content is read.
- **Extended headers**, structured differently in v2.3 and v2.4.
- **Frame size fields**: 3-byte big-endian in v2.2, 4-byte big-endian in v2.3, 4-byte syncsafe in v2.4 — plus the well-known population of v2.4 files whose taggers wrote plain big-endian sizes anyway, which needs heuristic tolerance or those files read as garbage.
- **Frame flags**: compression (zlib), encryption, grouping, and v2.4's data-length indicator. v2.2 has no frame flags at all.
- **Text encodings**: `0x00` ISO-8859-1, `0x01` UTF-16 with BOM, `0x02` UTF-16BE and `0x03` UTF-8 in v2.4 — and `0x03` appearing in v2.3 files in practice.
- **Terminators**: optional trailing terminator, terminator-as-separator for v2.4 multi-values, width depending on encoding.
- **Appended tags and v2.4 footers.**

This is the class of code where a subtle bug yields silently wrong query results over a whole collection rather than a crash.

## What the spec and prior art say

**Keys** are 2–255 characters from 0x20–0x7E. They are stored case-sensitively but readers are *recommended* to compare case-insensitively, and keys differing only in case are forbidden. `ID3`, `TAG`, `OggS` and `MP+` are reserved. Crucially, typical keys are expected to contain **spaces** — `Album Artist`, `Cover Art (Front)`.

**Values** are UTF-8 text, binary, or an external locator, selected by item flags. Multiple values live **inside one item**, separated by a null byte — unlike Vorbis, where the field is repeated.

**Prior art on naming:** there is no rigid standard for key names, and Mp3tag deliberately does not map APEv2 internally — it shows keys verbatim, exactly as it does for Vorbis comments, offering only user-configured mappings. Hydrogenaudio's informal key list and real-world files agree that `Year` often holds a full date (`2014-04-23`) and `Track` holds `11/12`.

## What TagLibSharp actually does, on hand-built tags

No ID3v2-style complications:

| Behaviour | Result |
|---|---|
| Keys with spaces and parentheses | Preserved verbatim |
| `GetItem("artist")` against a stored `Artist` | Found — lookup is case-insensitive, including multi-word keys |
| Null-separated multi-values | Split correctly into separate values |
| `Rock/Metal`, `Rock; Metal` | Left as single values — no separator guessing |
| `(17)Post-Rock` | Verbatim — no genre reference parsing |
| Binary item | `Type=Binary`, no text values |
| External locator | `Type=Locator`, text accessible |

Two real caveats did turn up. **Duplicate keys differing only in case** — forbidden by the spec but present in the wild — collapse silently to the last one. And **APEv1** (footer version 1000) values are ISO-8859-1 per spec but are decoded as UTF-8 regardless, so non-ASCII text mojibakes; APEv1 is rare, mostly early Monkey's Audio.

## Recommendation: option 1, reusing the string literal

```
apev2::"album artist" == "Various Artists"
id3v2::raw::"TXXX" == "x"
```

The argument that decides it for me is exactly your worry about future expansion: **this adds no new characters to the grammar.** `{ }` is the natural syntax for a set literal, and `IN (a, b)` is already in `deferred.md` — braces are the first thing you'd reach for if sets ever arrive. `[ ]` is the natural syntax for indexing, which came up earlier as a hypothetical. Backticks are free of obvious future use but are PowerShell's escape character. Reusing `"` leaves all of those untouched.

Two further things fall out for free:

- **Escaping.** A key containing a quote or backslash is handled by the existing string escape rules. With a new delimiter you'd have to invent an escape or forbid the character.
- **Coverage.** APE keys are `0x20`–`0x7E`, Vorbis field names `0x20`–`0x7D` minus `=`. A string literal expresses every legal key in both formats, so this is a complete solution rather than a wider net.

### Grammar

One production changes:

```ebnf
identifier = [ "::" ] name { "::" name_part } ;
name_part  = name | string ;
```

Note the asymmetry: a quoted component must be preceded by `::`, so the **first** component is never quoted. That keeps a leading string token unambiguously a string literal and needs no lookahead — the parser only considers a string as a name when it has already consumed a `::`. LL(1) holds, nothing else in the grammar moves.

### Three details that need stating

**Case.** The quoted form must match case-insensitively, like every other identifier and like the way APE and Vorbis lookups actually behave. That is a genuine exception to "the only case-sensitive text in a predicate is the contents of a string literal", so the Case sensitivity section needs a sentence — otherwise the two rules contradict.

**Identity.** `apev2::"artist"` and `apev2::artist` name the same item and must resolve to the same identifier, or one bad tag would warn twice under the warning-source rules. Resolution canonicalises; the quoted form is a spelling, not a distinct thing.

**Closed namespaces.** `id3v1::"artist"` resolves normally; `id3v1::"nonsense"` is an error, exactly as the unquoted form would be. No special case.

### The error message this unlocks

Someone will write `apev2::album artist` first. That's a syntax error today with nothing useful to say, and with this syntax it becomes: *an identifier cannot contain a space — write `apev2::"album artist"` to name an item whose key contains characters an identifier cannot spell.* Teaching the syntax at the exact moment of need is worth more than the aesthetics, and it's hard to get with option 2, where the error would have to propose a different construct entirely.

## Why not option 2

The minimal form would be something like `TAG(apev2, "album artist")` — namespace as a bare name so it's still statically checked, key as a literal, both required to be literals so resolution stays static and warning sources stay internable.

It's workable, and it generalises better to compound names: a future `TAG(id3v2, "TXXX", "my description")` addresses the description sub-field, which the quoted-component form would have to express as a fourth `::` component. That's a real advantage and the main thing that gave me pause.

But it costs you two spellings for one thing. `apev2::artist` and `TAG(apev2, "artist")` would both be legal and identical, which is a smell in itself and means resolution must canonicalise across two syntaxes rather than two spellings of one. And it inverts the model: naming tag data is what identifiers are *for*, and this makes the awkward cases reach for a different mechanism rather than the same one with an escape hatch. Plus the boilerplate you flagged, on every use, forever.

If the compound-name case later proves to need it, a function can be added then without disturbing anything — whereas picking it now means the common case pays for the rare one.

## What "interrupted" is

Ctrl-C, Ctrl-Break, or the console window being closed. The distinguishing feature is that the process is **terminated** rather than returning — it never reaches a point where it chooses a code.

On Unix, Ctrl-C sends SIGINT, signal 2, and the shell reports a signal-killed process as `128 + signal`, hence 130. The subtlety worth knowing: **Goro does not return 130; the shell synthesises it.** At the OS level a parent's `wait()` distinguishes "exited with status N" from "killed by signal N" — they're different bits in the status word. `$?` flattens the second form to `128+N`.

That's the answer to why it isn't in the error range: **it isn't in any range we control.** Listing it alongside our codes implies Goro picks it, and on Unix actually calling `exit(130)` would be worse than being killed, because it erases the killed-by-signal status that callers such as `make` and shell loops use to decide whether to abandon the rest of their work. The correct handling is to clean up, restore the default signal disposition, and re-raise the signal so the process genuinely dies of it.

Semantically an interruption is neither success nor malfunction — you asked for it — but non-zero is right, because you don't want `goro list && process-the-output` to carry on after you've hit Ctrl-C. And note it already falls into the failure bucket under the doc's own rule: anything non-zero below 10 means "did not produce a usable result".

**The defect:** 130 is Unix-only. ## The GNU convention

The pattern is to distinguish *"something went wrong doing the job"* from *"you asked for something malformed"*, conventionally 1 and 2 respectively. For tools that answer a question, 1 is further specialised to mean "ran fine, found nothing":

| Tool | 0 | 1 | 2 |
|---|---|---|---|
| `grep` | lines selected | none selected | error |
| `diff` | files identical | files differ | trouble |
| `ls` | fine | minor problems, e.g. an unreadable subdirectory | serious trouble, including usage |
| `cmp`, `sort` | fine | difference found | trouble |

`bash` uses 2 for builtin usage errors too. There's also the older BSD `sysexits.h` scheme — 64 `EX_USAGE`, 65 `EX_DATAERR`, 66 `EX_NOINPUT`, 70 `EX_SOFTWARE`, 74 `EX_IOERR` — which is more precise and never caught on outside BSD and sendmail.

**How our table departs:** I split on *when* — 1 means nothing was processed, 2 means work started and failed. GNU splits on *whose fault* — 1 is the generic failure, 2 is the malformed request.
