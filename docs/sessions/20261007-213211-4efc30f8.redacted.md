## The model

A datum the file records reaches a predicate by one of two routes, and the type system is the contract between them.

- **Field**: the datum as recorded, read with `source::field(...)`. It has the type the format records: **string** for text, **blob** for anything else. A field is never interpreted, so its type never changes.
- **Concept**: the datum interpreted, such as `year`, `id3v2::track` or `picture`. It has one name, one type, and a cell per source. Its type is the type of its *meaning*.

New types can then only arrive in three ways, and each one only adds:
1. a new target for `AS`;
2. a new concept, such as a future `date` that sits beside `year` rather than replacing it;
3. **promotion** of a blob concept to a richer type.

One rule closes off every other change: **a concept whose type is not blob never changes type.**

## The blob type

A blob is a datum Goro can tell is there but can't look inside yet.

| Construct                   | Blob?               | Why |
|-----------------------------|---------------------|-----|
| `IS ABSENT/USABLE/UNUSABLE` | yes                 | reads only cardinality and state
| `COUNT()`                   | yes                 | reads only cardinality
| operand of `AS`             | yes, no targets yet | targets out of blob arrive with the types they produce
| comparisons, `BETWEEN`, `=~` | no                 | these read content
| `PREFERRED()`               | no                  | it ties its arguments' types together (see below)
| `FALLBACK()`                | no                  | follows from existing rules: there is no blob constant
| `AS STRING`                 | no                  | follows from existing rules: it writes a type's canonical literal, and blob has none

Nothing ever consumes a blob, so a blob never warns.

**The promotion guarantee.** Changing an expression's type from blob to some type T keeps every valid predicate valid, with the same results and warnings, as long as the promotion:

- **(a) Keeps cardinality and every occurrence's state.** Anything that can fail when looking inside, such as decoding an image, must be a further conversion or accessor. Its failure is its own unusable occurrence, never the concept's.
- **(b) Agrees with the conversions from blob.** If `blob AS T` exists, it is what the promotion does. After promotion it becomes the identity, which `AS` already says.

`IS` and `COUNT()` read nothing but cardinality and state, so (a) covers them. (b) covers `AS`.

`PREFERRED()` is excluded for one reason: `PREFERRED(picture, id3v2::field("GEOB"))` would become a type mismatch on the day `picture` is promoted, because the field never is. Excluding it costs little, since `NOT (a IS ABSENT) OR …` still asks whether any of several exists. It does cost one irregularity: a plain blob concept is "chosen as `PREFERRED()` chooses", not "the value of a call you can write".

## Field types per source

- **`vorbis::field()`** is always a string, because Vorbis comments are text by definition. `METADATA_BLOCK_PICTURE` is base64 text and stays text as a field; it is the Vorbis cell of the `picture` concept that decodes it.
- **`id3v2::field()`** is typed by its frame identifier, which is a literal argument, so the type still never depends on the file:
  - string for `T…` frames (`TXXX` included), `W…` frames (`WXXX` included), `COMM` and `USLT`;
  - blob for every other frame: `APIC`, `POPM`, `PRIV`, `UFID`, `GEOB`, `PCNT`, and frames Goro doesn't know.

  This replaces the brief's leaning towards rejecting `id3v2::field("APIC")`. Existence and count then work the same way for every frame, including ones Goro will never interpret, with no concept needed per frame.
- **`ape::field()`** is a string. APE keys carry no type a predicate can know, and a binary flag is only seen once the file is read, so a binary item is an unusable occurrence. That fits the single meaning of "unusable": the predicate asked for text, and the data is there but isn't text. A concept `ape::picture` reading `Cover Art (Front)` covers the reverse case: a text item there is unusable.
- **`id3v1` and `file`** have no `field()`, as the brief already leans.

## A test for typing concepts

The information-loss problem you describe comes from a concept whose name promises more than its type holds. The test I'd use: **a concept's type must hold everything its name promises, and where no type does yet, the concept is a blob.**

- **`year` as a number passes.** A year is a number. A full date would be a separate `date` concept.
- **`comment` as a string passes.** The description and language of a `COMM` frame are how a frame is addressed, not its content, and `field()` reaches them through its arguments.
- **A `cover` concept over all `APIC` frames fails, and type isn't the only reason.** `APIC` frames also hold artist photos and back covers, so narrowing `cover` to front covers later would change its cardinality, which promotion forbids. The concept should be `picture`, a blob covering every attached picture; picking out which kind of picture waits for the promoted type.
- **`rating` from `POPM` as a number fails.** The rating is stored per email address, players use different scales, and the frame also holds a play counter. Better to define nothing yet; `id3v2::field("POPM")` already answers whether one exists.

## What this settles and what's open

This settles the brief's question about data that is not text, and with it all of non-text-tag-data. "Unusable" keeps one meaning, and the current trick of reading cover art as an unusable string goes away. I'd propose this line absorbs that one.

For you to decide:
1. **Blobs in `PREFERRED()`:** keep them out, as I recommend, or allow them and weaken the guarantee so it applies only between concepts.
2. **The type's name:** `blob` works. `opaque` names the property rather than how it's stored, which fits better given that the Vorbis picture is text on disk. The name will appear in error messages.
3. **An APE binary item read through `ape::field()`:** an unusable string, as I recommend, or absent.
4. **Where conditions (a) and (b) live:** they are rules for future type design, so I'd put them in the rationale beside the type, not in the spec. Does that suit you?

Frame addressing, trimming, and the function's name are unaffected and still open.

## The flaw: a type that converts can't be promoted freely

Under guarantee (b), every conversion out of blob has to survive every later promotion. Suppose `blob AS STRING("iso-8859-1")` exists. Then once `picture` is promoted to a picture type, that type must still decode "its bytes" as text, giving the same result. Each conversion added to blob becomes a rule every future type has to obey. That is the commit-now, regret-later problem again, just moved one level down.

The fix is to notice that "blob" was doing two jobs, the same split as fields versus concepts:

| Type     | Holds | Accepted by | Changes type? |
|----------|-------|-------------|---------------|
| `opaque` | a concept whose type is not decided yet | `IS`, `COUNT()` | yes, promoted once to its real type
| `blob`   | recorded bytes: what a non-text field is | `IS`, `COUNT()`, and `AS` with the targets it has | never

- **Promotion becomes trivial.** An opaque value has no conversions, so (b) has nothing to cover, and (a) is all that's left.
- **Blob can grow freely.** A blob is never promoted, so it can gain conversions, equality, or a length whenever we like.
- **The name `blob` keeps its SQL meaning**, a binary large object. That's why I'd give the placeholder a different name.

## The principle: the accessor chooses the type

**What kind of item the file holds never decides a type. It only decides whether an occurrence is usable in the view the predicate asked for.**

- **The text view is partial:** a binary item is unusable there.
- **The byte view is total:** every item has bytes, text items included.

So the byte view comes first and the text view is derived from it. That rules out `ape::field(k) AS BLOB`: by the time the string exists, a binary item is already an unusable occurrence, and `AS` can't get back what it never had.

## Syntax for reading an APE item as bytes

| Option | Example | Verdict |
|--------|---------|---------|
| Separate function | `ape::bytes("Cover Art (Front)")` | **Recommended.** Its result type is fixed by its name, as `field()`'s is.
| View argument | `ape::field("Cover Art (Front)", BLOB)` | Works, but puts a type name in a value position. That's `AS` again, spelled inside a call.
| Conversion | `ape::field(k) AS BLOB` | Impossible, as explained above.
| Nested view | `ape::raw::field(k)` | Brings back the nested namespaces this line removes.

`ape::bytes()` returns the item's value bytes whatever its flag says, so a text item yields its UTF-8 encoding. It also fixes a caveat already in the docs: values in an older APE tag written as ISO-8859-1 can be read correctly with `ape::bytes("Artist") AS STRING("iso-8859-1")`.

`id3v2::field("APIC")` and the other non-text frames would be typed `blob`, meaning the frame body as recorded. Whether TagLibSharp can give that back byte for byte belongs in the probe the brief already plans.

## Parameterised conversion targets

| Spelling | Example | Notes |
|----------|---------|-------|
| Literal parameters | `AS STRING("iso-8859-3")` | **Recommended.** No new token; parameters are literals like `field()`'s, so an unknown encoding is an error when the predicate is read, with a suggestion.
| Bare names | `AS STRING(latin1)`, `AS IMAGE(png)` | Reads well, but standard encoding labels contain hyphens and won't lex as names. Fine as an extra form beside strings, but not on its own.
| Keyword | `AS STRING USING "latin1"` | SQL's `CONVERT … USING`; a new reserved word for one use.
| Function | `DECODE(x, "latin1")` | Undoes what the as-operator line just settled.

Grammar: `target = name [ "(" literal { "," literal } ")" ]`. Which parameters a target accepts depends on the source type: `blob AS STRING` requires an encoding, and `5 AS STRING("utf-8")` is an error. I'd make the encoding required rather than defaulting to UTF-8. The encoding is exactly what the bytes can't tell you, and guessing it is the implicit-conversion trap the rationale already rejects. A conversion with a different parameter is a different warning source.

That suggests a rule for parameters: **a parameter supplies what the data cannot tell; it never tests what the data can.**

- An encoding qualifies.
- An image format doesn't: images identify their own format, so `AS IMAGE` would detect it, and "is it a PNG" becomes a question asked of the result. `AS IMAGE(png)` mixes a conversion with a filter.

In practice, image conversions at field level won't get much use anyway. By the common convention, an APE `Cover Art (Front)` item holds a file name and a NUL byte before the image, and an `APIC` body has its own header. Neither field's bytes are an image, so pictures really belong to concepts. Text decoding is the field-level conversion that earns its place.

## For you to decide

1. **The split:** separate `opaque` and `blob` types, or one type plus the rule that every promoted type keeps blob's conversions.
2. **The names:** `opaque` for the placeholder and `blob` for bytes, or something else.
3. **`ape::bytes()`** as a separate function, and whether other sources get a byte view later. Id3v1's codepage caveat would want one, but Id3v1 has no keys to pass it.
4. **Parameters:** string literals only, or bare names allowed as well.

- **Runtime**

  - The code-page encodings ship with .NET 10: `System.Text.Encoding.CodePages` shows up in the restore's list of packages pruned as part of the framework. So no new NuGet package should be needed.

## Unquoted words with hyphens

The lexer makes all its tokens in one pass before parsing starts, which rules out two cheaper-looking approaches:

- **Gluing touching tokens back together in the parser** is too fragile. `iso-8859-3` happens to lex as a name followed by two signed numbers, but `x-mac-roman` stops the lexer at `-m`, because a hyphen not followed by a digit starts no token. `utf-16le` splits into a number and a name.
- **Allowing hyphens in names everywhere** is clean today, but `year-1` would then be a name. Any future arithmetic would need spaces around its minus, which is the trap CSS `calc()` is known for, and the rationale already mentions arithmetic as possible.

**What works: one context-dependent token rule.** Inside the parentheses directly after a conversion target, a parameter is a *word*: a letter followed by letters, digits, `_` or `-`. This is cheap and contained:

- **The context can be read from the tokens.** `AS` is reserved and can only be followed by a target, so the lexer only needs to have just emitted `AS`, a name and `(`. It stays in this mode until `)`.
- **There's a precedent.** The lexer already looks back at the previous token to join the clock form of a duration (`Lexer.cs:568`).
- **No valid predicate is affected**, since that token sequence can't occur in one today.
- **The spec cost** is one sentence added to "Tokens and whitespace", next to the longest-token rule. Note that this makes "a token is always as long as it can be" depend on position for the first time.

Words cover essentially every encoding label people actually type, such as `utf-8`, `iso-8859-1`, `windows-1252`, `shift_jis`, `x-mac-roman` and `ascii`. Rare labels containing `:` or `.` would be rejected with the closest supported name suggested. Matching is case-insensitive, like everything else outside a string. If a future target ever needs a number or a string as a parameter, literals can be added to that position later without changing anything.

I'd recommend this spelling, with the work deferred until something produces a blob.

## APE: one key holding both binary and string?

**No, not within one tag.** APE allows one item per key, keys compared without regard to case, and each item has exactly one kind: text, binary or locator. A tag that breaks the rule doesn't get both either. I built such tags in a throwaway probe against TagLibSharp 2.3.0, and it kept the last item every time:

| Tag built with                         | TagLibSharp gives |
|----------------------------------------|-------------------|
| text item, then binary item, same key  | the binary item
| binary item, then text item, same key  | the text item
| `ARTIST`, then `Artist`                | `Artist` only

That matches the quirk `identifiers.md` already documents. So for one file and one key there is one item of one kind. The kind only varies *between files*, which is exactly what having two views handles.

One thing does differ under a single key: **cardinality**. A text item can hold several values separated by NULs, while a binary item is a single run of bytes. My leaning is that `ape::bytes()` gives one occurrence per value of a text or locator item, and one occurrence for a binary item. Then `ape::bytes(k)` and `ape::field(k)` always have the same number of occurrences, and differ only in type and in which occurrences are usable:

| Item              | `ape::field(k)` | `ape::bytes(k)` |
|-------------------|-----------------|-----------------|
| text, two values  | two strings     | two blobs
| locator           | its text        | its bytes
| binary            | one unusable    | one blob

## What the probe found besides

**TagLibSharp decodes a text item as UTF-8 as it reads it, and keeps nothing else.** A Latin-1 `Motörhead` (byte `F6`) comes back with U+FFFD in place of the `ö`. The item's raw value is null, and `Render()` writes the replacement character back out. So:

- **The bytes of a text item can't be had through TagLibSharp.** `ape::bytes("Artist") AS STRING(iso-8859-1)` only works if Goro reads the APE tag itself. That isn't much work: the format is a 32-byte footer followed by items of length, flags, key and value.
- **If the tag-reading line does that, it also improves on today in two places.** Invalid UTF-8 in a text item could become an unusable occurrence instead of being quietly garbled, which is the failure the damaged-data question worries about. And an older APE tag, which `identifiers.md` says won't read correctly outside ASCII, could be decoded as the ISO-8859-1 it was specified as.

None of this changes the design; it's for whichever line reads the tags. I've put it in the Log.

## Yes, `bytes()` applies to Id3v2, and that simplifies `field()`

With `bytes()` available, I'd change my earlier proposal. `id3v2::field()` should no longer be typed by its frame identifier.

- **`field()` is always a string and `bytes()` always a blob**, for every source that has keys: `id3v2`, `ape` and `vorbis`. A type then depends only on the function, never on an argument.

## PREFERRED(): the split solves most of it, not all

The split fixes mixing a concept with a field: `PREFERRED(picture, id3v2::bytes("GEOB"))` is a type mismatch today, so promotion can't break it. And since blobs are never promoted, `PREFERRED()` can accept them.

What's left is two *different* opaque concepts. If `opaque` is one type, `PREFERRED(picture, some_other_opaque)` is valid today and becomes a mismatch the day `picture` is promoted alone.

Rather than keeping opaque out of `PREFERRED()`, I'd give **each opaque concept a type of its own, which is the same type only within that concept.** An undecided type isn't known to equal another undecided type, so this is just the type-equality rule doing its job. `PREFERRED(id3v2::picture, ape::picture)` is then valid and stays valid, because a concept's cells are promoted together. Mixing concepts is an error from the start, and `PREFERRED()` needs no exception. That also removes the irregularity from my first proposal: the plain `picture` concept is once again the value of a call you can write.

## Opaque: one type per concept would balloon it, so I'm withdrawing that

With a type per concept, the list would read "string, number, bytecount, duration, boolean, blob, and an opaque type for each concept whose type isn't decided". On paper that's one entry and one sentence. In kind, though, the list stops being a closed set of names and becomes an open family, and the binder's types stop being a plain enumeration. That is exactly the part of the core you want closed.

So I've gone back to **one `opaque` type**, accepted only by the constructs that take any type on its own: `IS` and `COUNT()`. `PREFERRED()` relates the types of its arguments to each other, so it doesn't qualify. All we lose is reordering the cells of one concept, which plain `picture` already does in the standard order. ## 1. Addressing by v2.4: your nervousness is justified

I probed TagLibSharp 2.3.0 with hand-built tags:

| Tag   | Recorded                          | TagLibSharp gives |
|-------|-----------------------------------|-------------------|
| v2.4  | `TYER`, `TDAT`, `TDRC`            | all three, unchanged: nothing converted
| v2.3  | `TYER` 1991, `TDAT` 0102, `TIME` 1200 | one `TDRC` of `1991-01-02T12:00`
| v2.3  | `TORY`                            | `TDOR`
| v2.3  | `RVAD`                            | nothing: it's dropped
| v2.3  | `IPLS` with `producer`, `Someone` | `IPLS` holding only `producer`
| v2.2  | `TT2`, `TYE`, `PIC`, `CRM`        | `TIT2`, `TDRC`, an `APIC` with converted content, `CRM`

The library's view of a tag changes with its revision. It merges three frames into one, drops some, loses half a value in another, and leaves older frames in a v2.4 tag alone. The merged date also contradicts `identifiers.md`, which says a full date can't be recovered from v2.3.

Addressing by v2.4 can still be made watertight, with a rule that depends on the frame alone:

- **A fixed table, keyed on the frame's own identifier, whatever the tag's revision says.** A frame is renamed to its v2.4 identifier only where v2.4 holds the same data in the same form.
  - `TYER` becomes `TDRC` and `TORY` becomes `TDOR`, because the recorded text is valid in the new frame.
  - `TDAT`, `TIME`, `RVAD`, `EQUA` and `PIC` keep their own names, because their form differs.
- **A `TYER` in a v2.4 tag is read as `TDRC` too.** A tag holding both gives a bag of two occurrences, which is what it records.
- **Writing a renamed identifier is an error that suggests the v2.4 one**, so `id3v2::field("TYER")` offers `TDRC`.

The catch is that this only holds if Goro lists the frames itself rather than taking TagLibSharp's converted view. That's the same conclusion APE text items reached. It's work for whichever line reads the tags, but it's now two formats pointing the same way.

## 3. Trimming in normalized comparison: what could break it

**The big one is `AS`, which comparison never reaches.** Fields are no longer trimmed, and the as-operator line decided only yesterday that text converts only when it's the literal and nothing else. So `vorbis::field("BPM") AS NUMBER` on `"120 "` would be unusable and warn, and trailing spaces are common. I'd have `AS` ignore whitespace at the edges of text too. That reopens a rule we just settled, so it's your call. I'd decide it together with trimming, because the case for one is the case for the other.

The rest:

- **Prefix ranges.** `artist BETWEEN "the ".."the "`, meant as "begins with the word The", would become `"the".."the"` and match Thelonious Monk and Theodorakis, silently. One fix is to trim only data read from files; `normalization.md` already has a step that applies to file data alone. But then `x == "foo "` can never be true. I'd rather keep trimming on both sides and let `artist =~ r"^the "` handle it, since the space inside the subject survives.
- **Hunting for stray whitespace**, an obvious collection-cleanup task. `field =~ r"\s$"` never matches in normalized mode. It needs `LITERALLY`, just as diacritics in a pattern already do.
- **Blank fields.** A field of nothing but spaces is present and equal to `""` through `field()`, while concepts still treat it as absent. That's two answers for one piece of data, which is intended, since a field is the recorded form.
- **Where trimming goes among the normalization steps:** after step 3, which removes default-ignorable characters. Otherwise a zero-width space at the end would hide a trailing space. Step 2 already turns no-break and ideographic spaces into plain spaces.
- **`file` strings are essentially unaffected.** A path starts with `/` and a name ends with its extension. Only a file named `" leading.mp3"` would now equal `"leading.mp3"`.
- **Two improvements:** a leading space no longer sorts a value before everything else, and a trailing newline on lyrics or comments stops mattering.

## Claude

I don't think it will bite, but you've found one real limit, and it isn't about `field()` being a string.

**There are three ways in, not two.** Besides new concepts and new conversion targets, a source can gain new **source functions**. Each of the three only turns what was an error into something valid, so none of them can break an existing predicate. The rule that a type depends on the function and never on its argument means a richer reading gets a new function rather than changing `field()`. That's the cleaner result anyway.

**Nothing becomes unreachable.** `bytes()` gives every item, frame or comment whole, as recorded. Whatever reader we want later always has the full data to start from. The exceptions are the sources without source functions: Id3v1, whose comment can't be reached until a concept covers it, and `file`. Both can gain source functions later without breaking anything.

**The real limit: a conversion knows the value, not where it came from.** A blob doesn't say whether it's an `APIC` body, an APE `Cover Art` item (a file name, a NUL, then the image) or a FLAC picture block, and each lays out its data differently. So a conversion from a blob can only decode what's the same everywhere: text in a named encoding, base64, an image that identifies its own format. To get further it needs a parameter naming the layout, such as `AS PICTURE(apic)`. That does fit our parameter rule, since the layout is something the bytes can't tell you.

Structure that belongs to one format, under a name the predicate chooses, needs a construct that knows its source. Two examples:
- `POPM` frames, which are kept per email address;
- an APE `Cover Art (Back)` item.

Concepts can't help with either, because concepts are Goro's names and can't take the user's. What's left is further source functions. So the likely future isn't "everything through conversions from blob" but a few typed source functions per format. How those should look is the same ergonomics question you raised for aggregate types.

**One more loss, already present: strings in an unordered bag drop structure that spans several values.** In `TIPL` (and the older `IPLS`), the values alternate between a role and a person. `field("TIPL")` gives an unordered bag of strings, so you can't tell who did what. `bytes()` keeps the pairing, and so does any future reader built on it.

I've added this to the brief's Log as an observation, with no decision. If you want it in the rationale, it fits as one paragraph under the blob entry: a conversion out of a blob can only use what the blob holds.
