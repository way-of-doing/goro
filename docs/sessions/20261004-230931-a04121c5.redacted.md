# Is a literal in parentheses a literal?

The grammar never says, and that gap is older than this line.

In the grammar, `primary = literal | identifier | function_call | "(" expression ")"`. So `("^a")` doesn't parse as a `literal`. It parses as a parenthesized expression whose content happens to be a literal. When a rule says "must be a literal", nothing tells you whether that wrapper counts. I treated it as not counting, but that was a guess.

The same gap exists wherever a rule asks for a literal but the grammar only asks for an expression:

- the default of `FALLBACK()`: is `FALLBACK(x, (0))` valid?
- the numeric literal exception: does `file::duration > (90)` mean ninety seconds, or is it a type error?
- the `NUMBER()` rule against a string literal that isn't a valid number: is `NUMBER(("abc"))` rejected when the predicate is read?

Range endpoints don't have the problem. `range = literal ".." literal` is grammar, so `(1)..2` is a plain syntax error.

So yes, it's a defect: a question the spec can't answer. I'd fix it by saying parentheses don't matter here. Wherever a rule asks for a literal, a literal in parentheses counts. That matches how definiteness already works ("a parenthesized definite expression") and the general expectation that redundant parentheses never change anything. The modifier case in `deferred.md`, where they do change something, is already recorded as surprising. The fix is one sentence in the spec, plus the testing row I wrote, which then gets the opposite answer.

# Making the pattern part of the operator

## Does it shield regex syntax from changes to string literals?

Only partly. Moving the pattern into the operator shields it from changes to **expressions**. Changes to the **string token itself** still get through.

- **Expression-level changes are shielded.** Once the grammar says `"~=" pattern`, the pattern is a token rather than an expression. String concatenation, named constants, string functions, parentheses, or any future way of building a string at read time can't reach it. As an operand, every one of those would reopen the question of what counts as a literal, which is exactly the problem above.
- **Token-level changes are not shielded** while `pattern = string`. The concrete hazard is a new escape. Today `"\bfoo"` is an error, because `\b` isn't a string escape, and that error catches someone who meant a word boundary. Most languages read `\b` as backspace. If Goro's strings ever adopted it, `"\bfoo"` would quietly hand the regex engine a backspace. No valid predicate would change meaning, but the error that protects people today would disappear. Interpolation in ordinary quoted strings would be worse, since `{4}` is everyday regex syntax.

Full shielding needs a pattern production of its own. The simplest one is **`pattern = raw_string`**, which makes the regex engine the only thing that processes escapes. The cost is an `r` on every pattern: `artist ~= r"s$"`. The spec already calls raw strings "the better habit for patterns", and this makes the habit the rule. It also follows the project's usual reasoning about which direction to restrict: going raw-only now and admitting quoted strings later breaks nothing. It's a separate decision from moving the pattern into the operator, but only that move makes it a clean grammar rule.

## Claude

Almost. One small correction first: the direction is the other way round. The parse tree, which keeps every token, is what the AST is built from, and dropping parentheses is the usual thing to do at that step. The architecture doc has the parser build the syntax tree directly, so in practice the parser just returns the inner node when it finishes a parenthesized expression.

For nearly every rule, that's correct, because `(e)` behaves exactly like `e`:

- **Type and definiteness:** `evaluation.md` already says `(e)` has whatever `e` has.
- **Literal-ness:** after this change, a literal in parentheses counts as a literal, so the check is just "is this node a literal".
- **Warning sources:** sources are already defined so that how something is written doesn't matter.
- **Grouping:** the tree's shape already records it. `(a == b) == c` becomes `Eq(Eq(a, b), c)` either way, and `a == b == c` is rejected by the parser before any parentheses could be dropped.
- **Grammar positions:** `(1)..2` and `artist ~= (r"^a")` are parse errors, so nothing after parsing has to handle them.

**The exception is the modifier rule.** The spec still says `(ALL(genre)) == "x"` is an error, because the modifier sits inside a parenthesized expression rather than on the operand. If the parser drops the parentheses, static analysis sees `ALL(genre)` as the operand and accepts it, which contradicts the spec. The diagnostic also needs to know the parentheses were there, to say why it's rejecting the predicate. So as the spec stands, the parser has to keep something:

- a flag on the node saying it was parenthesized, checked only by the modifier rule; or
- a grouping node that every other rule unwraps through a helper.

**Or the spec could drop that exception.** Making parentheses transparent around modifiers too would leave one rule, "parentheses only group", and full erasure in the parser would then be correct. That's the `deferred.md` entry on redundant parentheses around a modified operand. It was held back only because nobody had tripped over it, not for any reason of meaning. The modifier rationale is about modifiers sitting far from the operator, and parentheses add no distance. Now that a literal in parentheses counts as a literal, the modifier case is the only place where adding redundant parentheses changes whether a predicate is valid.
