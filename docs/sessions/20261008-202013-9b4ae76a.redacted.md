**1. What we can still read from a damaged file**
- **Tags** fall into six levels of damage:
  - *Healthy.*
  - *Harmless quirks*, such as iTunes-style frame sizes or an ID3v2 tag in front of a FLAC file. These read fully.
  - *One damaged value*, such as invalid UTF-8. Only that value's text is lost; `bytes()` still has it.
  - *The tag's structure breaks partway.* Everything before the break is readable.
  - *The tag is unusable as a whole*, but the file's other tags and its audio are fine.
  - *Silent corruption*, such as a flipped bit inside valid text. Only Ogg can detect this, through its page checksums.
- **My proposal** is that from "structure breaks" downwards, that one tag source becomes *incomplete*. Every lookup in it returns what was read intact, plus one unusable occurrence standing for what was lost. - **Playing time** has its own ladder:

  - Damage in the middle of a stream doesn't shorten the timeline; truncation does.

## What "timeline definition" means

Playing time means **how long the stream lasts by its own clock, if every frame played**. Concretely:

- **MP3:** frames × samples per frame, minus the LAME tag's encoder delay and padding.
- **Opus:** the final granule minus pre-skip.
- **Vorbis:** the final granule.
- **FLAC:** the total samples.

The alternative is the *decodable length*: the samples a decoder actually outputs. That depends on the decoder. ffmpeg's Vorbis decoder stops dead at a missing page and reports 1.905 s for a 3.3 s file. A more forgiving decoder would report more.

The timeline is deterministic and matches what players display. Ogg and FLAC carry absolute positions, so damage in the middle doesn't move the end. Truncation does shorten it, because the positions past the cut no longer exist. Damage itself is the audio hash's job.

There is one gap. MP3 frames carry no positions. If we have to scan an MP3 because the header is missing or fails its checks, frames lost in a damaged region can only be estimated, from the bytes skipped divided by the average frame size. The prototype counts only the frames it finds, so in that case the scan undercounts.

## Worst case per format

In each format, a file with no recoverable audio gets no duration. It is then unreadable for `file::duration` only; its tags are unaffected.

**MP3**
1. **Find the audio.**
   - Skip any number of leading ID3v2 tags, and an APE tag with a header.
   - Strip ID3v1, Lyrics3, APE and an appended ID3v2 from the end, checking each one.
   - Find the first confirmed frame: a valid header with a matching header one frame length later. This also gets past junk.
   - One gap: if a tag's size points past the end of the file, we should search for audio from just after the tag header. The prototype doesn't do this yet, and neither does ffmpeg.
2. **Check the summary header.** Look for Xing or Info at both possible offsets, then VBRI. Trust its frame count only if:
   - the LAME tag CRC passes, where there is a LAME tag;
   - and its byte count matches the audio found, within one frame.
   A Xing header without a LAME tag has only the byte check, which is weaker.
3. **Otherwise scan every frame header to the end of the audio.**
   - On lost sync, search for the next confirmed frame. Frames in the damaged span are lost from the count.
   - Treat any later Info frame as a sign of joined files.
   - Free-format frames take their length from the next sync word.
4. **Apply gapless trimming.** Subtract the LAME delay always. Subtract the padding only if the scan's frame count matches the header.
5. **Cost:** the scan reads the whole file. It's cheap in CPU, and expensive in I/O on slow storage.

**FLAC**
1. Skip any leading ID3v2 tags and find `fLaC`. A lying tag size would need a search for `fLaC`, which isn't in the prototype yet.
2. **Walk the metadata blocks, trusting no length.** The first block must be STREAMINFO. Stop at the last-block flag, at a frame sync where a block header should be, or at an impossible block. If the chain is lost, search forward for the frame-0 header, checked by its CRC-8.
3. Strip ID3v1 and APE from the end.
4. **Find the last intact frame by searching backwards.** It needs a header passing CRC-8 and a frame passing CRC-16. The frame's end is found from the running CRC, which tolerates trailing garbage.
5. **Decide:**
   - STREAMINFO, if it matches that last frame;
   - the last frame, if STREAMINFO is 0 or the file is truncated (the tail is too short to hold the missing samples);
   - STREAMINFO, if a tail long enough to hold them is merely damaged.
6. **If STREAMINFO is destroyed,** take the sample rate and block size from the frame headers. That fails when a header defers to STREAMINFO for them.
7. **Cost:** a head read and a tail read. It becomes a forward search only when the metadata chain is lost.

**Ogg**
1. **Skip leading junk,** such as an ID3v2 tag, by searching for the `OggS` pattern.
2. **Take the cheap path when possible:** read the first page and the last 64 KB. If the last page has the first page's stream serial, passes its checksum and marks the end of the stream, it's a single stream and that's enough.
3. **Otherwise walk every page header,** skipping the page bodies. That finds chain links, interleaved streams, sequence gaps and checksum failures.
4. **For each stream:**
   - identify the codec from its first packet (Vorbis gives the sample rate; Opus gives pre-skip);
   - take the last granule on a page that passes its checksum, ignoring −1;
   - subtract Opus pre-skip.
   The prototype assumes a Vorbis stream starts at sample 0. That is true for encoder output, but not guaranteed.
5. **Multiplexed** (interleaved streams): declined. **Chained:** sum the links in seconds. **Truncated or bad last page:** the last good granule.
6. **No usable headers:** fail. Opus granules are always 48 kHz, but without OpusHead we don't know it's Opus.

## Unsynchronised, compressed and encrypted frames

All three are transformations the ID3v2 format applies to a frame's content when storing it. The question is whether `bytes()` gives the content or the stored form.

**Unsynchronisation** is an escape scheme. ID3v2 sits in front of MPEG audio, and old players scanning for a frame sync could mistake tag bytes for audio. So a writer inserts `00` after every `FF` that is followed by `00` or by `E0` and above. A reader removes those zeros again.
- **v2.2 and v2.3:** a tag-level flag escapes the whole tag body as one stream, frame headers included. Frame boundaries are only defined after the escaping is undone, so a single frame's "stored bytes" aren't even well defined.
- **v2.4:** escaping is per frame (flag `n`), and the tag flag means "all frames". The stored size is the escaped size, and an optional data length indicator gives the original size.
- **It isn't only pictures:** I just checked, and a UTF-16 byte order mark (`FF FE`) gets a zero inserted. So every UTF-16 text frame in an escaped tag is stored differently. mutagen reads such a frame back as plain `Title`.
- **Recommendation:** `bytes()` gives the content with the escaping undone. The escaping is transport, not data, and the same value written with and without it should give the same bytes.

**Compression** is zlib (v2.3 flag `i`, v2.4 flag `k`), with the decompressed size stored in front of the data. It is rare in practice.
- **Recommendation:** `bytes()` gives the decompressed content. Two taggers compressing the identical value can store different bytes, so the compressed form says nothing about the data.
- **Damage:** data that won't decompress is "one damaged value", so both `field()` and `bytes()` are unusable.
- **One robustness rule:** cap decompression at the declared size and at a hard limit. Goro reads untrusted files, and a tiny frame can claim a huge decompressed size and exhaust memory.
- **Today:** TagLibSharp silently drops compressed frames, so they read as absent. I verified this through its frame-creator hook.

**Encryption** (v2.3 flag `j`, v2.4 flag `m`) uses a method symbol registered by an `ENCR` frame. ID3 defines no algorithm; the owner of the method does. Goro can never decrypt it. I believe it was essentially never used, though I can't verify that from here.
- **`field()`:** the frame clearly exists and we know what it is (a `TPE1`, say), so it gives an unusable occurrence.
- **`bytes()`:** giving the ciphertext would make `bytes()` mean "content" for one frame and "ciphertext" for another, with nothing in the predicate to tell them apart. So it should be unusable too.

That gives one rule with no exceptions, matching your checksum decision:

> `bytes()` gives the frame's content with the format's own storage transformations undone: unsynchronisation, compression, and the extra prefix bytes the flags add (group ID, encryption method, data length indicator). Where a transformation can't be undone, because of encryption or broken zlib, the occurrence is unusable.

**The order of operations matters:** writers compress, then encrypt, then escape. So a reader undoes the escaping first, then decompresses. An encrypted frame stops at the second step.

There is one ambiguity I can't settle from here. The v2.3 spec implies frame sizes count the *unescaped* bytes, and TagLibSharp, mutagen and the prototype all agree. If `goro audit` ever finds real files written the other way, we could add a fallback check like the one for iTunes v2.4 sizes.

## Decision 2: can we know a tag is wholly unusable?

Yes, and early. With our own reader, reading a file's tags means parsing each tag fully: locating it, walking every frame, and decoding every key and value. That happens once per file, before any predicate asks anything. The result for each source is a list of fields plus a condition: healthy, quirks, structure broken, or unusable. Lookups afterwards only consult that list. So a wholly unusable tag has no fields, every lookup on it is absent, and its condition is still there to report the file. Nothing extra has to be tracked.

Two details matter:

- **"Unusable" means we couldn't even delimit frames,** not that every frame failed. Examples are a size past the end of the file, a version 5 header, or a vendor length overrun. A tag whose structure is fine but whose every value is bad is many cases of "one damaged value". Its keys are known, so it yields unusable occurrences under them, and it isn't reported as a file.
- **Parse every tag of the file, not just the sources a predicate touches.** The tags are small and sit in data we read anyway (for an MP3 we have to locate them to find the audio). This keeps the report independent of `PREFERRED()` short-circuiting. Otherwise whether a broken ID3v2 tag gets reported would depend on whether the Vorbis comment happened to answer first.

One limit remains. A tag whose header itself is wiped can't be recognised as a tag at all. But for MP3 it shows up as unexplained bytes before the first frame, which we detect, so we can report the file anyway.

## Decision 1: proposed warning structure

Today's three categories are ordered by how far a caller should distrust the result. The new one fits between the two existing ones:

| Code | Category     | Meaning                                                              | Form
|------|--------------|----------------------------------------------------------------------|------
| 10   | `data`       | junk was used, whether or not an answer depended on it                 | per file and source
| 11   | `unanswered` | an answer depended on junk, and the command decided                    | one per run, a count
| 12   | `damaged` (new) | a file was processed although part of it could not be read; answers about it may rest on data that is missing | one per run, a count, pointing to `goro audit`
| 13   | `file` (was 12) | a file was not processed at all                                      | per file

`damaged` ranks above `unanswered` because its failure is silent. A key lost behind a broken structure looks absent, so a predicate can be false without anything having been unanswered. It ranks below `file` because the file was at least processed.

- **What counts as damaged:** a broken tag structure, a wholly unusable tag, an Ogg comment page failing its checksum, junk before the audio, and audio damage the read detected while still computing a value. That last group covers a truncated FLAC, a STREAMINFO that lies, a bad last Ogg page and a missing Ogg page.
- **Counting:** a damaged file can also be unanswered, and is counted in both.
- **What changes:** warnings.md and exit-codes.md change, and rationale gets "Why are there four categories" in place of three.

## Playing time: files that would need a full scan

Only MP3 ever needs a full scan. FLAC and Ogg always settle from head and tail reads, apart from chained Ogg, which needs a header-only page walk. MP3 needs one in two cases:

- **The summary header fails its checks:** a truncated or joined file, or a frame count that lies.
- **There is no summary header at all:** VBR without Xing, or old CBR without Info. That isn't damage, just old.

I recommend skipping both by default. `file::duration` would then be unreadable, under the `file` category, with a reason such as "the playing time could only be had by reading the whole file". The alternative, reporting them as `damaged`, would put files that aren't damaged into that category and blur its meaning. A future flag that allows the scan then moves the truncated and joined cases into `damaged`, with a value.

There is one trade-off. File warnings are per file, so a collection of old rips without Info frames would warn once per such file. I have no data on how common they are. LAME and ffmpeg write the header by default; older encoders didn't. `goro audit` would be the tool that tells you.

I think this is the right seam, and the survey's prototype already has this shape: locate tags, parse them, find the audio's edges, collect the duration evidence, and report conditions. What it lacks is the "never walk" guarantee. Here is what I'd adjust in your sketch.

**What the edges give, per format**

| | Head | Tail | Needs both (collate) |
|---|---|---|---|
| MP3 | leading tags (ID3v2 chain, APE with header) and their values; junk B→C; first frame C; Info frame (Xing/VBRI, LAME delay, padding and CRC) → D | ID3v1, Lyrics3, APE footer chain, appended ID3v2 → F | Is the Xing byte count consistent with F? | FLAC | leading ID3v2; metadata block chain; STREAMINFO; Vorbis comment; pictures; first frame | ID3v1, APE; the last intact frame | STREAMINFO against the last frame (the tail search window comes from STREAMINFO's max frame size) |
| Ogg | BOS pages, codec headers, comment packet (may span pages) | last page: granule, EOS, serial | pre-skip and sample rate from the head turn the tail's granule into a duration; serials that differ mean a chain or a multiplex |

Beyond what we've discussed, the edges also give the format check: does the content match the extension? They also give the stream parameters, the encoder string, and FLAC's MD5-present flag. All are free, but I'd return them only once something needs them.

**Where the edges stop being enough.** These are the "surprising" cases, and the design should make them explicit:

- **Searching for the first frame when a tag's size lies (M9, M10), and for frame 0 when FLAC's metadata chain breaks.** These are forward searches of unknown length. Bound them to a window of a few hundred KB; give up past it, and record the condition.
- **A gap after the last MP3 frame without a valid header.** The tail can confirm E = F by finding a header whose frame length lands exactly at F. That needs at most one maximum frame length searched backwards. What it can't tell is how far a gap extends. Under the decided rules that case is already an unusable duration, so nothing needs a walk.
- **Chained Ogg.** Summing the links needs the link boundaries. Bisection on page serials, as libvorbisfile does, finds them in about log₂(size) page reads per link. That's many seeks, but not a walk. Multiplexed files are cheaper still: all their start-of-stream pages come first, so the head alone identifies them, and we decline them.

So "edges" should mean **bounded reads whose sizes follow the declared structure**, not fixed 64 KB windows. Tags are legitimately large: 64 KB of padding, megabytes of cover art. One concrete way to hold the line is a **read budget**: the parsers request byte ranges through a small source abstraction, and anything beyond structure plus bounded windows becomes a condition rather than a read. That turns "never walks the whole file" into something a test can assert, and it separates where bytes come from from how they're parsed, which is the prototype's biggest production gap.

**One refinement on "tags and their values".** Parse every frame header and every text value eagerly, but record only the offset and length of large binary payloads (APIC, PRIV, big APE binaries) and fetch them on demand. Otherwise every `goro list` run reads every file's cover art, though only `bytes()` on that frame needs it.

**Async head and tail branches: split them, but I wouldn't make them concurrent.**

- **Split:** writing Head → findings, Tail → findings and Collate(head, tail, length) → result as separate pure functions is worth having. Each part can be tested against the corpus alone, and the cross-checks live in one obvious place.
- **Concurrency:** I don't think it pays.
  - Goro already processes many files at once, and that is what keeps the storage busy. Two concurrent reads of the same file add contention, and seeks on spinning disks, without adding throughput.
  - The branches aren't fully independent anyway. FLAC's tail window and Ogg's duration both need head data, so collate sometimes asks for one more tail read.
  - Sequential reads within a file, with concurrency across files, keeps the executor model as it is.

**How it fits the current runtime.**
- **One analysis facet:** it would replace today's two TagLibSharp-backed facets, the tags (not yet bound) and the audio properties. It still loads only when a predicate first touches anything inside the file, so `file::path` and `file::size` stay free.
- **No new rule:** "every tag of a file is parsed whenever its tags are read" falls out naturally.
- **What each command takes from it:**
  - `goro list`: values plus conditions, which feed the `incomplete` count.

**2. Chained Ogg**

An Ogg file holds one or more *logical streams*. Each is identified by a serial number, starts with a beginning-of-stream page and ends with an end-of-stream page. *Chaining* puts complete streams one after another in one file. It comes about two ways:
- **Internet radio captures,** where each new track begins a new link;
- **plain concatenation:** `cat a.ogg b.ogg > c.ogg` produces a valid chain.

Every link is a whole stream of its own. It has its own codec headers, so Vorbis can be followed by Opus, and its own sample rate. Its granule positions restart at 0. And it has **its own comment header, its own tags**.

That causes two problems:
- **Duration.** The last page only tells you the last link's length. The total needs every link's boundary, its last granule, its sample rate and its pre-skip. Finding the boundaries means either walking every page or bisecting on serial changes, the way libvorbisfile does: about log₂(size) seeks per link. That isn't a walk, but it isn't edges either.
- **Tags, which is the bigger problem.** A radio capture is several tracks with different artists and titles. Whose tags are "the file's"? The first link's, the union of all, or none? There's no good answer.

The survey saw this go wrong in practice:
- TagLibSharp throws on both chained seeds;
- NVorbis reads only the first link;
- ffprobe claims 1.7 s for a file that decodes to 5.0 s;
- ffmpeg decodes only the first link of a Vorbis-then-Opus chain.

**My recommendation: decline chained files, as we decline multiplexed ones.** It's conservative, it avoids the tag question entirely, and it keeps Ogg analysis to edges only. Detection is cheap: the last page's serial differs from the first page's. One blind spot: a file concatenated with *itself* repeats the serial (which the spec forbids). It looks like one stream whose duration is the last link's. Only a walk can see that, so it's for `goro audit`'s deep mode.

**3. Tracked bounded reads: an outline**

/// Positioned reads from one file, with no stream position to share. Production wraps
/// RandomAccess.Read on a SafeFileHandle; tests wrap a byte[].
public interface IByteSource : IDisposable
{
    long Length { get; }
    int Read(long offset, Span<byte> into);   // fewer bytes only at the end of the file
}

/// Why a read happens. Each purpose has its own allowance in the policy.
public enum ReadPurpose
{
    Sniff,              // the first bytes: ID3, fLaC, OggS, a frame sync
    DeclaredStructure,  // bytes a header said exist: a tag body, a metadata block, a page
    Search,             // looking for something: first frame, fLaC after junk, last frame, last page
    Payload,            // a value read later, on demand
}

/// The limits that make "never walks the whole file" checkable.
public sealed record ReadPolicy(
    int HeadWindow = 64 * 1024,        // read once, then served from memory
    int TailWindow = 64 * 1024,
    int SearchLimit = 256 * 1024,      // per search, beyond the windows
    int PayloadLimit = 4 * 1024 * 1024 // the decompression cap lives with this
);

/// The analysis's only way to the bytes. It serves reads inside the head and tail windows
/// from memory, charges every read to its purpose, and refuses what the policy does not allow.
public sealed class BoundedReader
{
    public BoundedReader(IByteSource source, ReadPolicy policy);
    public long Length { get; }

    /// The bytes, or a refusal saying which allowance ran out. Never throws for content.
    public ReadResult Read(ReadPurpose purpose, long offset, int count);

    /// A search: scans forward or back from `from`, within the purpose's allowance,
    /// handing each candidate position to `accept` until it says yes.
    public SearchResult Search(long from, SearchDirection direction, Func<ReadOnlySpan<byte>, long, bool> accept);

    public ReadLog Log { get; }   // purpose, offset, length of every read: for tests and audit
}

public readonly record struct Region(long Start, long Length);

public sealed record FileLayout(
    AudioFormat Format,
    IReadOnlyList<TagIndex> Tags,      // where each tag is, its condition, and its fields' locations
    Region? LeadingGap,                // B to C
    Region? TrailingGap,               // E to F, when it can be known
    AudioLocation Audio,               // Found(C, D, F, E-if-known) | NotFound(why)
    DurationOutcome Duration,          // Known(samples, rate, basis) | Unusable(why)
    IReadOnlyList<Condition> Conditions,
    ReadLog Reads);

/// One field, located but not read: enough to answer "is there a TPE1" and to fetch it.
public sealed record FieldEntry(string Key, string? Description, Region Stored, Transform Transform);
//  Transform: None | Unsynchronised | Compressed(declaredSize) | Encrypted(method) | ...

/// Reads a value on demand. It undoes the transforms, decodes strictly, and charges Payload.
public sealed class TagValues
{
    public TagValues(BoundedReader reader);
    public ValueResult Bytes(FieldEntry field);
    public ValueResult Text(FieldEntry field);   // may be unusable: rung 2
}

**How the pieces interact, per file:**
1. The analysis facet opens an `IByteSource` and wraps it in a `BoundedReader`.
2. **Sniff:** the head window decides the format, and the format must agree with the extension.
3. **Head** (`Mp3Head.Read(reader)`): index the leading tags, search for C within `SearchLimit`, and parse the Info frame.
4. **Tail** (`Mp3Tail.Read(reader)`): follow the footer chain from the end of the file inwards, and check whether a frame ends exactly at F.
5. **Collate** (`Mp3Layout.Collate(head, tail, reader)`): the cross-checks, the duration outcome and the conditions. FLAC and Ogg occasionally request one more tail read here. A predicate that asks for a value later goes through `TagValues` on the same reader.

**Tests can then assert the guarantee directly**, for example: "on every corpus file, `Search` and `Payload` reads stay under their limits, and the reads total under 2 × window plus structure."

**4. Tags: no values up front**

This works, and it fits the damage rules neatly. The index, meaning frame headers, item headers and comment lengths, is what detects rungs 3 and 4 (broken structure, an unusable tag). Those are exactly the rungs that report the file, so the `incomplete` count is complete without reading any value. Rung 2, a value that won't decode, surfaces only when someone asks for that value. That's when it becomes an unusable occurrence with a data warning, and rung 2 never reported the file anyway. **The lazy design and the decided rules line up.**

Three places where locating a field means reading into its content:
- **Descriptions** of `TXXX`, `COMM`, `USLT` and `WXXX` are needed to answer `field("TXXX", "MOOD")`. They're short, at the start of the content, but still content.

## Decode parameters across formats

The general shape is **hash the audio units in decode order, plus the decode parameters**: values outside the audio units that a decoder needs, or applies, to produce its output. Summaries, informational fields and tags are excluded, ReplayGain tags included. I changed each field below and decoded with ffmpeg:

| Format | In the bucket | Not in it (changing it altered nothing) |
|---|---|---|
| MP3 | LAME delay and padding | the Info frame's byte count |
| FLAC | the sample rate, channels and sample size in STREAMINFO, but only when frame headers defer to them. | Opus | pre-skip (155,592 samples instead of 158,400), output gain (same length, different samples), final granule | input sample rate |
| Vorbis | final granule: 500 lower gave 500 fewer samples | the bitrate fields |

The Vorbis identification and setup headers, `OpusHead`'s channel mapping and AAC's decoder configuration belong in the bucket too: without them nothing decodes, so there was no output to compare and I didn't test them.

- **The audio is located by tables of absolute offsets.** A 5,000-character title moved the first audio chunk from byte 1,411 to 6,406, so editing a tag rewrites the table that points at the audio. It must be hashed by samples, as Ogg is by packets.

- **Raw ADTS AAC behaves like MP3 without a LAME tag.**

- iTunes stores gapless information as `iTunSMPB` *inside the tag*. Under "tags are never hashed", that would be lost.

- It stays immune to tag edits, since the comments are a packet of their own.

- **MP3 and FLAC:** the frames, `[D, E)`;

## The new shapes, with what the specs say

**1. UTF-16 without a byte order mark.** This is encoding `$01`.

| Source | What it says |
|---|---|
| ID3v2.3 spec | "Unicode strings must begin with the Unicode BOM ($FF FE or $FE FF) to identify the byte order." It gives no fallback. |
| ID3v2.4 spec | "$01 UTF-16 encoded Unicode with BOM. All strings in the same frame SHALL have the same byteorder." It defines a separate `$02` for big-endian UTF-16 *without* a mark. |
| RFC 2781 §4.3, the UTF-16 definition v2.4 cites | Without a mark, the text "SHOULD be interpreted as being big-endian." |
| Practice, run on the real files | mutagen, TagLibSharp, TagLibSharp2 and ATL all read it as **little-endian** and get the right text. Read as big-endian it's garbage. |

The writers that leave the mark out are evidently Windows software, where little-endian is native. So the choice is between:
- **little-endian:** matches every other reader, and gets the text right in all the files we have. It would be recorded as an implementation choice, with audit flagging it.
- **unusable:** strictly what the spec permits.

I recommend little-endian.

**2. A later value without its own byte order mark.** This turns out to be two questions.
- **v2.4:** "all strings in the same frame SHALL have the same byteorder". So a second string without a mark still has a defined byte order. Inheriting the first string's mark is the spec-consistent reading. TagLibSharp2 does that; TagLibSharp keeps only the first value.
- **v2.3, which is the file we actually have (`null_title_v2.mp3`):** v2.3 allows only one value per text frame. Its spec says that after the terminator "all the following information should be ignored and not be displayed". identifiers.md also says a v2.3 frame never holds more than one value. Yet the prototype splits v2.3 text at NULs, and so does mutagen. A real v2.3 file in the test data has NUL-separated values in its `TXXX` frames.

So the question is: does Goro honour v2.3's "ignore after the terminator", and the docs' "one value", or accept NUL-separated multi-values in v2.3 as practice? I lean towards practice, because that file's values only make sense split, but it contradicts identifiers.md. It's your call.

**3. An illegal frame name with a good size** (`Date` in a v2.3 tag). Both specs limit names to `A–Z` and `0–9`. Both also say the size field exists so readers can skip frames they don't know, and that's what mutagen does.
- **Proposal:** step over it when its size lands on another frame, padding or the tag's end. Such a frame can't be reached by `field()` or `bytes()`, since Goro's name check rejects the name, and audit reports it.
- **Otherwise:** keep treating it as a broken structure, as now, and lose the frames behind it.

**4. v2.2 frames in a tag declaring v2.3,** written by iTunes 12.1.2.27. This is simply a violation that no spec addresses. mutagen detects it by trying the v2.2 layout when the declared one fails. It's the same kind of fallback the prototype already does for iTunes' v2.4 frame sizes.
- **Proposal:** if the declared layout fails at the very first frame and the v2.2 layout reads cleanly to the end, read the tag as v2.2, through Goro's v2.2 rename table, and audit reports it.

**5. `GRP1`, `MVNM`, `MVIN`.** These aren't in any ID3 spec. They're Apple's text frames: grouping, movement name and movement number, written by iTunes 12.5 and later. They have the ordinary text-frame layout. Today identifiers.md allows `field()` only on `T…`, `W…`, `COMM` and `USLT` frames, so `field("GRP1")` is an error, though `bytes()` works.
- **Proposal:** add these three by name to the frames `field()` reads as text. That's a small closed list, and Apple-tagged collections will have them.
