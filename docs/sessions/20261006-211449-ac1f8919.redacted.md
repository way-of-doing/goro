## Type families by layer

```
text ─► Lexer ─► Parser ─► Binder ─► Analyses ─► Lowering ─► CompiledPredicate ─► evaluation
        tokens   SyntaxTree   SemanticTree   side tables   evaluation tree
```

`PredicateCompiler.Compile` runs the whole pipeline.

**Shared by every layer**
- **`Goro.Predicates.Values`:**
  - `GoroType` with `GoroTypes`, which maps each Goro type to the C# type that holds its data.
  - The data types `ByteCount` and `Duration`, alongside `decimal`, `string` and `bool`.
  - `Value<T>`, holding `Occurrence<T>` (`Usable<T>` or `Unusable<T>`).
  - `Truth`, `DatumOrder<T>`/`NaturalOrder<T>`, `SourceId`/`Origin` and `NumberText`.
- **`Goro.Predicates.Text`:** `ComparisonMode`, `Normalization`, `StringOrder`, `CaseFolding`, `DefaultIgnorable` and `UnicodeForms`.
- **`Goro.Predicates.Diagnostics`:** `Diagnostic`, `Suggestion` and `StageResult<T>`, which passes either a value or errors from one stage to the next.
- **`Goro.Predicates.Identifiers`:** the catalog side.
  - Lookup: `IIdentifierCatalog`, `IdentifierLookup`, `IdentifierName`, `IdentifierDeclaration(<T>)` and `IdentifierBinding<T>`.
  - The built-in catalog: `BuiltInCatalog`, built from `ClosedNamespace`/`OpenNamespace` with `FileNamespace` and `TagBindings`.
  - Reading files: `FileData` and its facets, and `UnreadableFileException`.

**1. Syntax (`Goro.Predicates.Syntax`)**
- **Lexer:** the `Token` family (`NameToken`, `StringToken`, `NumberToken`, `ByteCountToken`, `DurationToken`), plus `TokenKind`, `TokenFacts` and `ExactDecimal`.
- **Parser:** `SyntaxTree` and the `SyntaxNode` record family (`LiteralSyntax`, `IdentifierSyntax`, `ModifierSyntax`, `ComparisonSyntax`, `BetweenSyntax` and so on). The enums `ComparisonOperator`, `LogicalOperator`, `ModifierKind` and `TestedState` come from here too.
- **Errors:** `ParserDiagnostics` and `SyntaxDiagnosticCodes`, with `TextSpan` and `SyntaxPrinter` alongside.

**2. Binder (folders `Binding/Binder/` and `Binding/Semantics/`)**
- `Binder` is a static entry point over a private instance per tree. `BinderDiagnostics` and `Spelling` sit beside it.
- `SemanticTree` holds the syntax tree, the root node and the binder's own errors.
- The `SemanticExpression` family is made of sealed classes compared by identity:
  - Leaves: `SemanticLiteral` and `SemanticIdentifier`.
  - Calls: `SemanticConversion`, `SemanticCount` and `SemanticFallback`.
  - Errors: `SemanticMalformedCall` and `SemanticInvalid`.
  - Operators, all under `SemanticOperator`: `SemanticComparison`, `SemanticRange`, `SemanticMatch`, `SemanticStateTest`, `SemanticNot` and `SemanticLogical`.
  - `SemanticOperand` is not a node: it is an operand with its modifiers folded into a quantifier, holding the expression.
- `SemanticDiagnostics` is the shared base for quoting the user's text, and `SemanticDiagnosticCodes` is the single register of error codes.

**3. Analyses (`Binding/Analyses/`).** Each follows the same pattern: a static class with `Analyse(tree)` returns a result object holding its tables and errors.

| Analysis    | Result              | Errors                 | Fact it provides                        |
|-------------|---------------------|------------------------|-----------------------------------------|
| Cardinality | `CardinalityAnalysis` | `CardinalityDiagnostics` | `IsDefinite(node)`                    |
| Constants   | `ConstantsAnalysis`   | `ConstantDiagnostics`    | `RangeOf(range)` → `PreparedRange`    |
| Patterns    | `PatternsAnalysis`    | `PatternDiagnostics`     | `PatternOf(match)` → `Regex`          |
| Sources     | `SourcesAnalysis`     | none (uses `Shape`)      | `OriginOf(node)`, `Table`             |

The names are inconsistent: `ConstantDiagnostics` sits next to `ConstantsAnalysis`, and `PatternDiagnostics` next to `PatternsAnalysis`. That's an oversight, and an easy rename.

**4. Lowering (`Binding/Lowering/`)**
- `Lowering` walks the semantic tree.
- `TypedNodes` is where a Goro type known only as data becomes a C# type parameter.
- `PreparedRange`/`PreparedRange<T>` hold a range's ends, prepared by the constants analysis.

**5. Evaluation tree (root of `Binding/`, plus `Goro.Predicates.Evaluation`)**
- The node families:
  - `BoundExpression`/`BoundExpression<T>`/`IBoundExpressionFunc`, `BoundCondition` and `BoundOperand<T>` with `Quantifier`.
  - Values: `Literal<T>`, `IdentifierReference<T>`, `Conversion<TFrom,TTo>`, `Count<T>` and `Fallback<T>`.
  - Conditions: `ComparisonTest<T>`, `RangeTest<T>`, `RegexMatch`, `StateTest<T>`, `Not`, `And` and `Or`.
- What lowering hands over is a `CompiledPredicate`, which also carries the `SourceTable`.
- Run-time machinery lives in `Goro.Predicates.Evaluation`: `EvaluationContext`, `OperatorEvaluation` and `Quantification`.

**Namespaces don't follow the layers.** Everything from the binder to the evaluation tree is in one namespace, `Goro.Predicates.Binding`; only the folders separate the layers. The evaluation nodes also sit in `Binding` while their run-time helpers sit in `Evaluation`. This is the same knot as the open question about renaming the "Bound" types. Separately, the semantic tree and the analyses are `public` only so the tests can reach them, since there is no `InternalsVisibleTo`.

## What the error reordering meant

Errors are listed by where they start. The question was what happens when two errors start at the same character, which happens when an error about an inner part shares its first character with an error about the part around it.

The old binder made one pass and found inner errors first, so the inner one was always listed first. After the split, the binder's errors were collected before the analyses' errors. With a stable sort by start alone, a binder error about the outer part jumped ahead of an analysis error about the inner part. Here is the real output now:

```
NUMBER(1.5 < file::duration) > 1
goro: error: Durations count whole seconds only, goro!     ← constants, marks `1.5` (7..10)
goro: error: `NUMBER()` won't take a boolean, goro!        ← binder, marks `1.5 < file::duration` (7..27)
```

Sorted by start alone, these two would have swapped. A second case, using the test catalog, where `flag` is a boolean that isn't definite:

```
STRING((flag) AND ("m")) IS USABLE
old/now:            indefinite-condition on `(flag)`, then boolean-not-convertible on `(flag) AND ("m")`
stage order would give: boolean-not-convertible first
```

The comparison against `main` found 74 such predicates out of about 215,000, all of this kind. Most were `boolean-not-convertible` with `indefinite-condition` (58), `match-subject-not-string` with `indefinite-condition` (8), and a few with fractional or negative unit literals. No error appeared, disappeared or changed text; only the order of same-start pairs moved.

Sorting by start and then by end restores the old order exactly: the shorter span (the inner part) comes first. That rule is now written down in `PredicateCompiler`, rather than falling out of the order the binder happened to visit nodes.

## How the tests are grouped

`tests/Goro.Tests/Predicates/` mirrors the source namespaces: `Syntax`, `Binding`, `Evaluation`, `Identifiers`, `Text`, `Values` and `Diagnostics`. Within `Binding` there are now two kinds of test.

**End-to-end, by topic (unchanged).** These are the files named like `*BindingTests.cs` plus `EndToEndTests` and `ErrorReportingTests`. They go through `PredicateCompiler` via `BindAssert` and look only at the final errors or compiled predicate. They are grouped by language topic, so most span more than one stage:

| File                | Stages it exercises (roughly)                                                 |
|---------------------|-------------------------------------------------------------------------------|
| Identifier, Modifier, Null | binder                                                                 |
| Type                | binder, constants (negative or fractional unit literals)                      |
| Definiteness        | binder (not a condition), cardinality                                         |
| Function            | binder (arity, unknown function, types), constants (FALLBACK default, NUMBER of a literal) |
| Range               | binder (endpoint types), constants (reversal)                                 |
| Pattern             | binder (subject type), patterns                                               |
| Source              | sources                                                                       |
| ErrorReporting      | all of them: how many errors are reported, and in what order                  |
| EndToEnd            | compile, then evaluate                                                        |

**Per stage, new (`Binding/Analyses/`).** `Analyse.Bind(text)` parses and binds a predicate. `tree.Find("COUNT(genre)")` picks out a node by the text it was written as. Each test then runs one stage directly and checks what that stage produced:
- `SemanticTreeTests`: what the binder builds (modifiers folded, number literals standing in for units, identity conversions kept, error nodes), and that it leaves alone the rules owned by analyses.
- `CardinalityTests`, `ConstantsTests`, `PatternsTests` and `SourcesTests`: each analysis's facts and errors, including that each still reports its own errors on a tree the binder already found wrong.
- `LoweringTests`: what lowering produces, and that it reuses the analyses' compiled pattern and prepared range ends rather than redoing them.

`Evaluation/` is a third style. Those tests build evaluation trees by hand (`Evaluation/Support/Bound`) with no compiler involved.

Whether to regroup the end-to-end files by stage is the open question in the Log. Leaving them as they are kept them as an independent check during this change.

## A better namespace layout

The main problem is that one namespace, `Goro.Predicates.Binding`, holds four layers: the binder and semantic tree, the analyses, lowering, and the evaluation tree. Only folders separate them. The evaluation nodes also live apart from their run-time helpers in `Evaluation`. I'd make it one namespace per layer, with each folder matching its namespace:

```
Goro.Predicates               PredicateCompiler, CompiledPredicate   ← the public face: text in, predicate out
Goro.Predicates.Syntax        (unchanged)
Goro.Predicates.Binding       Binder, SemanticTree, Semantic*, BinderDiagnostics, Spelling,
                              SemanticDiagnostics, SemanticDiagnosticCodes
Goro.Predicates.Analyses      Cardinality, Constants, Patterns, Sources, their results and diagnostics, Shape
Goro.Predicates.Lowering      Lowerer (renamed: a class may not share its namespace's name), TypedNodes, PreparedRange
Goro.Predicates.Evaluation    the evaluation tree (BoundExpression … RegexMatch, Not/And/Or, SourceTable)
                              + EvaluationContext, OperatorEvaluation
Values, Text, Diagnostics, Identifiers   (unchanged)
```

What this buys:
- **The pipeline reads off the namespaces.** Syntax, then Binding, Analyses, Lowering and Evaluation, and each layer uses only the ones before it plus the shared ones.
- **"Binding" means what it means in Roslyn's naming:** the binder and the tree it produces. That mostly settles the open question about renaming "Bound". Once the evaluation tree lives in `Evaluation`, the prefix could later be dropped (`Evaluation.Expression<T>`, `Condition`, `Operand<T>`), but that's optional and can wait.

One cycle would remain:
- **`Identifiers` and `Evaluation` reference each other.** `IdentifierDeclaration.Bind` creates an `IdentifierReference`, which holds its declaration. The same cycle exists today between `Identifiers` and `Binding`.
- **It isn't urgent.** It could be broken later by having lowering build the reference.

**Tests** would mirror that layout 1:1:
- **`Binding/`:** `SemanticTreeTests`.
- **`Analyses/`:** the four analysis test files.
- **`Lowering/`:** `LoweringTests`.
- **`Evaluation/`:** unchanged; these tests build evaluation trees by hand.
- **`Compiler/`:** the current end-to-end files, which test the whole compiler rather than the binder.
  - I'd keep them grouped by topic (`RangeTests`, `FunctionTests`, `ErrorReportingTests`, …) and drop the `Binding` suffix, with `BindAssert` becoming `CompileAssert`.
  - Topic grouping is how the spec is organised, so someone asking "how are ranges checked?" finds one file. Splitting them by stage would scatter each topic across several files.
  - This also settles the second open question: keep them by topic, but name them for what they test.
