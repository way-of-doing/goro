# Evaluation of the predicate specification

## Verdict up front

This is a genuinely good spec — better than most shipped query languages get. The null/taint model, the static-error guarantee, the quantifier-nesting decision, and the modifier placement restriction are all correctly reasoned and the rationale doc earns its keep. What follows is not a list of things that are wrong so much as a list of places where the spec has not yet been pushed to the point where an implementer has no choices left, plus a handful of places where two documents disagree.

The important structure in the findings: **most of the awkward individual questions trace back to seven systemic issues.** Four of them are model-description problems (the spec's conceptual vocabulary doesn't quite match its own rules), two are "the cure rewrote something it shouldn't have", one is a genuine hole. Fix those seven and roughly two thirds of the individual items below either vanish or become one-line clarifications.

# Part 1 — Systemic issues

## S1. The bag model has a hole at `null`, and the hole is load-bearing

`rationale.md` designates the bag invariant as *the test for future additions*: "_Every_ value in a predicate is conceptually a bag… A bag of cardinality zero, or one with a single `null` value, cannot appear in the language (plain `null` should be used instead)."

So plain `null` is the stand-in for **both** the empty bag and the singleton-null bag. The rest of the spec then reads it as one or the other depending on which rule you're in:

- `COUNT(null) == 0` (predicates.md:384) — the **empty-bag** reading.
- General operator rule 1 makes `ALL(x) == "a"` **false** when `x` is plain null — the **singleton-null-bag** reading. Under a true empty-bag reading, universal quantification over nothing is vacuously *true*.
- The multivalue section says "a null among a multivalue's values participates in this iteration like any other value" — again, null is a value, not an absence.

Both individual behaviours are the ones you want. The problem is that the *invariant* used to adjudicate future design questions is internally inconsistent, so it will adjudicate wrongly. `rationale.md` itself flags the hazard ("it would then be possible to have `ALL()` vacuously match with an empty bag") without noticing that plain null already occupies that position and has already been given the opposite answer.

**Recommendation.** State the model as: a value is a bag of cardinality ≥ 1, *or* the distinguished absence `null`. Null is **not** a bag. Then `COUNT(null) == 0` is an explicit special case ("COUNT reports 0 for an absent value") rather than a conflicting reading, `ALL(null)` being false follows from rule 1 with no tension, and the invariant that actually matters — cardinality 1 is indistinguishable from a simple value — survives intact and unambiguous. Also fix `rationale.md`'s "_Every_ value is conceptually a bag", which is the sentence that creates the problem.

*Explains:* the COUNT/ISNULL asymmetry, `ALL()` over an absent value, the "can an empty string exist" question (C1), and why `ISNULL` is hard to name (F1).

## S2. "Type" is doing the work of three orthogonal axes

`predicates.md` lists **null** as one of "the types that Goro recognizes", then immediately relies on types being static ("Nothing about a particular file can change the type of an expression"). Those two statements cannot both be true if null is a type. The spec resolves it implicitly — "a file determines only whether a value is present, absent or unusable, and whether it is single or multivalued" — which is exactly the right model, but it is buried in the Errors section rather than stated in the Types section. Ranges and multivalues *do* get "not types themselves" treatment; null does not.

The cost shows up as wording that doesn't parse cleanly:

- "With the exception of numeric literals **and null**, operators… require the operands to have the same type" (:256) — null isn't a type, so it can't be an exception to a same-type rule.
- "It is an error to apply `LITERALLY()` to an operand of any type other than string; **null** and string multivalues are of course still permitted" — mixes an axis (nullability) with a type.
- **boolean** is listed as a type but is positionally restricted in a way no other type is, which is really a statement about the grammar, not the type lattice.

**Recommendation.** One short subsection up front: every value has (a) a **type** from {string, number, bytecount, duration} — statically known; (b) a **cardinality** ≥ 1, or absence — file-dependent; (c) a **taint** flag on an absence. Boolean is a fourth type that only the logical operators and the predicate root accept. Rewrite the three sentences above against that vocabulary.

*Explains:* several wording problems, the `LITERALLY`-on-null confusion, and half of S1.

## S3. Quantifier scope is per-operator, so **no compound operator can be specified by desugaring** — and the spec desugars twice

Because an operand's quantifier is realised by the operator that consumes it, splitting one operator into two logical operators changes the quantifier scope. Two places in the docs do this or plan to:

- **`BETWEEN`** (:140): "the value is considered to be part of the range if and only if `min <= v` and `v <= max` are both true." Read as *per-combination*, this is correct. Read as an AST-level rewrite — which is how it is phrased, and it is phrased before multivalues are introduced — it is wrong: for `v = {0, 20}`, `v BETWEEN 1..10` is false but `1 <= v AND v <= 10` is **true** (each conjunct finds a different witness). An implementer who desugars in the parser produces a subtly wrong operator and no test in `testing.md` would catch it.
- **`IN`** (deferred.md:34): "Can also be implemented as simple syntactic sugar around OR." True existentially (∃ distributes over ∨), **false universally**: `ALL(x) IN (a,b)` is ∀x(x=a ∨ x=b), which is not (∀x x=a) ∨ (∀x x=b). The deferred note records a plan that is incorrect.

**Recommendation.** Write the rule down once, as a constraint on the language rather than a note on two operators: *an operator is a single quantifier scope; multivalue iteration happens at the operator boundary, and no operator may be defined as a rewriting into other operators.* Then restate `BETWEEN` as a single three-way test evaluated once per combination, and correct the `IN` note. This rule will be needed again for `MAX`/`MIN`, for any arithmetic, and for anything set-shaped.

## S4. Within-operator short-circuit over an *unordered* bag makes warnings — and therefore exit codes — nondeterministic

Two statements collide:

- Multivalues are "an **unordered** collection" (:113).
- "an existentially-quantified operand causes the result to be true **as soon as** any one of its values leads to a true result" (:209).

"As soon as" is short-circuit. So for `genre == "rock"` where `genre` is `{"rock", <tainted null>}`, whether a warning is emitted depends on which value the iteration reaches first — and the spec says the collection has no order. Consequences:

- The set of warnings for a given file is implementation-defined, and can change between Goro versions (swap a `List` for a `HashSet`) with no visible cause.
- `--strict-exit-code` returns **10 or 0 nondeterministically** for the same file and the same predicate. That is an observable, scriptable nondeterminism in the one part of the design that exists to be scripted.
- It interacts with the concurrency model: nothing else in the spec makes results depend on scheduling, and this does.

**Recommendation.** Specify that within-operator iteration **does not** short-circuit: every combination is evaluated. Bags are tiny (a handful of tag values), so the cost is nil, and this makes the warning set a deterministic function of (file, predicate) — which is also what makes the rationale's claim that "the set of warnings a predicate is capable of emitting is enumerable before any file is read" testable end-to-end. Keep `AND`/`OR` short-circuiting, which is a different mechanism and is needed for the `ISNULL` guard. The alternative — pin bag order to the order values were read from the file — works too but leaks tag layout into semantics and is harder to test.

## S5. Taint is write-only: it can be reported but never queried, and the sanctioned guard converts warnings into silence

Two halves of one problem.

**(a) The guard silences the warning it was supposed to explain.** The documented idiom is `NOT ISNULL(NUMBER(x)) AND NUMBER(x) > 5`. `ISNULL` is true if *any* value of a multivalue is null, and `ISNULL` never warns, and `AND` short-circuits. So for `x = {"3", "junk"}`: the guard fails, the right operand is never evaluated, the file does not match, and **no warning is emitted at all**. The file is silently skipped despite carrying a perfectly good value — which is precisely the failure mode `predicates.md`:256 identifies as unacceptable ("Goro silently skipping processing of files without providing any notification").

`rationale.md` reasons about this case but only considers the opposite failure (guard passes, warning fires anyway). The conservative choice was correct on the merits; what wasn't noticed is that it trades a *loud* wrong answer for a *silent* one, and that the guard is the only construct in the language that can do that.

**(b) There is no way to ask which files have tainted data.** Taint is observable only as a line on stderr. A predicate cannot select on it: `ISNULL(year)` is true both for "no year tag" and for "year tag full of junk", and `COUNT(year) == 0` is true for both as well. So the tool that exists to be "a powerful, scriptable library query tool" (vision.md:13) cannot answer the single most obvious library-hygiene query — *show me the files whose tags I need to fix* — even though it already computes the answer and throws it away into stderr.

**Recommendation.** Add `ISTAINTED(expr)` (returning true if the value, or any value of a multivalue, is a tainted null; never warns, like its siblings). It is a handful of lines given the machinery already specified, it turns the warning system from a log into a query, and it closes (a) as well: `ISTAINTED(x)` lets a user find and triage the files their guard skipped. This is the single highest-value addition I'd make. Also worth considering: an `ANYUSABLE()`/existential counterpart to `ISNULL`, because today there is **no** way to express "at least one value of `x` is usable" — the modifier restriction (correctly) forbids `ISNULL(ANY(x))`, and the only workaround is the obscure `x == x`, which happens to mean exactly that (and which, incidentally, is not a tautology — worth a sentence somewhere).

## S6. Normalization is specified as a property of values but behaves as a property of operators, and for `~=` it violates its own stated principle

**(a) The concept is split.** `LITERALLY` is described as one of three "modifiers", all of which "set an independent property of **the operand**" (:334). But two sentences later: "it is enough for _just one_ of the operands… to be a `LITERALLY()` value to disable normalization" (:356). That is not an operand property; it is an operator-level flag contributed by either operand. `ALL`/`ANY` genuinely *are* per-operand and independent ("An operand's quantifier applies independently of any other operand's"). So the unified "modifier" concept contains two mechanically different things, and the sentence that describes them together is wrong about one of them.

**(b) `~=` rewrites the pattern after declaring that rewriting patterns is unacceptable.** Rule 4 (:132): "case-folding a regular expression would silently rewrite it, so `~=` leaves the case of both operands alone". Correct. But the *other* half of normalization — NFD-decompose and discard combining marks — is applied to the pattern anyway. That is also silently rewriting the pattern, and it can change what the pattern *means*, not just what it matches: `"e\u0301?"` (optional combining acute) becomes `"e?"`; `"ö{2}"` becomes `"o{2}"`. The stated principle and the specified behaviour contradict each other.

**Recommendation.** Two changes. First, stop calling `LITERALLY` an operand property: describe normalization as an operator mode, set by any operand carrying `LITERALLY`, and keep quantifiers as the per-operand property they are. Consider splitting the two into "quantifiers" and "comparison modes" in the prose even if they share a grammar production. Second, for `~=`, normalize the **subject only** and leave the pattern untouched, which is the only position consistent with rule 4's own argument — the pattern author can write `[eé]` if they want it, and a user who wants marks stripped from the pattern has no coherent use case. Then `LITERALLY` on `~=` means one thing (don't normalize the subject, and match case-sensitively) instead of two.

## S7. "raw" means three different things

`identifiers.md` defines raw namespaces as providing tag data "without interpreting it", yielding "the text as recorded in the file", with the raw testing class titled "Fidelity of the raw namespaces". Three rules then depart from that in different directions:

1. **Value-preserving but name-translated.** `id3v2::raw::TDRC` on a v2.3 file reads a frame that is *not in the file* (v2.3 stores `TYER`), and every v2.2 3-character frame is likewise reached under its v2.4 name. So "raw" preserves the value but not the on-disk naming.
2. **Synthesized values.** `TXXX`/`COMM`/`WXXX` resolve to `"[MOOD] calm"` (:204) — a string that exists nowhere in the file, invented by Goro, in the namespace whose entire promise is fidelity. It is also not unambiguously parseable (a description containing `]`, or a value beginning with `[`), so a user cannot reliably split it back apart. And it means `id3v2::raw::TXXX == "5"` can never match.
3. **Semantically identical to the cooked namespace.** For APE, "for every identifier other than `track` and `year`, the `ape::raw` counterpart resolves to exactly the same thing" — so most of `ape::raw` exists only for symmetry.

Plus the trimming question (C4). None of these is wrong as behaviour; the problem is one word carrying four different promises, in a namespace family users will reach for precisely when they need to trust it.

**Recommendation.** Redefine "raw" explicitly as **"uninterpreted value, string-typed, never tainted"** — dropping the fidelity language — and add a short "what raw does *not* promise" list: frame naming is unified to v2.4, values are trimmed (or not — decide), and description-bearing frames are synthesized. For (2) specifically, I'd resolve description-bearing frames to the **value alone** in the raw namespace and leave description-addressing to the deferred two-part identifier, rather than ship an invented encoding that a later feature will have to deprecate.

# Part 2 — Contradictions between documents

**C1. Can a string value be the empty string?** `predicates.md`:117 says `artist` may resolve to "the empty string if that's what the tag records". `testing.md` requires that a field "present but empty, and one that is present but only whitespace… **must yield an untainted null**", for every namespace including raw. `identifiers.md` specifies empty-after-trim → null only for date- and track-shaped data. These cannot all hold. It matters a lot: if empty → null, then `artist == ""` is unsatisfiable, `ISNULL(artist)` cannot distinguish "no tag" from "empty tag", and **there is no way to find files with empty tags** — a mainstream library-cleanup query. Decide, state it once for all string-typed identifiers, and say what happens to a value that is whitespace-only *after* trimming versus one that was empty to begin with.

**C2. `track` is used four times as a bare global identifier but does not exist.** The global namespace is **closed** and contains only `artist`, `album`, `genre`, `title`, `year`. Yet `predicates.md` writes `track > id3v2::raw::XXXX` (:256), `FALLBACK(track, 0)` and `NOT ISNULL(track)` (:264), and `track == 1` (Deduplication section). All four are static errors as specified. Either add `track` to the global namespace — which you almost certainly want; it is the most-filtered field after artist and every format namespace has it — or rewrite the examples.

**C3. The grammar forbids modifiers on `BETWEEN`'s range, the prose implies they're allowed.** Prose: a modifier may be applied "to an operand of a comparison, **range**, or regex operator". Grammar: `comparison_tail = "BETWEEN" range` and `range = literal ".." literal`, so `x BETWEEN LITERALLY("a").."b"` does not parse. Reconcile (the prose is defensible if "operand of the range operator" means only the left side, but it doesn't read that way).

**C4. Trimming scope is defined in one namespace and used everywhere.** "Every value is trimmed of leading and trailing whitespace before it is used" (identifiers.md:175) sits under **Id3v2 → Common behaviour**. Is `vorbis::artist` trimmed? Is `ape::"album artist"`? Is `id3v2::raw::TIT2`? The answer changes what `NUMBER(" 5")` does and whether raw namespaces are faithful. Lift the rule to a shared Definitions section and state explicitly whether raw is exempt.

**C5. `predicates.md` SYNOPSIS advertises `--filter` on every command;** only `list` accepts it. `deferred.md` acknowledges the gap, so this is just a doc-sync item — but the synopsis is the first thing a reader sees.

**C6. Exit code 10 makes exit code 11 almost unobservable.** `rationale.md` defends warnings-not-failing on the premise that "for the collections Goro is built for, **warning is the normal case** rather than the exceptional one". `exit-codes.md`:91 then says warnings take precedence over "nothing matched". Combine the two: on the collections Goro is built for, a run that matched nothing will return `10`, not `11`, essentially always. The code the rationale defends as "unambiguous and it never fires spuriously" is masked by the code it defends as ordinary. The two arguments are individually sound and jointly self-defeating. Options: make the informational codes additively combinable (e.g. a bitmask, 16 = warned, 1 = no match), add a distinct code for "warned and matched nothing", let `--strict-exit-code` take a list of conditions to report, or simply invert the precedence — the query-level fact is the rarer and more actionable one.

**C7. `rationale.md`:50 claims dedup makes "the number of warnings match the number of things that are actually wrong".** Per-source dedup means a file with three junk `DATE` fields produces **one** warning (the dedup table's `m > 1` row confirms this). The claim is one warning per bad *identifier* per file, not per bad datum. Worth correcting because someone will later "fix" the dedup rule to make the claim true.

# Part 3 — Footguns

**F1. `ISNULL` is named for a thing it does not test.** For multivalues it means "contains at least one unusable value". The semantics are right (rationale argues it well); the name is wrong, and the name is what users reason with at 2am. `NOT ISNULL(x)` reading as "x is not null" invites exactly the misreading that makes S5(a) bite. Rename now while it's internal — `HASNULL(x)` makes `NOT HASNULL(x)` read as "no nulls in x", which is precisely correct, and it stops implying a relationship to `COUNT(x) == 0` that the spec then has to spend a paragraph denying.

**F2. Regex literals need every backslash doubled, and the spec never says so or shows it.** `escape = "\" ( '"' | "\" )` — a backslash must be followed by `"` or `\`. Therefore `"\d{4}"` is a **syntax error** and the user must write `"\\d{4}"`. Nearly every real regex needs `\d`, `\s`, `\.`, `\(` or `\\`. Not one regex example in the docs contains a backslash, so the first thing a user writes will fail with a message about an invalid escape in a string, not about their regex. Add an explicit paragraph plus a worked example (`artist ~= "\\(live\\)$"`), and consider a raw-string form for patterns — `~=` is the only place where the collision is systematic.

**F3. Numeric-literal polymorphism reaches *string*, one-directionally.** Rule 3 says a numeric literal converts to "the decimal string representation" for a string operand. So `year == "2000"` is an **error** (string literal vs number) while `id3v2::raw::TRCK > 9` is **accepted** and silently performs a string comparison in which `"10" > "9"` is false. Rule 3 exists to make `file::size BETWEEN 60..120` work; the string direction is collateral and gives the raw namespaces — every one of which is string-typed — a silent numeric-looking comparison. Consider restricting the polymorphism to bytecount and duration, and requiring `STRING(5)` or `"5"` for the string case. You lose nothing anybody wants and remove the asymmetry where the *more common* user error (quoting a number) errors while the rarer one succeeds wrongly.

**F4. A typo in an open namespace is silent, forever.** `vorbis::artistt` is never an error and matches nothing. `architecture.md` promises "an unresolvable identifier should suggest the closest defined one" — which can only apply to closed namespaces. So the spec's whole "every error is reported before any file is processed" posture has one hole, and it is in the namespaces users will use most. Exit code 11 partially covers it. Worth considering: an end-of-run notice when an identifier resolved to null for *every* file examined, or a `--explain` mode. Cheap, and squarely in the Pit-of-Success spirit.

**F5. `ALL(a) < b` does not mean what it reads as.** Under quantifier nesting it is ∀a∃b, i.e. "max(a) < max(b)". `rationale.md` works this out for `a > ALL(b)`; `predicates.md` illustrates the ∀∃ case only with `==`, where it reads naturally as containment, and never warns that for the *ordering* operators the same rule produces an aggregate comparison. Add the ordering example to `predicates.md` with the max/min gloss — the rationale doc is not where a user will look.

**F6. The polymorphic-number unit is easy to get wrong in the direction that doesn't error.** `file::size > 1000` is 1000 **bytes**; `file::duration > 90` is 90 **seconds**. Both are reasonable; neither is stated prominently, and the type system cannot catch a user who meant kilobytes. One sentence in rule 3 plus one example each.

**F7. `COUNT` counts resolved values, not tags.** `COUNT(id3v2::genre) > 1` is **true** for a single `TCON` frame holding `(17)Post-Rock`, because genre resolution produces two values from one frame. The doc presents `COUNT(genre) > 1` as "is true if and only if `genre` is a multivalue", which is accurate but invites reading it as "has more than one genre tag". Note the distinction where `COUNT` is defined.

**F8. Predicate operand order determines I/O cost, and nothing says so.** `file::size > 10mb AND artist == "x"` reads tags only for large files; reversed, it reads tags for everything, and the global `artist` facade may consult up to four tag formats per file. Since `AND` is specified as strictly left-to-right with no reordering permitted (correctly — the `ISNULL` guard depends on it), the user is the optimizer and doesn't know it. Add a short performance note: cheap predicates first, `file::` identifiers are free, tag identifiers are not. Also worth stating as an architecture requirement that the pipeline planner opens only the data sources the predicate's identifier set actually mentions.

**F9. The global facade can hide the very data problem the warning system exists to surface.** If a file's Vorbis `DATE` is junk but its Id3v2 `TDRC` is fine, `year` resolves to the good value and the taint is discarded with no warning. Correct behaviour for a facade; worth one explicit sentence, because it is the interaction that makes `deferred.md`'s "should a warning name the tag format" question matter more than it looks.

# Part 4 — Blanks

**B1. What happens when a *file* cannot be read?** `predicates.md`'s Errors section gives an exhaustive-sounding list of per-file conditions — "a value that is missing or cannot be interpreted, a regular expression arriving from tag data that turns out not to be valid, and a match that exceeds the matching timeout" — and I/O failure is not among them. But the whole design premise is a 100K-file collection with bit rot in it. Is an unreadable, truncated, or non-audio file a warning-and-continue, or does it produce exit code 1 ("the run started but could not be completed"), which would violate the never-abort-midway constraint? This is the largest genuine hole in the spec, and it is arguably more important than anything in Part 3 because it is the scenario the tool was built for. I'd add a fourth per-file condition category, decide whether it warns or gets its own channel, and give it its own informational exit code — conflating "one tag field is junk" with "I could not read this file at all" loses the more serious signal.

**B2. What is a number, numerically?** Never stated. Double, decimal, rational? It matters for: `1.4kib` being "exactly 1433.6 bytes" (not exactly representable in binary floating point, so the exactness claim is technically false); `STRING(number)`'s output; whether `NUMBER(STRING(x)) == x`; and overflow on `999999tb` or `999999999h`. `System.Decimal` makes every claim in the doc literally true and has ample range for file sizes and durations; that's what I'd specify.

**B3. `STRING()`'s exact output format.** "Its decimal string representation" is not a spec. Culture (presumably invariant — say so), trailing zeros (`STRING(1.50)`), exponent notation for large values (`"1E+21"` would not round-trip through `NUMBER()`). One sentence pinning it to invariant culture, no exponent, shortest round-trippable.

**B4. Can `file::duration` / `file::size` be tainted?** `identifiers.md` gives no taint rules for the `file` namespace. A file whose audio stream is corrupt so that duration cannot be determined is textbook "present but uninterpretable" — i.e. tainted — but nothing says so. Related to B1.

**B5. No cross-format fallback can be expressed.** `FALLBACK`'s default must be a **literal**, `COALESCE` was deliberately removed, and the global facade is **closed** with five names. So "prefer `ape::"album artist"`, else `vorbis::albumartist`" — a completely ordinary want — cannot be written at all, for any field outside those five (albumartist, composer, disc number, comment, track…). The only route is `(NOT ISNULL(a) AND a == "x") OR (ISNULL(a) AND b == "x")`, which evaluates `a` twice and does not generalize. `rationale.md` explains why `COALESCE` went (deferred.md:38, and the reasoning is sound) but neither doc explains why `FALLBACK`'s default must be a literal, which is the first thing a reader will try to break. Add the Q&A entry, and consider either widening the global namespace or revisiting the literal-only restriction now that the taint-audit objection is understood.

**B6. Range endpoints must be literals, unexplained.** `year BETWEEN x..y` is impossible; so is `year BETWEEN FALLBACK(x,1900)..2000`. Nothing in `rationale.md` addresses why. It may well be deliberate, but it should be recorded as a decision rather than read as an oversight.

**B7. Mixed-type range endpoints are rejected even when one is a polymorphic numeric literal.** `file::size BETWEEN 60..120kb` is an error, while `60..120` and `60kb..120kb` both work. Letting a numeric-literal endpoint adopt the other endpoint's type is a two-line change and removes a surprise.

**B8. The static `min > max` check is not well-defined for strings.** Whether `"B".."a"` is valid depends on whether the comparison is normalized, which depends on whether the *other* operand carries `LITERALLY` — a modifier on the left-hand side of the `BETWEEN`. So a "static" range check has to consult a modifier elsewhere in the expression. Specify which comparison the endpoint check uses (I'd say: the same one the operator will use, and say explicitly that this means the left operand's modifier participates).

**B9. Warnings have no machine-readable form, and the JSON shape forecloses one.** Warnings are prose on stderr; `--strict-exit-code` reports only *whether* a run warned. A user who wants to act on warnings across 100K files must parse English. Meanwhile `list -o json` emits a **top-level array**, so a `{"results": […], "warnings": […]}` envelope cannot be added later without breaking every consumer. That's a compatibility decision being made by omission, right now, and it's free to change today. At minimum: pin a stable one-line warning format and state that each warning is written atomically.

**B10. Output ordering is unspecified.** With a concurrent pipeline over 100K files, nothing says whether `list`/`hash` output follows input order. For the headline use case — hashing a library twice and diffing to find bit rot — stable ordering is the difference between `diff` and `sort | diff`. Adjacent to predicates, but worth settling in `pathspecs.md` or the command docs.

*Minor blanks:* `--filter=''` (empty predicate) behaviour; `--filter` given twice; whether a pathspec that matches nothing while others match warrants a warning (code 12 only covers "no files at all").

# Part 5 — Where the cure may be worse than the disease

**P1. Normalizing the regex pattern.** Covered in S6(b). The cure for "the user didn't type the umlaut" rewrites the user's pattern, by the same argument the spec uses to refuse case-folding it. Strip marks from the subject only.

**P2. Numeric-literal polymorphism reaching string.** Covered in F3. The cure for `BETWEEN 60..120` enabled silent string-vs-number comparison across every raw namespace.

**P3. `ISNULL` = "any null".** Covered in S5(a). The cure for guard-leakage means the guard now silently skips files instead of warning about them, and (with the modifier restriction) leaves no way to write the existential guard. The semantics are still right; the missing piece is `ISTAINTED()` to make the skipped files findable.

**P4. Whole-second durations — the reproducibility half of the argument doesn't hold.** Truncation genuinely earns its keep by making `==` expressible; that argument is correct. But `rationale.md` also claims it makes results reproducible across decoders, and it doesn't: it moves decoder disagreement from *every* comparison to the integer boundaries, where it is still fully present. A file whose true length a decoder reports as 245.0004s versus 244.9996s truncates to 245 versus 244, and `file::duration == 4m5s` flips. Truncation concentrates the wobble rather than removing it. I'd keep the design and drop the reproducibility claim to "reduces" rather than "does not wobble" — or note that reproducibility comes from pinning the TagLibSharp version, which is where it actually comes from.

**P5. `--strict-exit-code` bundles three orthogonal signals behind one boolean.** Covered in C6. A caller who wants "fail if nothing matched" cannot get it on a collection that warns — which is, by the design's own premise, all of them.

# Part 6 — Grammar and lexical defects

**G1. The grammar is formally ambiguous for `ALL(x)`, and the doc's claim about it is therefore wrong.** In an `operand` position, `ALL(genre)` matches both `modifier "(" operand ")"` and `primary → function_call`. Outside an operand position — as a function argument, say — `COUNT(ALL(genre))` matches `function_call` and is **grammatically well-formed**; it is rejected only by the static constraint "a `function_call` names an existing function". So predicates.md:468's claim that the placement restriction "is imposed by the grammar rather than by a rule laid on top of it" is not accurate: it is imposed by exactly such a rule, which is also why the modifier names had to be reserved (as the Reserved words section says). Either fix the claim, or make it true by excluding the three modifier names from `name` in `function_call`.

**G2. The clock duration form caps its leading field at 59, rejecting the conventional spelling of long durations.** `two_digits` is constrained to 0–59 in *both* groups, so `90:00` — how every player displays a 90-minute file — is a syntax error, while `90m` is fine and `250:00:00` is fine because the *hours* field is unbounded. Let the leading field be unbounded in both forms.

**G3. `1:59` does not parse.** `two_digits` is exactly two digits, so minutes below 10 must be written `01:59`. Users will write `1:59` constantly. Either accept one-or-two digits in the leading position, or make sure the diagnostic says "write 01:59" rather than "unexpected token".

**G4. The unit form has no field bounds while the clock form does.** `1h100m` (= 2h40m) and `100s` are legal; `01:90` is not. Probably intentional, entirely undocumented. One sentence: unit-form fields are unbounded and additive.

**G5. Lexing rule is never stated.** The spec leans on `10kb` and `1h10m` being "single tokens" and on `1..100` versus `1.` but never says the lexer takes the longest valid literal (maximal munch). Without it, `5mb` versus `5m`+`b`, and `1h10mb`, are underdetermined. State it.

**G6. Negative numeric literals can convert to bytecount and duration, which have no negative values.** `file::size > -5` and the range `-5..5` as a bytecount range are both legal per the rules and can never be meaningful. Either reject a negative numeric literal when it converts to bytecount/duration (static, trivial), or note that it's harmless.

**G7. Strings have only two escapes, so several characters are unwritable.** `escape = "\" ( '"' | "\" )` means no `\n`, `\t`, `\uXXXX`. A literal tab or newline is technically admitted by `string_char` but unwritable from most shells. For a tool used to find tags with junk whitespace in them, and given F2, this is worth a decision rather than an omission.

**G8. The `::and` escape hatch is currently dead.** "If an identifier happens to coincide with a keyword, it can still be referenced by explicitly qualifying it, e.g. `::and`" — but the global namespace is **closed** and will never contain `and`, and every qualified position is already unambiguous (`ape::all` needs no escape). The provision can only ever matter if Goro itself names a global identifier after a keyword, which the spec separately says it won't do for functions. Keep it as forward-looking if you like, but say that's what it is.

*Also:* the grammar admits reserved modifier names as namespace and identifier parts (`all::x`, `ape::any`), which is fine and unambiguous but unstated. And `ALL(ANY(x))` is resolved silently by "outermost wins" — contradictory quantifier stacking is statically detectable and has no legitimate use; I'd make it an error and allow only redundant stacking.

# Part 7 — Overclaims

**O1. "Removal of all diacritics" is not what the rule does.** NFD + discard combining marks handles ö, ü, é, å, ñ. It does **not** touch ø, ł, đ, ð, þ, ß, ı, æ, œ — none of which decompose. So `artist == "orsted"` will not match "Ørsted", `"crass"` will not match "Craß", and Turkish dotless ı will not match `i`. The promise as written will be read as "accent-insensitive matching works", and for Scandinavian, Polish, Icelandic, German and Turkish catalogues it partly won't. State the rule as what it is ("Unicode combining marks are removed after NFD decomposition") and list the known non-matches, or move to compatibility decomposition plus an explicit fold table if you want the stronger promise.

**O2. "The order in which the operands were written never affects the result of an operator" (:211) is false as written.** `a < b` is not `b < a`; `~=` has fixed asymmetric roles (left = subject, right = pattern), and its own section then says multivalue `~=` follows "the ordinary quantifier and nested iteration rules". The intended claim is narrower and worth stating precisely: *which side an operand is written on does not change the quantifier nesting*, so `ALL(a) == b` ≡ `b == ALL(a)` and `a < ALL(b)` ≡ `ALL(b) > a`. As it stands an implementer could read it as a commutativity guarantee.

**O3. "Comparison between values of type number, bytecount, and duration are trivial"** — true once B2 is settled, not before.

**O4. The reproducibility half of the duration argument.** See P4.

**O5. `rationale.md`'s warning-count claim.** See C7.

## User

Let's brainstorm around S2 a bit. It strikes me that the passage a "file determines only whether a value is present, absent or unusable, and whether it is single or multivalued" is possibly hinting at a big opportunity.

What if we made this an explicit dimension of the type system?

Forget about null completely. A value has a static type. It also has a tri-state dynamic aspect: present, absent, or unusable. Absent is close to current untainted null, unusable is the tainted null. It follows that a multivalue, which is itself necessarily always present whenever encountered, cannot hold absents. We can add IS USABLE and similar tests and guards.

## Claude

This is the right thread to pull. That sentence is currently the most load-bearing sentence in the whole spec and it's sitting in the Errors section as an aside. Promoting it to the definition changes the spec less than you'd fear and buys more than I expected when I started working it through.

Let me first pin down the structure precisely, because your formulation has a consequence you didn't state, and it's the one that pays for everything.

---

# 1. The structure, stated precisely

Your tri-state isn't quite flat. Work out where each state can live:

- **absent** is a property of a *whole value*. "There is nothing here."
- **unusable** is a property of an *individual occurrence*. "There is something here and I can't interpret it."

So the real structure is:

> A value has a static **type**. Dynamically, it is either **absent**, or a bag of one or more occurrences, each of which is **usable** or **unusable**.

Which means the cardinality ladder finally closes:

| Cardinality | What it is |
|---|---|
| 0 | **absent** — the empty bag, and the only empty bag |
| 1 | a simple value, usable or unusable |
| n ≥ 2 | a multivalue, each occurrence usable or unusable |

**This repairs S1 outright.** Today plain `null` is forced to be both the empty bag and a singleton-null bag, and the spec reads it one way for `COUNT` and the other way for rule 1. Under your model absent *is* cardinality zero, with nothing else pretending to be it, and the cardinality-1 invariant gets a stronger statement than it has now: *no construct distinguishes a bag of cardinality 1 from a simple value, and absent is the unique value of cardinality 0.*

I'd also adjust the vocabulary one notch: call the states **usable / unusable / absent**, and keep "present" as a prose umbrella for usable-or-unusable. Then every state name is directly testable and the tests read like their states. ("Present" as a state name plus `IS USABLE` as the test invites exactly the confusion the redesign is trying to kill.)

## The consequence you didn't state: absence must be *elided*, not stored

If a bag cannot hold absents, then every rule in `identifiers.md` that currently maps present data to an untainted null becomes illegal as written, because those rules fire per occurrence. Each one has to be re-decided as one of: yields a **usable** value, yields an **unusable** value, or the occurrence is **elided** (cardinality drops, and drops to 0 → absent if it was the only one).

That's not a defect — it's a forcing function, and it's where a lot of the value is, because the cases it forces are precisely the ones already sitting open in your docs (C1, B4, and two `deferred.md` entries). More on that in §5.

---

# 2. What the model buys — the three exemptions collapse into one rule

This is the biggest win and I didn't see it until I worked the warnings through.

Today's consume rule is *"operators always consume, since they always produce a boolean, so an operator given a tainted null always warns"* — and then `ISNULL()` and `FALLBACK()` need bespoke carve-outs, and `COUNT()` needs a Q&A entry explaining why it *doesn't* get one. Three exceptions, because the rule is stated in terms of **what a function returns**.

Restate it in terms of **what a function reads**:

> Consuming an unusable value means producing a result derived from **the content** of that value. Only consuming warns.

Now watch the exceptions evaporate:

- `NUMBER()`, `STRING()` map unusable → unusable. They don't derive anything from the content. Silent. *(Same as today, same reason.)*
- `COUNT()` reads **cardinality**, which is knowable without interpreting any occurrence. Silent — and today's Q&A explaining why COUNT warns can be deleted. `COUNT` becomes a pure cardinality query, which is what its name always claimed.
- `FALLBACK()` substitutes *instead of* interpreting. Silent. Not an exemption — a consequence.
- A state test reads **state**, not content. Silent. Not an exemption — a consequence.
- Comparison, range and regex operators interpret content. They warn. Unchanged.

One rule, zero carve-outs, and the rule is more intuitive than the one it replaces. If nothing else came of this redesign, I'd do it for this.

Note the one real behaviour change hiding in there: **`COUNT` of a single unusable occurrence becomes 1, not 0.** Today a junk year tag counts as 0 because a tainted null *is* null. Under the new model there is one occurrence; it just can't be read. That's strictly better — `COUNT` stops conflating "no tag" with "one junk tag" — and it makes `COUNT(x) == 0` exactly equivalent to `x IS ABSENT`, so the two never disagree.

# 3. The state tests, and why they must be operators

## They cannot be functions

`rationale.md` (correctly) bans modifiers inside function arguments, so `ISUSABLE(ALL(x))` is unwritable by construction. But quantifier choice is *exactly* what a guard over multivalued data needs to express. So a function form cannot carry the feature. The tests have to be **operators**, taking an `operand` — which is the one position where modifiers already live.

That's a pleasing forcing argument: the modifier restriction, which looked like a pure cost, turns out to dictate the right syntax here.

```ebnf
comparison_tail = comparison_op operand
                | "BETWEEN" range
                | "~=" operand
                | "IS" state ;          (* new *)

state           = "USABLE" | "UNUSABLE" | "ABSENT" ;
```

Non-associative, precedence level 2 with the other comparisons, result type boolean. `ALL(x) IS USABLE` parses with zero other grammar changes, and `ALL(NUMBER(x)) IS USABLE` works because modifiers already go outside function calls.

## All three tests earn their place — here's the proof

With the default existential quantifier:

| value of `x` | `x IS ABSENT` | `x IS USABLE` | `x IS UNUSABLE` |
|---|:---:|:---:|:---:|
| absent | **T** | F | F |
| {usable} | F | **T** | F |
| {unusable} | F | F | **T** |
| {usable, unusable} | F | **T** | **T** |
| {unusable, unusable} | F | F | **T** |

And with `ALL()`:

| value of `x` | `ALL(x) IS USABLE` | `ALL(x) IS UNUSABLE` |
|---|:---:|:---:|
| absent | F | F |
| {usable, unusable} | F | F |
| {unusable, unusable} | F | **T** |

No test is derivable from the others, because absent makes both quantified forms false and therefore breaks the De Morgan duality that would otherwise collapse them. Six readable combinations:

| You want | You write | Today |
|---|---|---|
| a conservative guard: every occurrence readable | `ALL(x) IS USABLE` | `NOT ISNULL(x)` |
| an optimistic guard: at least one readable | `ANY(x) IS USABLE` | **unwritable** |
| the tag is not there at all | `x IS ABSENT` | **unwritable** |
| some occurrence is junk — *find files to fix* | `ANY(x) IS UNUSABLE` | **unwritable** (this was my `ISTAINTED()` suggestion) |
| every occurrence is junk | `ALL(x) IS UNUSABLE` | **unwritable** |
| the tag is there and readable | `NOT (x IS ABSENT) AND ALL(x) IS USABLE` | `NOT ISNULL(x)` |

Three of the five previously-unwritable rows are things I flagged as gaps in the review (S5a, S5b, C1's "find empty tags"). They all fall out of one operator.

## Skip `IS NOT`

It's tempting and it's redundant: `x IS NOT USABLE` ≡ `NOT (ALL(x) IS USABLE)` and `ALL(x) IS NOT USABLE` ≡ `NOT (ANY(x) IS USABLE)`. Because the quantifiers are explicit and dual, `IS NOT` adds nothing — while adding a second `!=`-vs-`NOT ==` trap to explain. Leave it out; it's the reversible direction.

## Default quantifier: existential, same as everywhere else

This one's worth arguing rather than asserting, because it reverses today's `ISNULL` choice.

`ISNULL` had to be conservative because the other reading was *unwritable* — `rationale.md` says so: "the guard would only ever work on data that happened not to be multivalued." Once `ANY()`/`ALL()` are available on the operand, that constraint is gone, and the consistency prize is large: **every operand in the language is existential unless wrapped in `ALL()`, with no exceptions.** Today `ISNULL` is the sole exception and costs a paragraph ("Unlike most functions, `ISNULL()` does not apply to each value of a multivalue individually").

The clinching argument is the failure direction. With a conservative default, a wrong guard **silently skips** files — that's S5(a), where `NOT ISNULL(NUMBER(x)) AND NUMBER(x) > 5` drops a file with a perfectly good value *and emits no warning*, because `ISNULL` is silent and `AND` short-circuits. With an existential default, a wrong guard lets the unusable value through to an operator, which **warns**. Loud-wrong beats silent-wrong for this tool, and silent-wrong was the thing the whole taint design exists to prevent.

So: `x IS USABLE` means "some occurrence is readable", and the doc says plainly that a conservative guard is spelled `ALL(x) IS USABLE`.

# 4. The draft spec text

## Replacing the Types section

> ### Values
>
> Every value in a predicate has a **type**, which is fixed by the predicate's text and never depends on the file being examined: `string`, `number`, `bytecount`, or `duration`. The type determines which operations are allowed and how their results are computed, and because it is static, every type error in a predicate is reported before any file is opened.
>
> A file determines two further things about a value, neither of which is part of its type.
>
> The first is its **cardinality**. A value is either **absent**, meaning the file holds nothing for it, or it is a bag of one or more occurrences. A bag is unordered and its occurrences are not deduplicated, so the same datum recorded twice occurs twice. A bag of exactly one occurrence is indistinguishable from a simple value: no construct in the language can tell them apart, and everything this document says about simple values holds unchanged for a bag of cardinality one. Absent is the only value of cardinality zero — there is no such thing as an empty bag distinct from absence.
>
> The second is the **state** of each occurrence in the bag. An occurrence is **usable** when its data can be interpreted as the value's type, and **unusable** when the data is there but cannot. A tag field holding `"nineteen ninety one"` where a year is expected is one unusable occurrence, not an absent one; the distinction matters because unusable data is a defect in the file worth reporting, whereas absent data is ordinary. An unusable occurrence behaves like a usable one in no respect except that using it produces a warning.
>
> Absence is a property of a whole value and unusability is a property of an occurrence, so **a bag never contains absences**: an occurrence that is not there is not an occurrence. Where a rule below would discard an occurrence entirely, it reduces the value's cardinality, and a value all of whose occurrences are discarded is absent.
>
> **boolean** is a fifth type, and the only one with no dynamic aspect: a boolean is always a single usable value. Booleans are produced only by the comparison, range, regex, state-test and logical operators, and may appear only as operands of `AND`, `OR` and `NOT` or as the predicate as a whole.

## Replacing general operator rule 1

Today's rule 1 is one sentence doing two jobs, which is why the Multivalues section has to patch it later. Split it:

> 1. **An absent operand makes a comparison, range, or regex operator false**, whatever its other operands are, and the operator's iteration over any multivalue operand does not run. So if a file carries no Id3v2 tag, `id3v2::track == 5` and `id3v2::track != 5` are *both* false. This rule does not apply to the state-test operator `IS`, whose purpose is to observe absence, nor to the logical operators, whose operands are booleans and therefore never absent.
> 2. **An unusable occurrence makes any combination containing it false**, and using it emits a warning. Under the default existential quantifier an unusable occurrence therefore simply fails to contribute a match; under `ALL()` a single one is enough to make the operator false.

And then, in the Multivalues section, the rule that has to be written down explicitly and cannot be derived:

> Because absence is the value of cardinality zero, it would be consistent with ordinary quantifier semantics for `ALL(genre) == "rock"` to be *vacuously true* for a file with no genre at all. Rule 1 makes it false instead. This is deliberate: a predicate asking that every genre be rock is asking about genres, and a file with none is not a file that satisfies it. Universal quantification in Goro is non-vacuous, and it is non-vacuous because absence is intercepted before iteration rather than because the quantifier is unusual.

That paragraph is the single most important addition. It is also the answer to the question `rationale.md` currently defers ("it would then be possible to have `ALL()` vacuously match with an empty bag") — the empty bag has arrived, and the answer is written down.

## The warning rule

> A warning is emitted when an unusable occurrence is **consumed**. Consuming means producing a result derived from the *content* of the occurrence. An operator that compares, matches or ranges over it consumes it. A function that maps it to another unusable value — `NUMBER()`, `STRING()` — does not: it passes the value along, keeping the source it was born with. `COUNT()` reads cardinality and `FALLBACK()` substitutes for the occurrence rather than reading it, so neither consumes. A state test reads state, not content, and never consumes. A modifier computes nothing and never consumes; applying one leaves the following operator as the consumer.

Everything else about warnings — birth, source, per-file per-source dedup, stderr, exit code 10 — is untouched. The taint flag becomes the state itself, so `predicates.md`'s "plain null versus tainted null, behaving identically in every respect but one" disappears: those were two states wearing one type's clothing.

## Migration table

| Today | Under the new model |
|---|---|
| `NOT ISNULL(x)` | `ALL(x) IS USABLE` |
| `ISNULL(x)` | `NOT (ALL(x) IS USABLE)` |
| `NOT ISNULL(NUMBER(x)) AND NUMBER(x) > 5` | `ALL(NUMBER(x)) IS USABLE AND NUMBER(x) > 5` |
| `COUNT(x) == 0` | `x IS ABSENT` |
| `COUNT(x) > 1` | unchanged — "is multivalued" |
| `FALLBACK(x, 0)` | unchanged |
| — | `ANY(x) IS UNUSABLE` — find files whose tags need fixing |
| — | `(year IS ABSENT) OR year > 1990` — treat missing as pass, junk as fail |

# 5. The decisions the model forces — and closes

Every rule that currently produces an untainted null from data that *exists* has to be re-decided. Here is the full list from `identifiers.md`, with what I'd choose:

| Case | Today | Proposed | Why |
|---|---|---|---|
| Empty / whitespace-only field, **string**-typed identifier | untainted null (`testing.md`) or `""` (`predicates.md:117`) — **contradictory** | **usable `""`** | Resolves C1 in favour of `predicates.md`. An empty string is perfectly interpretable *as a string*. Makes `artist == ""` work and "find my empty tags" writable — a mainstream cleanup query that is impossible today |
| Empty / whitespace-only field, **number**-typed identifier (`id3v1::year`, `*::track`) | untainted null, by explicit special case | **unusable** | One rule instead of a special case: data exists, cannot be read as a year, therefore unusable. **Cost: an empty year frame now warns where it didn't.** See below |
| APE item flagged **binary** (`Cover Art (Front)`) | untainted null | **unusable** | Closes `deferred.md`'s "distinguishing tag data that is not text from tag data that is absent". For a string-typed identifier, unusable can only mean "present but not text", so `ape::"cover art (front)" IS UNUSABLE` *is* "this file has cover art" |
| Id3v2 `APIC` and other genuinely binary frames | no identifier defined | **unusable** | Same; `id3v2::APIC IS UNUSABLE` becomes a real query, and `testing.md`'s "scenarios deliberately not covered" section can shrink |
| `file::duration` on a file whose audio stream can't be read | unspecified (**B4**) | **unusable** | Answers B4, and warning here is genuinely useful given the tool's purpose |
| Frame absent from the file (`id3v2::TYER` on the v2.4 view) | untainted null | **absent** | Unchanged in substance |

**The empty-numeric-field call is the one worth arguing over.** The alternative is elision — treat an empty field as carrying no data, so it contributes no occurrence, and a value all of whose occurrences were empty is absent. That preserves today's warning volume exactly. It costs an elision rule and one observable wrinkle: `COUNT(vorbis::year)` and `COUNT(vorbis::raw::date)` would then disagree for a file with DATE fields `"1991"` and `""`, because the raw namespace is string-typed and keeps the empty one.

I lean **unusable** (no elision rule at all, one uniform rule, and an empty `TDRC` frame genuinely is junk data you'd want to know about), but it is a judgement call about warning noise on real collections and you know your collections. If the noise turns out to be bad, elision is a strictly-later change that only ever *removes* warnings, so this is the reversible direction too.

## The global facade gets a one-line definition

Today's four-bullet best-effort rule plus the bespoke taint-carry sentence becomes a join over the state lattice `absent < unusable < usable`:

> A global identifier takes the value of the strongest-ranked format whose value is not absent. If every format is absent, the result is absent — unless some format's value was unusable, in which case the result is unusable, so that a defect is never silently discarded when nothing usable was found.

Same behaviour as specified today, derived rather than asserted.

# 6. What this costs, honestly

**The vocabulary pass is real work.** Every "resolves to null" and "tainted null" in `predicates.md` and `identifiers.md` changes; `testing.md`'s empty-field scenario row inverts; `rationale.md` needs four Q&A entries rewritten (the `ISNULL` one, the `COUNT` one, the multivalues invariant, and the modifier one whose sharpest argument — that `NOT ISNULL(ALL(x))` reads stronger than it means — no longer describes anything that exists). `exit-codes.md` and `pathspecs.md` are untouched.

**State becomes a compatibility surface.** Today, whether an empty year frame yields a plain or tainted null is nearly unobservable — it only changes whether one warning fires. Once users can *branch* on state, every row in that table above becomes a promise you have to keep. ## ID3v1 verification — it inverts your answer, for a good reason

ID3v1 is a fixed 128-byte trailer: `TAG` + title(30) + artist(30) + album(30) + **year(4)** + comment(30) + **genre(1)**, with v1.1 stealing two comment bytes for a NUL and a track byte. Working the "empty numeric field → unusable" rule through that structure turns up something structural:

**Every other format Goro reads makes field presence a deliberate act. ID3v1 does not.** A Vorbis `DATE` field exists because a tagger chose to write one. The four ID3v1 year bytes exist in *every ID3v1 tag ever written* — they are part of the struct. So if "data is there but can't be interpreted → unusable" keys off field existence, then **every ID3v1 file with a blank year warns**, and on a real collection that is a very large fraction of them. That's not a signal, it's a permanent noise floor, and it would land on exactly the format where the user has the least ability to do anything about it.

The fix isn't a special case in the type system — the three states survive untouched. It's one added clause to the *resolution* rules, which is where per-format differences belong:

> A fixed-width field padded entirely with NUL bytes or spaces records nothing, and therefore resolves to absent rather than to an unusable occurrence.

That keeps your answer intact for Vorbis, APE and ID3v2, where an empty field *was* written on purpose, and inverts it for ID3v1, where it wasn't. Principled rather than grafted: the question "does this file record anything here" is precisely what each namespace's resolution rules exist to answer, and it is legitimate for a fixed-layout format to answer it differently from a keyed one.

Then the barbarism proper. Five more things fall out, four of which are gaps in `identifiers.md` rather than consequences of the redesign:

**1. `"0000"` is not padding, and it is the common blank.** Trimmed, `"0000"` is four digits, matches the `YYYY` format, and resolves to **year zero**. Gregorian has no year zero, and `identifiers.md` explicitly says date-shaped data "conceptually resolves a full Gregorian calendar date". So as specified today, `id3v1::year == 0` is true for a great many files and `year BETWEEN 1900..2030` is quietly false for them. That's a *usable and wrong* value, which is strictly worse than an unusable one — no warning, no state test catches it, and the file silently fails every year filter. I'd have the date-shaped rules reject a year of zero outright → **unusable**. NUL/space padding → **absent**. Those really are two different things, and telling them apart is the new model working as intended.

**2. The genre byte, problem one: `0` means Blues.** `0xFF` is the conventional unset marker → absent, fine. But a tag zero-filled by a lazy writer has genre byte 0, which is a legitimate index meaning **"Blues"**. Under the model that is genuinely a usable value; there is no state for "the tagger probably didn't mean this", and there shouldn't be. This wants a documented caveat, which `identifiers.md` currently doesn't carry.

**3. The genre byte, problem two: unassigned indices are unspecified.** For byte 200 (no assigned genre), `identifiers.md`'s rule — "a reference to a table position that has no genre assigned to it is left as recorded" — is written for ID3v2's *text* frame and means nothing for a byte. Unspecified today. I'd say **unusable**: the byte is there and it doesn't name a genre.

**4. `id3v1::raw::genre` is a contradiction as written.** The doc says of that namespace: *"Year; the type of this identifier is the only difference with the `id3v1` namespace"* — which makes `id3v1::raw::genre` equal to `id3v1::genre`, i.e. `"Rock"`. But mapping byte 17 to `"Rock"` **is** interpretation, which is the one thing a raw namespace promises not to do. So it's either interpreted (breaking the namespace's promise) or it's `"17"` (breaking the stated "only difference is year"). This is S7 acquiring a fourth meaning of "raw", and it needs your call.

**5. `id3v1::track` does not exist.** ID3v1.1 defines a track byte, v1.1 is overwhelmingly the common variant in the wild, track is a prime filter field — and neither `id3v1` nor `id3v1::raw` lists it. Track byte `0` is the unset convention → absent. While in there, `id3v1::comment` is 30 bytes on v1.0 and 28 on v1.1, which the doc also doesn't mention.

Two further caveats ID3v1 earns and doesn't have (both "usable but wrong", correctly *not* new states): the format specifies ISO-8859-1 while files in the wild use whatever the local codepage was, so values can decode to mojibake — `identifiers.md` gives APE's older revision exactly this caveat and gives ID3v1 none; and 30-byte fields truncate on write, so `id3v1::artist == "…"` can fail where the facade succeeds.

**Net:** the model came through unchanged. All the pressure landed on per-format resolution rules, which is where you want it.

## Issues with NonBacktracking + CultureInvariant — yes, three worth naming

## Regex literal syntax — prior art

Four families, and the useful observation is that only one of them is actually about regexes.

**Slash-delimited** — `/pattern/flags`: Perl, JavaScript, Ruby, sed, awk, Vim, Raku. Dominant by far. Beyond your dislike, the domain argues against it independently: `/` is unusually common *inside* the patterns this tool will see — `AC/DC`, `3/12` track numbers, paths — so it would need escaping in precisely the frequent cases.

**Raw or verbatim strings, prefixed** — Python `r"..."`, Rust `r"..."` / `r#"..."#`, C# `@"..."`, C++ `R"(...)"`. Not regex literals at all; raw strings, which is what actually solves the escaping problem. Regexes in these languages are conventionally just raw strings.

**Alternative delimiters with no escape processing** — Go's backtick raw string, triple-quotes in Python/Kotlin/C#, Perl's `m{...}` with a chosen delimiter, PostgreSQL's `$$...$$` dollar quoting (`$tag$...$tag$` when the delimiter itself collides).

**No special syntax at all** — SQL. `LIKE`, `SIMILAR TO` and PostgreSQL's `~` all take ordinary string literals, and in *standard* SQL strings backslash is not an escape character, so `'\d+'` is already literal. PostgreSQL keeps that and offers `E'...'` when you want escapes. Worth noting because it's the mirror image of our problem: they made the ordinary string raw and added an escaping form, where we'd keep the escaping form and add a raw one.

### The reframe I'd argue for: we want a raw string, not a regex literal

A dedicated regex literal implies a regex *type*, and that asks questions with no good answers — can it be compared with `==`, can an identifier have it, how does it interact with the polymorphic numeric literal, is it a fifth type in a model we just closed? A raw string is simply a string: no new type, no new typing rules, and the existing static check ("the right operand of `~=` must be a valid pattern if it is a literal") works unchanged. It also earns its keep elsewhere — a tag comment holding a Windows path compares cleanly without doubling every separator. This is what Python, Go and Rust do in practice.

### What our grammar absorbs easily, ranked

**`r"..."` — my recommendation.** The lexer rule is one line: an identifier that is exactly `r` or `R` with a `"` immediately next, no whitespace, is a raw-string prefix. There's no grammatical ambiguity to resolve, because identifier-followed-by-string is not valid in any production — so nothing that parses today changes meaning, and `r == "x"` is untouched since the whitespace breaks the prefix. Strong familiarity from Python and Rust, and crucially **no shell hazard**.

**Backtick — cheapest to lex, and I'd reject it on shell grounds.** Zero collisions, trivial tokenising, good "raw" precedent from Go. But the predicate reaches Goro through a shell, and while backticks inside single quotes are literal, a user who double-quotes the argument — which they will, the moment a pattern contains an apostrophe — gets *silent command substitution*. The shell runs whatever is between the backticks. That failure is confusing at best and I don't think a CLI tool should accept it for a syntactic convenience.

**Triple-quote `"""..."""`** — needs genuine lookahead, since `""` is already a valid empty string and `""""` is ambiguous. Costs more than `r"..."` and buys nothing.

## How the raw literal is specified

The interesting choice is that `raw_string` folds **into** `string` rather than sitting beside it in `literal`:

```ebnf
string          = quoted_string | raw_string ;

quoted_string   = '"' { string_char | escape } '"' ;
string_char     = <any character other than '"' and "\"> ;
escape          = "\" ( '"' | "\" | "n" | "r" | "t" )
                | "\x" hex hex
                | "\u" hex hex hex hex ;

raw_string      = ( "r" | "R" ) '"' { raw_char | '""' } '"' ;
raw_char        = <any character other than '"'> ;

hex             = digit | "a" .. "f" | "A" .. "F" ;
```

`literal = string | number | bytecount | duration` needs no change, and because `name_part = name | string`, a raw string works as a quoted identifier part for free — `ape::r"album artist"` parses without another word of grammar.

**Two rules the productions cannot state**, which I put alongside the existing whitespace rule since the `r` prefix needing to abut its quote belongs there too:

- **A token is always as long as it can be.** This was already load-bearing and undocumented — it's what decides `5mb` in favour of a bytecount rather than a five-minute duration followed by a stray `b`. Your review flagged it as a gap; it's now written down.
- **Inside a raw string, a pair of quotes is taken greedily as the escaped quote**, so the string ends only at a quote standing alone. `r"a""b"` is the three characters `a"b`, and a raw string holding one quote needs four in a row.

And the reassurance that made `r"` safe: **an identifier is never followed by a string in any production**, so reading `r"` as a raw-string opener cannot change the meaning of anything that parsed before, and an identifier named `r` is untouched wherever whitespace, an operator or a `::` follows it.

## What `\N` actually does elsewhere

You haven't encountered one because it isn't a newline anywhere. It is, however, taken three times over:

- **Named Unicode character.** Python and Perl both use `\N{NAME}` — `"\N{GREEK SMALL LETTER ALPHA}"` gives α. Bare `\N` without braces is a syntax error in Python.
- **"Any character except newline."** Perl since 5.12, and PCRE, use bare `\N` in a *regex* as the complement of `\n`. So in the regex world `\N` means very nearly the opposite of a newline.
- **NULL.** MySQL and PostgreSQL use `\N` for NULL in text-format dumps.

In the C family it's simply invalid: Java and C# reject it at compile time, C is undefined behaviour with a warning, and **JavaScript silently drops the backslash and hands you `N`** — which is precisely the failure we avoided by making an unknown escape an error. I also verified that .NET's own regex engine rejects both `\N` and `\U` as unrecognized escapes.

**My recommendation is to keep the escape letters lower case, but for a better reason than the one currently in the doc: `\U`.** If escape letters are case-insensitive, `\U` becomes a synonym for `\u` taking four digits. In Python and Perl, `\uXXXX` is the four-digit form and `\UXXXXXXXX` the eight-digit one — and eight digits is exactly the improvement we'd want later, because a character outside the Basic Multipl Plane currently has to be written as a surrogate pair. Making the two synonyms permanently spends the one spelling that would fix that. `\N{...}` for a named character is a weaker version of the same argument.

So the cost of case-insensitivity isn't `\N` itself, which nobody will type — it's foreclosing two future spellings that other languages have already made conventional. If you'd still rather keep the blanket rule intact, that's a legitimate trade and I'll make the change; it's one clause either way.

Either way, **the justification clause in the Case sensitivity section needs rewriting.** It currently says `\N` being an error "is what a reader familiar with any other language expects", which overstates it — no language makes `\N` a newline, but JavaScript doesn't error on it either. If we keep lower case I'd replace that with the `\U` reasoning; if we go case-insensitive the clause goes away entirely.

## Precedent: there are two traditions, and they split cleanly

**`-o` / `--format` governs the payload only.** `kubectl -o json`, `docker --format`, `aws --output json`, `journalctl -o json`, `git --porcelain` — in all of them errors and diagnostics stay human prose on stderr, untouched. This is the dominant convention for *query* tools, which is what Goro is.

**A dedicated flag switches diagnostics to machine-readable.** `rustc --error-format=json` (stderr stays the diagnostic channel; only its format changes) and `cargo --message-format=json`. This is the convention for *compilers*, where diagnostics are the product rather than a side remark.

**And one outlier:** `npm --json`, where the flag means "everything I emit is JSON". This is the shape you're proposing, and it's the least imitated of the three.

So there is precedent for structured diagnostics — strong precedent — but essentially none for *coupling* them to the payload format switch. rustc and cargo both keep them on separate flags.

## I think coupling is a bad idea, and the reason is domain-specific

Not just precedent-counting. Three arguments, in ascending order of how much they persuade me:

**It couples two independent axes and deletes the two combinations people want.** "How should the answer be formatted" and "how should remarks be formatted" are orthogonal. Coupling gives you two of the four combinations, and the two you lose are both real: JSON rows with prose warnings (piping to a script while watching the terminal), and plain rows with structured warnings (a script that parses warnings but wants paths it can eyeball).

**It puts a global effect on a per-command option.** `-o` is documented per command; `--strict-exit-code` and `--no-warn` are established as global. Stderr's format is a global concern, so it belongs on a global flag or it's action at a distance — the same objection this design already made about modifiers sitting far from the operator that realises them.

**The decisive one: it contradicts why the streams are separate.** `warnings.md` says warnings go to stderr "so that they cannot interfere with the machine-readable output". The premise of that separation is that the two channels are *independently consumable by different audiences*. Coupling their formats says they're two halves of one output instead — which is a different design, and not the one the rest of the docs assume.

The scenario that settles it for me is the cron job you keep coming back to:

```sh
goro hash -o json > today.json 2>> warnings.log
```

JSON to a file for diffing; warnings accumulating in a log a human greps once a month. Those want *different* formats, and prose is the better one for the log. Coupling makes that invocation impossible.

**So: when the time comes, a separate narrow flag.** `--warn-format=plain|json`, parallel to `--no-warn`, global. Narrow is the reversible direction, and nothing stops a future `--json` convenience alias that sets both if that ever proves worth it.

## The bigger thing your ordering decision just exposed

Framing B9 as "array versus envelope" was my mistake. The real question is **array versus JSON Lines**, and your ordering decision is what makes it obvious.

A top-level array is the wrong container for this tool:

- It implies a document with a beginning and an end, which fights the streaming, unordered, concurrent model you just committed to.
- Over 100K files it either buffers everything or emits `[`, rows, `]` and has to get the commas right — and **an interrupted run leaves invalid JSON**. Given Ctrl-C is explicitly a thing the exit-code doc discusses, that's a real failure mode: a `hash` run over a huge library, killed at 80%, yields a file that no parser will read.
- It breaks the Unix composition you just invoked. `| sort`, `| head`, `| wc -l` all work on lines and none work on a pretty-printed array — which is exactly why I had to correct my own `sort` advice in `hash.md` a moment ago.

JSON Lines fixes all three. Every prefix is valid, so an interrupted run leaves 80K usable records. `sort`, `head` and `wc -l` work identically on both output formats, so the ordering answer becomes one sentence instead of two. `jq` consumes it natively, and `jq -s` reassembles an array for anyone who wants one. And it dissolves B9 outright: there is no wrapper, so there is no wrapper to foreclose — warnings could later ride the same stream as records with a different `type` field, with result/warning *interleaving preserved*, which the two-stream design can never offer.

The cost: `-o json` producing something that isn't a single JSON document surprises some people. Two ways to handle it — add `-o jsonl` alongside and leave `json` alone (additive, safe, but two JSON formats is clutter for a tool trying to stay lean), or redefine `json` as lines and say so plainly. I lean to the second, on the grounds that the array form's only advantage is looking familiar, and it's actively worse at everything this tool does.

This one does touch code — `JsonOutputRenderer` and its tests — so it's not free the way the doc changes have been. Small, though, and smaller now than after anyone depends on it.

2. **Finding the junk.** The inverse, and this is the strong one: `LITERALLY(id3v2::raw::TIT2) ~= r"^\s|\s$"` finds files with stray whitespace in their tags — a real cleanup task — and **only works if raw doesn't trim.** If everything trims, that query cannot be written at all.
3. **Empty versus whitespace-only.** A frame holding three spaces is a usable empty string if trimmed, and a usable three-space string if not.
4. **`NUMBER()` on padded numeric text.** `NUMBER(id3v2::raw::TLEN)` where the frame holds `" 240 "`: numeric literal syntax admits no surrounding whitespace, so untrimmed it's unusable and trimmed it's 240.

**"To return unusable?"** No — and this is worth being precise about. An untrimmed string is a perfectly good string, so not trimming produces a *different value*, never an unusable one. Unusability only arises where interpretation fails, and raw doesn't interpret. The single exception is (4), where the unusability happens downstream in `NUMBER()` rather than in the identifier.

## The recommendation

**Raw does not trim**, and I'd land it as a consequence rather than a decision: **interpretation trims, and raw does not interpret.** That folds the trimming rule into the principle already established for raw namespaces instead of adding an exception to it, which is the same move that settled the Id3v1 byte fields.

The decisive argument is (2). The raw namespace exists to be the one place you see what is actually there. If it trims, there is nowhere left to look, and "find my badly-padded tags" becomes unexpressible — in a tool whose purpose is library hygiene.

Against that, (4) is the only real cost, and it's narrow: wherever an interpreted counterpart exists it already trims and parses, so `id3v2::track` handles the padded case and you'd only be stuck on a frame with no interpreted counterpart, like `TLEN`. The obvious escape if anyone ever cares is a `TRIM()` function, which I'd not record anywhere — it's self-evident to whoever wants it.

## One consequence that needs stating, or the rules collide

The blank-field rule currently reads "a field that is empty, **or that holds nothing but whitespace**". If raw doesn't trim, that whitespace clause is an *interpreted-side* rule only — for raw, whitespace is content, so a three-space frame is a usable three-space string rather than a usable empty one.

And that must not be confused with the Id3v1 rule, which stays as it is in both namespaces: NUL-or-space padding in a fixed-layout field records **nothing**, so it's absent even in `id3v1::raw`. That isn't trimming, it's the question of whether anything was recorded at all — a different axis, and the two rules would look contradictory side by side unless the distinction is spelled out.

So the lifted rule in Definitions would be four layered statements:

- a fixed-layout field padded to blank records nothing, and is absent in either namespace;
- otherwise a field that exists holds whatever it holds;
- an interpreted identifier trims leading and trailing whitespace before using the value;
- a raw identifier does not, whitespace being part of what was recorded.

## The underlying problem

One rule is answering two independent questions:

## Proposed restructure — three rules on three axes

# Queue item 17 — suggested edits

Two `rationale.md` entries. They're less alike than my item implied: one restriction has a real cost, the other almost none, and I think the entries should say so.

## Entry 1

> Q: **Why must the second argument of `FALLBACK()` be a literal?**
>
> A: Because a literal default cannot be absent and cannot be unusable, and that is what makes the function total: whatever `FALLBACK()` is handed, its result is a usable value of the right type. A guard with no failure mode of its own is worth a good deal, and it is the whole reason the function is silent — there is no question of whether the default was evaluated, or of what happens when the default is itself the thing that is broken.
>
> Admitting an arbitrary expression would take that away and would reopen a question that has already been answered by removing something. `FALLBACK(vorbis::artist, id3v2::artist)` is what everybody would immediately write, and that is `COALESCE()`, which was dropped before first publication. The reason it was dropped is precisely the one that applies here: a construct selecting among several candidates has to say whether the candidates it did not use were evaluated, because that decides whether an unusable occurrence in an unused candidate warns, and no answer to that is both useful and consistent with the short-circuiting that `AND` and `OR` are relied on for. Letting the default be an expression would smuggle the same question back in through a function that exists to be simple.
>
> The cost is real and worth naming. Cross-format preference is expressible only for the five identifiers the global namespace covers; for anything else — an album artist, a composer, a disc number — there is no way to say "prefer the APE item, else the Vorbis field". The global namespace is the answer for the common cases and the honest position is that the uncommon ones are not served. Relaxing the restriction later would break nothing that is valid today, which is the direction worth keeping open.

## Entry 2

> Q: **Why must the endpoints of a range be literals?**
>
> A: Mostly so that `min > max` can be an error. A range whose endpoints are the wrong way round is a mistake rather than a query, it is worth catching, and catching it before any file is opened requires both endpoints to be known when the predicate is read. With arbitrary expressions the check would have to be dropped, losing a genuine diagnostic, or moved into evaluation, which would add a fourth per-file condition to a list this documentation has worked to keep at three.
>
> Two further questions would arrive with it, neither hard but both unnecessary. An endpoint that resolved to several occurrences would need the range itself to carry a quantifier, which is a new mechanism for a construct that is otherwise two literals and a pair of dots. An endpoint that resolved to nothing would need a rule about whether the range is then absent or the operator simply false.
>
> Unlike the restriction on `FALLBACK()`, this one costs almost nothing. A range between two values read from the same file is a query nobody has wanted, where cross-format preference is wanted constantly. That asymmetry is why the two restrictions read alike in the specification and are worth separating here.
