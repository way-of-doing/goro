For `*.mp3`-style glob matching, there are a few real options in .NET:

The search pattern already supports `*`/`?` wildcards matched against the filename, and `SearchOption.AllDirectories` makes it recursive. Here's the actual mechanics of what's happening:

**Why a registrar is needed at all**: Spectre.Console.Cli needs to construct your `HashCommand`/`ListCommand` instances when those subcommands run. Without a registrar, it falls back to `Activator.CreateInstance(commandType)` internally — which requires a **public parameterless constructor**. With a registrar, you tell it how to build command instances (and anything else), so they can take real constructor dependencies.

**The catch I hit**: once you supply a registrar, Spectre uses it as the *only* resolution mechanism for the whole framework — not just your types. Internally it registers its own default services (like a help provider) and later asks the registrar to resolve `IEnumerable<IHelpProvider>` — i.e., "give me every registered implementation of this interface, as a collection." My hand-rolled registrar was a dictionary of `Type → one factory`, so it has no concept of "multiple registrations of the same service" or "resolve me the whole collection." That's real container machinery, not just a lookup table, and Microsoft.Extensions.DependencyInjection already implements it correctly — that's precisely why Spectre's own official example wraps that package instead of a bespoke dictionary.

So concretely, your two options:

- **A — Microsoft.Extensions.DependencyInjection**: Add the package, build an `IServiceCollection`, register `FileDiscoveryService`, `TagLibAudioHasher`, `PipelinePlanner`, `ConcurrentExecutor`, `HashCommand`, `ListCommand` on it, `BuildServiceProvider()`, and write a thin `TypeRegistrar`/`TypeResolver` (per Spectre's documented pattern) that just forwards calls to that container. `Program.cs` stays the one composition root; commands keep clean constructor-injected dependencies. This correctly handles whatever Spectre needs internally because M.E.DI's container already does collection-resolution properly — it's not extra magic, just the standard, well-tested implementation of the thing I was trying to hand-roll.

Good catch — the current `IPipelineStage<TResult>` isn't really generic over its input, it's fixed to `string filePath`. That's precisely why it can't compose: stage B always expects a raw file path as input, never the output of stage A. A "verify" stage that wants to consume a `HashResult` (to compare it against something) has nowhere to plug in.

**The direct fix** — generalize the interface to carry both type parameters:

```csharp
public interface IPipelineStage<in TInput, TOutput>
{
    Task<TOutput> ExecuteAsync(TInput input, CancellationToken cancellationToken);
}
```

...and add a `Then` combinator that sequences two stages into one:

```csharp
public static IPipelineStage<TIn, TNext> Then<TIn, TOut, TNext>(
    this IPipelineStage<TIn, TOut> first, IPipelineStage<TOut, TNext> second) => ...
```

This is standard function composition (a Kleisli arrow, if you want the term) — `hashStage.Then(compareStage)` gives you a genuine `IPipelineStage<string, VerifyResult>`, built directly out of the existing hash machinery plus one new comparison stage. `IExecutor.ExecuteAsync` generalizes the same way (two type params instead of one); its actual implementation doesn't change at all, since `Parallel.ForEachAsync` never cared what the element type was — it was only the stage interface that hard-coded `string`. `IPipelinePlanner.PlanVerify(...)` would then literally be `PlanHash(options).Then(new CompareStage(...))`, which is exactly the reuse you're after.

**On TPL Dataflow**: it's the right tool if the pipeline ever becomes a real *graph* — fan-out (one file's result feeding multiple downstream consumers), fan-in (aggregating across files, e.g. a future "find duplicates" command), or backpressure between differently-paced stages. My recommendation: generalize `IPipelineStage`/`IExecutor` now (no new dependency, small change), and treat Dataflow as something to reach for later specifically when a command needs real fan-out/fan-in, not preemptively.

## Claude

Good instinct, and worth pulling on the specific worry you raised — it's pointing at a real bug, not just a stylistic concern.

Your sketch (`Entries.Where(...).SingleOrDefault(); return algorithm != default;`) has a subtle problem even before touching the enum's shape: `HashAlgorithmKind.Md5 = 0` (the first declared member), and in C# `default(HashAlgorithmKind)` *is* `0`. So `algorithm != default` can never distinguish "not found" from "found Md5" — both produce `algorithm == default`. That's exactly the sharp edge you sensed. Adding a synthetic `Unspecified = 0` member "fixes" it, but at the cost of a footgun everywhere else: any accidentally-uninitialized field or `default(HashAlgorithmKind)` elsewhere in the codebase would now silently mean something instead of being an obvious null/zero value. I'd avoid that.

There's a way to get the terseness you want without touching the enum at all: the `Entries` tuple has *two* fields, and only one of them (`Value`, the enum) has this default-collision problem — `Name` (a `string`) has a perfectly good, unambiguous `null` default. So use `Name`'s nullability as the "found" signal instead of the enum's:

```csharp
public static bool TryParse(string? value, out HashAlgorithmKind algorithm)
{
    var trimmed = value?.Trim();
    if (string.IsNullOrEmpty(trimmed))
    {
        algorithm = HashAlgorithmKind.Md5;
        return true;
    }

    var match = Entries.FirstOrDefault(e => string.Equals(e.Name, trimmed, StringComparison.OrdinalIgnoreCase));
    algorithm = match.Value;
    return match.Name is not null;
}

public static string ToName(this HashAlgorithmKind algorithm) =>
    Entries.FirstOrDefault(e => e.Value == algorithm).Name
    ?? throw new ArgumentOutOfRangeException(nameof(algorithm), algorithm, "Unsupported hash algorithm.");
```

Terse, no enum change, and the "not found" case is unambiguous by construction rather than by convention.

There's a second option that leans even harder into "self-explanatory": since this is fundamentally a name→value/value→name lookup, build two `Dictionary`s from `Entries` once (via LINQ's `.ToDictionary(...)`), and let `TryParse`/`ToName` become one-line `Dictionary.TryGetValue` calls — `TryGetValue` *is* the try-parse pattern, so there's no predicate/scan to read at all:

```csharp
private static readonly IReadOnlyDictionary<string, HashAlgorithmKind> ByName =
    Entries.ToDictionary(e => e.Name, e => e.Value, StringComparer.OrdinalIgnoreCase);
private static readonly IReadOnlyDictionary<HashAlgorithmKind, string> ByValue =
    Entries.ToDictionary(e => e.Value, e => e.Name);

public static bool TryParse(string? value, out HashAlgorithmKind algorithm) =>
    string.IsNullOrEmpty(value?.Trim())
        ? Set(out algorithm, HashAlgorithmKind.Md5)
        : ByName.TryGetValue(value.Trim(), out algorithm);
```
(that last one needs a tiny helper or an `if`-block for the default-case assignment — slightly less clean as a one-liner, so probably worth keeping as a short `if` + `return ByName.TryGetValue(...)`.)

I'd lean toward the `FirstOrDefault` version — it keeps the single `Entries` array as the one source of truth rather than three derived structures, which fits the "one file, one place" goal from last time. Same treatment would apply to `OutputFormatExtensions` for consistency.
